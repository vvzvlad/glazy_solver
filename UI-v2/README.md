# UI-v2 — прототип интерфейса и инструкция по внедрению

Рабочий React-прототип нового интерфейса решателя. Открывается локально:

```bash
python3 -m http.server 8000 --directory UI-v2
# http://localhost:8000/
```

Никакой сборки не нужно: React и Babel подключены с CDN, JSX транспилируется в
браузере. Это прототип, а не продакшн-сборка — про порт см. раздел 6.

---

## 1. Что это и чем отличается от `UI/`

Один экран вместо трёх режимов: **формула Зегера на входе → рецепт на выходе**.
Из старого интерфейса переехало всё, кроме структуры; из ТЗ намеренно **не**
реализованы пошаговый и интервальный режимы (обоснование — раздел 7).

Три колонки: цель → варианты → инвентарь.

## 2. Файлы

| Файл | Что внутри | Что с ним делать при внедрении |
| --- | --- | --- |
| `gs-data.jsx` | Мок-данные: материалы, решения, чувствительность, достижимость, пороги | **Заменить целиком** на слой запросов к API |
| `gs-ui.jsx` | Примитивы (`DeltaBar`, `Bar`, `NumField`, `Panel`…) и общая математика: матрица вкладов, «ради чего взят», статус ППП | Переносится как есть |
| `gs-side.jsx` | Левая колонка (цель, отношения, карта SiO₂×Al₂O₃) и правая (инвентарь) | Переносится как есть |
| `gs-results.jsx` | Вердикт достижимости, карточки решений, «на чём держится», матрица вкладов | Переносится как есть |
| `gs-app.jsx` | Оболочка, состояние, импорт, замес | Переносится, состояние — на выбор (useState/стор) |
| `gs-base.css` | **Все токены дизайна** (палитра в oklch, плотность, тёмная тема) + раскладка | Слить пять css в один |
| `gs-extra.css`, `gs-fix.css`, `gs-chart.css`, `gs-v2.css` | Наслоения по ходу работы | То же |

Порядок подключения css важен: `base → extra → fix → chart → v2`.

## 3. Куда что подключать — по блокам

Ниже: что показывает блок, откуда берёт данные сейчас и что должен дать бэкенд.

### 3.1. Цель (левая колонка)

| Что | Сейчас | Нужно от бэкенда |
| --- | --- | --- |
| Группы R₂O/RO, R₂O₃, RO₂ | `GS.OXIDE_GROUPS` | `GET /api/oxide_groups` — отдать `database/oxide_classification.json` |
| Роль оксида «треб. / попут.» | `guessRole()` в `gs-side.jsx` | Признаки считаются на клиенте, но нужны данные: `NEVER_ACCIDENTAL` и `OXIDE_THRESHOLD` (см. 3.5) |
| Кнопка «Σ 0.994 → 1.000» | локально | ничего |
| Si/Al, R₂O/RO | локально | ничего |
| Карта SiO₂×Al₂O₃ | локально | ничего |

**Роли — не косметика.** «Попутный» означает, что солвер не должен гнаться за
точным значением, а должен держать **одностороннее ограничение сверху**:
`Fe₂O₃ ≤ 0.03`, а не `Fe₂O₃ = 0.012`. Для NNLS это выбросить строку и проверить
границу постфактум; для feasibility-LP выражается напрямую. Без этого солвер
подсыпает 0.3% оксида железа ради третьего знака — то есть плодит junk.

### 3.2. Варианты решений (центр)

| Что | Сейчас | Нужно от бэкенда |
| --- | --- | --- |
| Рецепт, ошибка, число материалов | мок из реального прогона | `POST /api/solve` — есть |
| Бейджи junk / min / дрейф / ₽ / глины | `s.quality` | `quality_metrics.solution_quality` — есть в ветке |
| Бейдж «газы» | `U.loiStatus()` | **нет**: нужно поле ППП у материала со статусом, см. 3.6 |
| Подпись отличия («на костной золе», «глинозём вместо каолина») | `s.label`, `s.labelWhy` | **нет**: нужна кластеризация, см. ниже |
| «Свёрнуто ещё N похожих» | `s.collapsed` | то же |

**Кластеризация решений** — единственная заметная новая работа на бэке в этом
блоке. Правило: два решения считаются одним и тем же, если совпадает набор
материалов (с точностью до junk-компонента легче 2%) **и** каждая доля
отличается меньше чем на 1 абс.%. Порог 1% не выдуман — по нему Glazy считает
рецепты одинаковыми. Из кластера оставить лучший, остальные посчитать в
`collapsed`. Подпись отличия строится диффом против рекомендованного: выпавший
материал, замена, разница в числе компонентов, разница в цене.

Ранг «#3» пользователю не говорит ничего — подпись обязательна.

### 3.3. На чём держится рецепт

| Что | Сейчас | Нужно от бэкенда |
| --- | --- | --- |
| Доли риска по материалам | `s.sensitivity` | `POST /api/sensitivity` → `by_material` — **есть** |
| ±σ по оксидам | `s.spread` | тот же ответ, `per_oxide` — **есть** |

Формат `sensitivity` в моке точно повторяет ответ `recipe_sensitivity`, кроме
одного добавленного поля: `flux: true/false`. Оно нужно интерфейсу, потому что
для плавня фраза «двигает SiO₂» выглядит как баг — плавень задаёт знаменатель
unity и двигает формулу целиком. Считается тривиально: `via_oxide ∈ плавни`.

Показывать `per_oxide` **только для оксидов-требований**: сигма у пассажира
отвечает на вопрос, которого никто не задавал.

### 3.4. Загрязнение — три уровня вместо тревоги

Функция `contamination()` в `gs-results.jsx`. Оксид, которого нет в цели, — это
норма, а не ошибка: он приезжает с материалами всегда. Уровни:

* **след** — серым, без реакции;
* **заметно** — подпись эффекта («глушит», «красит») и кнопка «→ в цель»;
* **значимо** — цветом, это уже другая глазурь.

Для **плавней** порог не абсолютный, а доля от суммы плавней
(`FLUX_SHARE_NOTABLE`): незаявленный плавень меняет знаменатель и двигает всё.

Кнопка «→ в цель» переводит оксид в цель как попутный с верхней границей.

### 3.5. Пороги — единственное, что пока выдумано

`OXIDE_THRESHOLD` в `gs-data.jsx` помечен `PROVISIONAL`. Определение порога:
**нижняя граница диапазона, в котором оксид добавляют намеренно** — если он
приехал в таком количестве, глазурь будет цветной/глушёной независимо от
намерений.

Как получить настоящие числа: ступень 7.6 ТЗ уже предусматривает дамп Glazy
(~35 000 рецептов). Прогнать его **нашим** кодом в **нашей** конвенции, взять
распределение ненулевых значений по каждому оксиду, нижний квартиль и есть
порог. Побочно тот же прогон даёт дефолты для `oxide_weights`.

`NEVER_ACCIDENTAL` считается из `database/materials.json` в десяток строк:
оксид не может быть примесью, если его несут только материалы, которые сами и
есть этот оксид. По нашей базе это CoO, CuO, Cr₂O₃, SnO₂, ZrO₂, NiO, Li₂O —
любое их присутствие в цели есть намерение.

### 3.6. Инвентарь (правая колонка)

| Что | Сейчас | Нужно от бэкенда |
| --- | --- | --- |
| Список, поиск, «в наличии / вся база» | `GS.MATERIALS` | `GET /api/materials` — есть |
| Группировка (шпаты, глины, карбонаты…) | поле `group` в моке | **нет**: добавить поле или вывести из типа |
| Флаг «раств.» | поле `soluble` | **нет**: перенести `isWaterSoluble` из SegerLab (27 материалов из 216, см. `DATA_NOTES.md`) |
| ±% разброса паспорта | поле `tol` | `database/material_tolerance.json` — **есть** |
| Цена | поле `price` | `database/prices.json` — есть в ветке `feature/lp-step-intervals` |

**ППП** нужен отдельным полем со статусом, иначе бейдж газовыделения врёт:

* `passport` — из паспорта, доверяем;
* `residual` — посчитан как `100 − Σ оксидов`, доверяем только если анализ дан на непрокалённое вещество;
* `unknown` — анализ на прокалённое вещество, остаток ничего не значит.

Ловушка именно в третьем: у прокалённого анализа остаток равен нулю, и наивная
формула покажет «газовыделение 0», то есть «наколов не будет» — самый вредный
из возможных ответов. Поэтому бейдж показывается, только когда у **всех**
материалов рецепта статус `passport` или `residual`.

### 3.7. Вердикт достижимости

`GS.FEASIBILITY_OK` / `FEASIBILITY_BAD` → ступень 2 ТЗ, `check_feasibility`.
Формат мока повторяет ТЗ, кроме поля `why` у недостижимого оксида — короткая
человеческая причина («нет литиевого сырья в наборе»). Это то, чего не делает
ни один конкурент: они выдают плохой фит молча.

### 3.8. Импорт

Только **формула**, никогда не рецепт: формула Зегера и есть формат обмена, а
чужой рецепт назовёт материалы, которых у нас нет. Переключатель источника
(Glazy / Seger / своя) — это один коэффициент перенормировки:

```
u_наш[i] = u_чужой[i] / Σ u_чужой[k],   k ∈ наши плавни
```

Работает точно даже когда следовые оксиды обрезаны — оксиды, по которым
конвенции расходятся (Fe₂O₃ у SegerLab плавень, у нас нет), в наш знаменатель
и так не входят. Конвенции выписаны поимённо в `DATA_NOTES.md`.

## 4. Порядок внедрения

Каждый шаг самостоятелен и полезен без следующего.

1. **Каркас на текущем API.** Цель + инвентарь + карточки решений на
   `POST /api/solve` и `GET /api/materials`. Работает уже сегодня.
2. **Бейджи качества** — `quality_metrics` готов.
3. **«На чём держится рецепт»** — `POST /api/sensitivity` готов, добавить
   `flux` в ответ.
4. **Кластеризация вариантов и подписи отличий** — новая работа, но чистый
   постпроцессинг выдачи солвера, бэкенд не трогает.
5. **Вердикт достижимости** — ступень 2.
6. **Роли оксидов + односторонние ограничения** — ступень 3, `oxide_weights`.
   Проверяется измеримо: `junk_count` и `min_portion` на корпусе должны
   улучшиться.
7. **Пороги загрязнения** — после корпусного прогона.
8. **ППП и бейдж газов** — после появления поля.

## 5. Дизайн-система

Всё в `gs-base.css`, менять там.

* **Шрифты**: IBM Plex Sans (интерфейс) и IBM Plex Mono (все числа, с
  `tabular-nums` — колонки цифр выравниваются разряд в разряд). Оба с полной
  кириллицей.
* **Цвет**: тёплый нейтральный фон, один акцент (синий — действие и ввод
  человека) и три зарезервированных статусных тона. Всё в oklch.
* **Тёмная тема** — не инверсия, а отдельный набор токенов; переключается
  классом `gs-dark` на корне.
* **Плотность**: базовый кегль 12.5px, строка таблицы 20–24px. Расчёт на
  десктоп от 1280px; ниже 1180px правая колонка скрывается.

**Одно правило, которое важнее остальных:** шкала отклонения задана **одним
местом** — `TONE_OK = 0.02`, `TONE_WARN = 0.1` в `gs-ui.jsx`. В текущем `UI/`
код считает по 0.01/0.1, а легенда обещает 0.02/0.1 — рассогласование, которое
здесь физически негде допустить. Не заводите вторую копию порогов.

Отклонение показывается **тонкой полоской от центра**, а не заливкой всего
числа: число остаётся читаемым, сигнал несёт бар.

## 6. Порт в продакшн

1. `window.GS`, `window.GSUI`, `window.GSSIDE`, `window.GSRES` → обычные
   `export`/`import`. Это единственная неидиоматичность, и она навязана
   средой прототипа.
2. `gs-data.jsx` → слой запросов (fetch/react-query), форма данных не меняется.
3. Пять css → один файл или CSS-модули; токены оставить кастом-проперти.
4. Babel из браузера → любой бандлер.
5. React 18, хуки, никаких сторонних библиотек — ни графиков, ни UI-китов.
   Карта SiO₂×Al₂O₃ и все полоски — свой SVG и div-ы.

⚠️ **Формально это нарушает правило ТЗ «UI — vanilla JS без библиотек».** Решение
об этом принято отдельно; при внедрении правило в ТЗ надо либо отменить, либо
переписать прототип на ванили.

## 7. Что намеренно не реализовано и почему

| Что | Почему |
| --- | --- |
| **Пошаговый режим** (ступень 4) | Керамисту не нужно смотреть, как сходится NNLS. Единственное осмысленное содержание — «почему взят этот материал» — схлопнуто в колонку «ради Al₂O₃» в таблице рецепта |
| **Интервальный режим** (ступень 5) | Петля «сужай, пока не схлопнется» — инструмент исследования без точной цели, а пользователь приходит с точной. Полезная часть — достижимые доли материалов — вытащена в обычный режим |
| **Панель настроек солвера** | Выбор движка classic/iterative, seed, penalize_unlisted — внутренняя кухня. Спрашивать об этом керамиста значит расписаться, что мы сами не разобрались |
| **cond / rank** | Отладка солвера. Полезное содержание («материалы почти взаимозаменяемы») честнее выражается через чувствительность, в граммах и оксидах |
| **КТР** | Сообщество ему не верит («не знаю, верно ли калькуляторы считают»), автор ОВО новичкам — «забудьте о ктр». Число без набора коэффициентов и без КТР массы вредно |
| **Зоны на карте Стулла** | Их границы определены для одного флюсового баланса и одного конуса. Нарисовать их на глаз — декоративная наука |
| **Растяжки** | Журнальная функция, а не солверная: математики там нет, а нужен журнал с фото и режимами обжига. Эта ниша занята SegerLab. Наш аналог — пробники по чувствительности (v3, см. ниже) |

## 8. Следующие шаги по чувствительности

Реализован **v1** — ранжирование материалов по «плечо × неопределённость».

* **v2** — полосы ±σ по оксидам. Визуально почти бесплатно: `DeltaBar` уже
  умеет рисовать подложку (`spread`), нужны только данные.
* **v3** — пробники. Монте-Карло с **коррелированными** возмущениями (дрейф
  партии гидрата — это один общий фактор, а не независимые оксиды; текущая
  квадратичная сумма даёт верхнюю оценку), затем PCA облака, три цели вдоль
  главной оси, каждая решается обратно тем же солвером. На выходе — три
  настоящих рецепта, имитирующих плохую партию. Это отвечает на главную боль
  «формула сошлась, а глазурь не сошлась», и этого не может ни один конкурент.
