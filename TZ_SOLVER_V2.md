# ТЗ: LP-слой, унификация UMF-математики, пошаговый режим и интервальный режим (LIPGLOSS)

## 0. Контекст

Проект — решатель рецептов глазурей по UMF-формуле: `common.py` (математика UMF),
`solver_classic.py` (NNLS по случайным подмножествам), `solver_iterative.py`
(итеративный приоритетный beam search), `api_server.py` (Flask API + отдача UI),
`UI/` (vanilla JS, без фреймворков). Предыдущий рефакторинг завершён
(см. `REFACTORING.md`), обе ветки решателя работают, тесты зелёные.

Это ТЗ — следующий шаг, по результатам исследования отраслевых практик
(LIPGLOSS, Insight-live, glass batch calculation). Пять ступеней:

| Ступень | Что | Зачем |
| --- | --- | --- |
| 1 | Единая классификация оксидов + фиксы математики + детерминизм | Сейчас три расходящиеся копии списков флюсов и искажённая ошибка классика |
| 2 | Feasibility-LP + диагностика + валидация базы | Пользователь должен видеть «цель недостижима, виноват оксид X», а не молчаливый плохой фит |
| 3 | Взвешенная невязка NNLS | Следовые оксиды и молярные массы искажают метрику |
| 4 | Пошаговый режим (trace + playback в UI) | Наблюдать вживую, как итеративный решатель сходится |
| 5 | Интервальный режим а-ля LIPGLOSS | Цели-диапазоны, достижимые min/max по каждому оксиду |
| 6 | Модель additional-компонентов (isAddition) | Стандарт Glazy: добавки поверх базы 100%; данные уже в recipes.json, код их игнорирует |
| 7 | Тесты обратной задачи (UMF → рецепт) | Точные внешние оракулы + метрики качества решения + корпусная регрессия на дампе Glazy |

Ступени выполнять по порядку: каждая опирается на предыдущую. Исключение:
ступень 6 независима и может делаться в любой момент; ступень 7 требует
ступеней 1, 2 (feasibility для сценария B корпуса) и 6. После каждой
ступени — все тесты зелёные, атомарные коммиты.

**Жёсткие правила:**

- Python 3.13, **новых зависимостей не добавлять**: всё LP — через
  `scipy.optimize.linprog(method='highs')` (scipy>=1.7 уже в requirements).
- Комментарии в коде — только английские.
- UI — vanilla JS без библиотек (никаких chart.js и т.п.).
- Таргетные правки; существующие сигнатуры функций не ломать — только
  расширять опциональными параметрами со значениями по умолчанию,
  сохраняющими текущее поведение.
- Контракт `POST /api/solve` меняется (см. 2.4) — UI обновляется в той же
  ступени, ничего не остаётся сломанным между коммитами.

## Ступень 1 — единая классификация оксидов и фиксы математики

### 1.1 Проблема

Три расходящихся источника правды о том, что считать флюсом:

- `common.oxides_classification()` (`common.py:19-25`): RO включает MnO, FeO,
  CoO, NiO, CuO («extended»-стиль), **PbO отсутствует вовсе**;
- `common.calc_ratios_umf()` (`common.py:356-357`): RO — только
  MgO/CaO/SrO/BaO/ZnO, т.е. отношение R2O:RO считается в другой конвенции,
  чем нормировка UMF;
- `common.calculate_umf_from_recipe()` (`common.py:389-390`): собственные
  inline-копии списков;
- `UI/js/app.js:72-76` (`oxide_groups`): четвёртая копия, опять другая
  (PbO/CdO есть, MnO2 в RO2, P2O5 в R2O3).

Плюс: `solver_classic.solve_recipe()` (`solver_classic.py:121-139`) после
`weights_to_umf` (уже unity-нормированного результата!) дополнительно
масштабирует фактический UMF так, чтобы он совпал с целью по **наименьшему**

репортуемую ошибку; итеративный решатель этим путём не пользуется, поэтому

## Ступень 2 — feasibility-LP, диагностика, валидация базы

### 2.1 Новый модуль `feasibility.py` (чистая математика, без Flask)

Работаем в **молярном пространстве** с нормировкой на unity флюсов — это
делает ограничения линейными (UMF дробно-линеен, но однородно-линеен:
`lo <= n_i/S_flux <= hi  <=>  n_i - hi*S_flux <= 0  и  lo*S_flux - n_i >= 0`).
Этот же аппарат переиспользует ступень 5.

```python
    ...

def check_feasibility(target_umf, materials, tol=DEFAULT_FEASIBILITY_TOL):

```

`check_feasibility` — Чебышёв-LP (минимакс) через
`scipy.optimize.linprog(method='highs')`:

- Переменные: `x` (n материалов, сырые граммы) и `t` (максимальное отклонение).
- Нормировка масштаба: `S_flux(x) = f·A·x = 1` (равенство).
- Для каждого оксида i целевой формулы: `|(A x)_i - b_i| <= t * s_i`,
  где `b_i` — целевое UMF-значение, `s_i = max(b_i, 0.1)` — масштаб оксида
  (чтобы SiO2~3 и MgO~0.05 давали сопоставимый относительный допуск).
- Оксиды, которые материалы могут принести, но которых нет в цели
  (загрязнение), включаются в задачу с `b_i = 0` — как `_expand_target`
  в итеративном решателе.
- `x >= 0`, минимизировать `t`.
- Константы модуля: `DEFAULT_FEASIBILITY_TOL = 0.05` (5% относительных),
  `OXIDE_SCALE_FLOOR = 0.1` — с комментариями, что это настраиваемые пороги.

Возврат:

```python
{
  "feasible": bool,              # t* <= tol
  "max_relative_deviation": t_star,
  "per_oxide": [                 # sorted by |delta| desc
    {"oxide": "SiO2", "target": 3.151, "closest": 3.149, "delta": -0.002,
     "relative": 0.0006, "reachable": True},
    ...
  ],
  "unreachable_oxides": ["Li2O", ...],   # relative > tol
  "closest_recipe": {"Material": pct, ...}  # x* renormalized to sum 100
}
```

`closest_recipe` — бесплатный побочный продукт LP: `x*`, нормированный к 100%,
материалы < 0.1% отброшены. Это «ближайшая достижимая точка» для пользователя.

Если LP вернул `status != 0` (не сошёлся) — `{"feasible": None, "error": ...}`,
решатели при этом работают как раньше (feasibility — диагностика, не блокер).

## Ступень 3 — взвешенная невязка NNLS

### 3.1 Суть

NNLS сейчас минимизирует невязку в весовых %, что неявно взвешивает оксиды
молярной массой, а следовые оксиды либо тонут, либо шумят. Добавляем механизм
пооксидных весов важности: строки матрицы и целевого вектора домножаются на
`w_i` перед `nnls` — стандартный приём взвешенного МНК.

### 3.2 Правки

- `solver_classic.solve_recipe(oxide_matrix, target_umf, material_names,
  available_materials=None, oxide_weights=None)`:
  - `oxide_weights: dict[str, float] | None` — None = текущее поведение;
  - перед `nnls`: `A_w = diag(w) @ A`, `b_w = w * b`, где `w_i =
    oxide_weights.get(oxide, 1.0)`;
  - ошибка решения по-прежнему считается НЕвзвешенно (`calculate_umf_error`) —
    веса влияют только на оптимизацию, не на репортинг.
- Прокинуть `oxide_weights` через `solve_glaze_recipe`,
  `find_multiple_solutions`, `solver_iterative._solve_material_set` /
  `find_best_recipe` (опциональный сквозной параметр).
- API: опциональное поле `"oxide_weights": {"SiO2": 1.0, "Fe2O3": 0.2, ...}`
  в `POST /api/solve` и `POST /api/solve_iterative`.
- UI в этой ступени не трогать (веса — API-фича; появятся в UI при
  необходимости отдельной задачей).

### 3.3 Тесты

В `tests/test_solver_classic.py`: синтетический кейс из 3-4 материалов, где
целевой SiO2 систематически недобирается; с `oxide_weights={"SiO2": 10}`
абсолютная невязка по SiO2 в решении должна уменьшиться по сравнению с
невзвешенным запуском (и тест на то, что `oxide_weights=None` даёт байт-в-байт
прежний результат при том же seed).

## Ступень 4 — пошаговый режим (trace + playback в UI)

### 4.1 Архитектурное решение

Итеративный решатель сходится за секунды (сотни маленьких NNLS), поэтому
**никакого SSE/WebSocket**: решатель записывает полный trace своей работы,
UI получает его одним ответом и проигрывает как анимацию с перемоткой
(автовоспроизведение включено по умолчанию — визуально это и есть «вживую»,
плюс возможность отмотать назад, которой у настоящего стрима не было бы).

### 4.2 Правки `solver_iterative.py`

Ввести класс-регистратор:

```python
class SolverTrace:
    """Records solver states and events for step-by-step playback"""
    def __init__(self): self.states = []; self.events = []
    def add_state(self, parent_id, iteration, added, state) -> int: ...
    def add_event(self, event: dict) -> None: ...
    def as_dict(self) -> dict: ...
```

- `find_best_recipe(..., trace: SolverTrace | None = None)` — при `None`
  поведение и производительность не меняются (все вызовы трейсера под
  `if trace is not None`).
- Точки записи:
  - `start`: инвентарь, `target_umf`, `full_target`, стартовый набор
    (имена + приоритеты), стартовое состояние (id=0);
  - `_expand_state`: событие `expand` — `parent_id`, `iteration`,
    `focus_oxide`, топ кандидатов из `ranked` (имя, score, priority,
    ограничиться `TOP_CANDIDATES * 3`), результаты проб `trials`
    (имя, error, id нового state или null, попал ли в beam, stalled);
  - `_shrink_to_limit`: событие `shrink` (какой материал выброшен);
  - завершения веток: `branch_converged` / `branch_stalled`;
  - `finish`: список решений с их `state_id`.
- Каждый state в трейсе: `id`, `parent`, `iteration`, `added` (материал),
  `recipe`, `result_umf`, `error`, `materials_count`, `focus_oxide`
  (худший оксид этого состояния), `residual_umf` ({оксид: target-actual},
  только |значение| > 0.001).
- Новая обёртка:

```python
def find_best_recipe_traced(*args, **kwargs) -> dict:
    # {"solutions": [...], "trace": {...}}; each solution carries "state_id"
```

Путь сходимости решения восстанавливается по `parent`-ссылкам от
`state_id` до корня — это и есть таймлайн для playback.

### 4.3 Правки `api_server.py`

**Новый `POST /api/solve_iterative`:**

Запрос: `{"umf": {...}, "inventory": [...], "max_materials": 10,
"max_solutions": 5, "error_threshold": 0.1, "trace": false,
"oxide_weights": null}` (все кроме umf — опциональны).

Ответ: `{"solutions": [...], "feasibility": {...}, "trace": {...} | null}`.
Весь ответ прогонять через `make_json_safe` (в трейсе возможны inf/NaN).

### 4.4 UI: пошаговый режим

Файлы: новый `UI/js/steps.js`, правки `index.html` (подключение скрипта,
разметка панели), `styles.css`, минимальные правки `app.js`.

- **Рефакторинг для переиспользования**: `create_umf_element(recipe_umf)`
  (`app.js:552`) читает глобальный `current_umf` — переделать в
  `create_umf_element(actual_umf, target_umf)`, все текущие вызовы передают
  `current_umf` явно. Пошаговый режим вызывает её же для каждого шага.
- **Вход в режим**: переключатель «Пошаговый режим» рядом с существующим
  `min_materials_toggle`. При включении панель решений заменяется панелью
  playback; запрос уходит на `/api/solve_iterative` с `trace: true` и тем же
  инвентарём, что собирает `index.html`.
- **Панель playback:**
  - селектор решения («Решение #1 (ошибка 0.8%, 5 материалов)», ...) — по
    `solutions[].state_id` строится путь состояний от корня;
  - контролы: ⏮ назад, ▶/⏸ автоплей (интервал ~800 мс), ⏭ вперёд,
    ползунок `input[type=range]` по шагам; автоплей стартует сам при
    получении трейса;
  - заголовок шага: «Итерация k/N — добавлен {материал} — ошибка E»
    (стрелкой показать изменение ошибки против прошлого шага);
  - рецепт шага: таблица материал/вес%, добавленный на этом шаге материал
    подсвечен, у остальных — дельта веса против предыдущего шага серым;
  - UMF шага: `create_umf_element(state.result_umf, trace.target_umf)` —
    существующая раскраска расхождений работает из коробки;
  - блок «почему»: «хуже всего сходится: {focus_oxide}; кандидаты:
    name (score), name (score), ...; выбран: {added}» — из событий `expand`
    для перехода к этому состоянию;
  - прогресс ошибки: простая полоска-график из div-ов (высота ~40px, столбик
    на шаг, текущий шаг подсвечен) — без библиотек.
- **Прочее**: при изменении UMF-инпутов в пошаговом режиме — обычный debounce
  и перезапрос трейса; при выключении режима — возврат к обычному списку
  решений без повторного запроса (`current_solutions` сохраняются).

## Ступень 5 — интервальный режим (LIPGLOSS)

### 5.1 Суть

Пользователь задаёт **диапазоны** по оксидам (и опционально по материалам),
а система через LP отвечает: какие значения каждого оксида/материала вообще
достижимы при всех остальных ограничениях одновременно. Пользователь сужает
диапазоны, пока интервалы не схлопнутся в рецепт. Это главный рабочий режим
LIPGLOSS (два LP — min и max — на каждую величину).

### 5.2 Новый модуль `lp_intervals.py`

Использует `build_molar_matrix` и `flux_row` из `feasibility.py`.

Математика (ключ к корректности — однородность ограничений):

- Все ограничения записываются однородно-линейно и потому верны при любой
  нормировке масштаба:
  - оксид i в UMF-диапазоне `[lo_i, hi_i]`:
    `(A x)_i - hi_i * S_flux(x) <= 0` и `lo_i * S_flux(x) - (A x)_i <= 0`;
  - материал j в диапазоне весовых процентов `[lo_j, hi_j]`:
    `100 * x_j - hi_j * sum(x) <= 0` и `lo_j * sum(x) - 100 * x_j <= 0`;
  - `x >= 0`.
- Для min/max **UMF оксида i**: нормировка-равенство `S_flux(x) = 1`,
  целевая функция `±(A x)_i` (значение UMF линейно при этой нормировке).
- Для min/max **процента материала j**: нормировка-равенство `sum(x) = 100`,
  целевая функция `±x_j`.
- LP `status == 3` (unbounded) — верхняя граница бесконечна (реальный случай:
  max SiO2 не ограничен, пока в инвентаре есть чистый кварц и нет верхней
  границы SiO2) → в ответе `null`, UI показывает «∞».
- LP `status == 2` (infeasible) — ограничения несовместимы →
  `{"feasible": false}` для всего запроса (достаточно обнаружить на первом же
  LP; остальные не считать).

```python
def compute_intervals(oxide_constraints, materials,
                      material_constraints=None) -> dict:
    # oxide_constraints: {"SiO2": [3.0, 3.5], "Al2O3": [0.3, 0.5], ...}
    #   (UMF units; an oxide missing from the dict is unconstrained)
    # material_constraints: {"Nepheline Syenite": [0, 40], ...} (weight %)
    return {
      "feasible": True,
      "oxide_intervals": {"SiO2": [3.05, 3.42], "MgO": [0.0, None], ...},
      "material_intervals": {"Каолин КЖФ-1": [0.0, 55.3], ...},
      "example_recipe": {"Material": pct, ...},   # x from any solved LP,
    }                                             # renormalized to 100%
```

Какие оксиды включать в `oxide_intervals`: все из `oxide_constraints` плюс
все оксиды, которые могут принести материалы инвентаря (незаданные — без
ограничений, но их достижимый интервал тоже интересен — это и есть
«ползучее загрязнение» в цифрах). Материалы с нулевой формулой — исключать
(как в ступени 2). Число LP: 2×(оксиды + материалы), при ~20 материалах и
~15 оксидах это ~70 крошечных LP — быстро, оптимизировать не нужно.

### 5.3 `api_server.py`: новый `POST /api/intervals`

Запрос:

```json
{
  "oxide_constraints": {"SiO2": [3.0, 3.5], "Al2O3": [0.35, 0.42]},
  "material_constraints": {"Улексит (Химпэк)": [0, 20]},
  "inventory": ["...", "..."]
}
```

Ответ — результат `compute_intervals` через `make_json_safe`.
`inventory` опционален (default — `resolve_inventory()`), ограничения
материалов опциональны.

### 5.4 UI: режим интервалов

Файлы: новый `UI/js/intervals.js`, правки `index.html`, `styles.css`.

- **Вход в режим**: третье положение переключателя режимов (обычный /
  пошаговый / интервалы) — реализовать как группу кнопок-табов над панелью
  решений.
- **Ввод**: в интервальном режиме у каждой строки оксида вместо одного
  input — два (`min`/`max`). При входе в режим текущее точечное значение V
  разворачивается в `[V*0.9, V*1.1]` (пустые/нулевые — без ограничения).
  Debounce 500 мс → `POST /api/intervals`.
- **Вывод**:
  - в каждой строке оксида рядом с инпутами — достижимый интервал
    «⇒ [3.05 … 3.42]» (или «⇒ [0 … ∞]»); интервал уже, чем 0.01 —
    подсветить зелёным (схлопнулся); заданный диапазон, не пересекающийся
    с достижимым, — красным;
  - в панели материалов (чекбоксы инвентаря в `index.html`) — у каждого
    отмеченного материала серым его достижимый диапазон «0–55%»;
  - блок «пример рецепта из допустимой области» — `example_recipe`
    (рендер тем же кодом, что рецепт решения);
  - `feasible: false` — красный блок «Ограничения несовместимы — расширьте
    диапазоны» вместо интервалов.
- Ограничения по материалам в UI v1 не редактируются (только отображение
  достижимых диапазонов); redактирование — задел на следующую итерацию.
  URL-hash в интервальном режиме не трогать (persist только точечного UMF,
  как сейчас).

## Ступень 6 — модель additional-компонентов (isAddition)

### 6.1 Данные и проблема

Стандарт Glazy: база рецепта нормирована к 100%, добавки (колоранты,
глушители, SiC) задаются как +X% сверх базы с флагом `isAddition`.
В `database/recipes.json` эти данные **уже лежат** в Glazy-формате:

```json
{"recipeId": ..., "name": ..., "type": ...,
 "includeAdditionsIntoCalculations": false,
 "recipe": [{"material": {"id": ..., "name": "..."}, "value": 30, "isAddition": false}, ...]}
```

Факты (проверены):

- 11 рецептов, база каждого суммируется ровно в 100, добавки поверх (до 13%);
- у 5 рецептов реальные добавки: «Матовая кальциевая» (TiO2 4), «Флотинг»
  (TiO2 5, Fe2O3 3), «Пенная» (TiO2 10, SiC 0.5), «Белая глянцевая»
  (циркон 7, SnO2 6), «Марганцевый металлик» (CuCO3 8, CoCO3 2, Fe2O3 3);
- `includeAdditionsIntoCalculations` у всех 11 — `false`;
- `common.load_recipes()` никем не вызывается — форму возврата можно менять;
- фикстуры `tests/fixtures/reference_recipes.json` — те же 11 рецептов, но
  добавки при создании **выброшены**, а UMF посчитан по базе.

Семантика флага: `include_additions == false` → добавки — чистые метаданные,
химия (UMF) считается по базе; `true` → добавки участвуют в химии
(конвенция дампа Glazy: нормировка по полному весу рецепта — для UMF это
чистый масштаб, отдельной математики не требуется, достаточно включить
добавки в суммирование оксидов).

**Жёсткий инвариант ступени:** все текущие флаги false ⇒ ни один эталонный
UMF и ни одно поведение существующих тестов не меняется.

### 6.2 `common.py`: модель рецепта

- `load_recipes()` — переписать, возвращать нормализованные записи:

```python
{
  "recipeId": ...,
  "name": ...,
  "type": ...,
  "include_additions": bool,   # from includeAdditionsIntoCalculations, default False
  "base": {material_name: value},        # entries with falsy isAddition
  "additional": {material_name: value},  # entries with truthy isAddition
}
```

  Имя — из `entry["material"]["name"]`; повтор материала внутри одной части —
  суммировать; отсутствующие флаги трактовать как false.

- `merge_recipe_components(base, additional)` — плоский `{имя: вес}`,
  пересекающиеся материалы суммируются; аргументы не мутируются.
- `recipe_for_chemistry(recipe)` — для нормализованной записи: merged, если
  `include_additions`, иначе копия `base`.
- `fixture_chemistry_recipe(reference)` — то же правило для записи фикстуры
  (`reference["recipe"]` + `reference.get("additional", {})` при

## Ступень 7 — тесты обратной задачи (UMF → рецепт)

### 7.1 Принцип: два уровня проверки

У обратной задачи нет единственного решения, поэтому веса рецепта ассертятся
**только** в определённых системах (материалов ≈ оксидов, матрица
невырождена — там решение единственно; кейсы 7.4). Для всех остальных
кейсов проверка двухуровневая:

1. **Химия** (необходимое условие): `forward(solver(UMF, materials)) ≈ UMF`,
   судья — наш прямой расчёт. Само по себе это тест достижимости, а не
   качества — солвер его уже проходит.
2. **Качество** (главный уровень): решение сравнивается с оригинальным
   рецептом по метрикам 7.3. Оригинал — не «правильный ответ»
   (решений много), а **доказательство существования**: эту химию можно
   получить вот таким числом материалов, такими долями и такой стоимостью.
   Требование к солверу — «не хуже оригинала по каждой оси», а не
   «совпасть с оригиналом».

Все нужные эталонные числа вшиты в эту ступень — внешних документов для
выполнения не требуется.

### 7.2 Предусловия

- **(а) Пресеты конвенций флюсов.** Наш набор unity — это конвенция
  ceramicscalc-2018; современный Glazy считает иначе (без FeO/CoO/NiO/CuO,
  с MnO и PbO), поэтому на рецептах с колорантами таргеты из Glazy
  разъезжаются с нашими на ~20% по всем оксидам сразу (проверено на рецепте
  с 4.77% CuO: лишние 0.06 моль CuO в знаменателе unity раздувают его в
  1.22 раза и пропорционально проседают весь UMF). В
  `database/oxide_classification.json` (из ступени 1) добавить:

```json
"unity_presets": {
  "legacy": ["Na2O", "K2O", "Li2O", "MgO", "CaO", "SrO", "BaO", "ZnO", "PbO", "MnO", "FeO", "CoO", "NiO", "CuO"],
  "glazy":  ["Na2O", "K2O", "Li2O", "PbO", "SrO", "BaO", "ZnO", "CaO", "MgO", "MnO"]
}
```

  `weights_to_umf()` / `calculate_umf_from_recipe()` получают опциональный
  параметр `convention="legacy"` (default — текущее поведение). Тесты,
  сравнивающие с опубликованными Glazy-числами, используют `"glazy"`;
  корпусные round-trip тесты конвенции не касаются (таргет считается нашим
  же forward-расчётом).

- **(б) Тестовый шов — инъекция материалов.** Оба решателя жёстко грузят
  `database/materials.json`. Добавить опциональный параметр
  `materials=None` в `find_multiple_solutions` / `solve_glaze_recipe` /
  `find_best_recipe`: None → как сейчас, иначе — использовать переданный
  список записей материалов (той же структуры, что materials.json).

### 7.3 Метрики качества решения: модуль `quality_metrics.py`

Новый чистый модуль (без Flask), используется корпусным тестом,
`compare_solvers.py` и юнит-тестами:

```python
def solution_quality(recipe, original, materials,
                     prices=None, priorities=None) -> dict:
    # recipe, original: flat {material: weight percent} dicts (each sums to ~100)
    # materials: material records (formulas, for LOI and clay detection)
    # prices: optional {material: price per kg}; priorities: optional {material: int}
```

Метрики (для каждой возвращать значение решения, значение оригинала и
дельту/отношение; пороги — именованные константы модуля):

| Метрика | Как считается | Порог «не хуже» (default) |
| --- | --- | --- |
| `count_delta` | len(recipe) − len(original) | ≤ +1 |
| `junk_count` | число компонентов легче 2.0 вес.% | junk решения ≤ junk оригинала |
| `min_portion` | наименьший вес компонента | ≥ 1.0%, если у оригинала минимум ≥ 1.0% |
| `cost_ratio` | Σ price·w/100 решения ÷ то же оригинала | ≤ 1.2 |
| `priority_ratio` | Σ priority·w/100 решения ÷ то же оригинала | ≤ 1.2 |
| `rounding_drift` | UMF-ошибка решения после округления долей до 0.5% и перенормировки к 100 | ≤ 0.02 |
| `assembly_score` | «собираемость»: cost_abs × len(recipe); без цен — len(recipe) | абсолютного порога нет — отслеживается против baseline (7.7) |
| `set_jaccard`, `share_delta` | пересечение множеств материалов; сумма abs(Δ долей) по общим | без порога, диагностика |
| `clay_content` | суммарная доля глинистых материалов (ключевые слова в имени: каолин/глина/бентонит/kaolin/clay/bentonite) | warning, если < min(5%, половина от оригинала) |
| `loi_delta` | abs(LOI замеса решения − оригинала); LOI замеса = 100 − Σ вкладов оксидов на 100 г сырья | без порога, диагностика |

Пояснения:

- `rounding_drift` — главная анти-вырожденность: решение на компенсирующей
  паре коллинеарных материалов разваливается от ±0.5% погрешности весов,
  честный рецепт устойчив. Считается через `calculate_recipe_composition` +
  `weights_to_umf` до и после округления, ошибка — `calculate_umf_error`.
- `cost_ratio` считается только когда цены покрывают **все** материалы обеих
  сторон; иначе `null` + поле `cost_coverage` (доля покрытых материалов).
  Цены регион-зависимы (США — фритты, РФ — сырые компоненты), поэтому
  `cost_ratio` осмыслен только когда решение и оригинал живут в одной
  снабженческой реальности; для чужого оригинала (Glazy) считать вместо
  ratio **абсолютную** стоимость нашего решения `cost_abs` (руб/кг замеса).
- `assembly_score` — «легко ли это собрать» для случаев без сопоставимого
  оригинала (сценарий B корпуса; доступность там гарантирована
  конструкцией — инвентарь только наш, собираемость вырождается в цену и
  число позиций): `cost_abs × len(recipe)`; пока цен нет —
  `len(recipe)` с пометкой `cost_abs = null`. Абсолютного порога у метрики
  **нет** — она отслеживается относительно baseline-прогона (7.7): смотрим,
  не стала ли хуже после изменений солвера, и видим, когда тюнинг начал
  оптимизировать лучше. Внутри одного прогона скор дополнительно ранжирует
  несколько решений одной цели.
- `priority_ratio` — прокси дешевизны/доступности для нашей базы
  (`priorities.json`, меньше = базовее; материал без записи = DEFAULT_PRIORITY);
  для дампа Glazy не применяется.
- `clay_content` — технологичность: глазурь без глинистых материалов не
  держится в суспензии, даже если химия идеальна.

Новый файл `database/prices.json` — формат `{"Каолин КЖФ-1": 90}` (цена
руб/кг). Заполняется **один раз** агентной разметкой: агент собирает цены
российских поставщиков по нашей базе материалов (в первую очередь
inInventory и материалы из `priorities.json`, остальные по мере надобности),
результат проверяется человеком и коммитится; дальше файл просто живёт в
репозитории и правится руками при смене цен. Материал без записи выпадает
из cost-метрики (см. `cost_coverage`). Сбор цен — разовая задача вне кода
солвера, в ступень входит только формат файла и его потребление метриками.

`compare_solvers.py` дополнить колонками `junk`, `drift` и `cost` (при
наличии цен) — сравнение движков становится сравнением качества, а не
только химии.

Юнит-тесты `tests/test_quality_metrics.py` (синтетика, без солвера):
junk/min_portion детектятся на рукотворном рецепте; `rounding_drift` на
паре почти-коллинеарных материалов с компенсирующими долями заметно больше,
чем на однозначном рецепте; `cost_ratio == null` при неполном покрытии цен.

Задел на будущее (в этой ступени НЕ делать): те же метрики затем включаются
в сам солвер — parsimony уже есть (сортировка по числу материалов),
least-cost режим — это целевая функция `min Σ price·x` на LP-аппарате
ступени 5.

### 7.6 Корпусный бенчмарк на дампе Glazy

`tests/test_inverse_corpus.py`, медленный, по умолчанию скипается:

- **Данные**: официальный дамп Glazy — репозиторий
  `github.com/derekphilipau/glazy-data`, файл `glazy_20260531.yaml.gz`
  (~8 МБ gz; имя пиновать; актуальное имя опубликовано в файле `LATEST`

  скачать raw-файл в кэш `~/.cache/glazy_solver/` (requests уже в
  зависимостях); нет файла и сети → `skipTest`. Дамп в git **не коммитить**
  (CC BY-NC-SA; в кэш — можно, политика Glazy этот сценарий прямо разрешает).
- **Формат дампа** — плоские YAML-записи с полями `ID`, `Parent ID`, `Name`,
  `Type` (`Material` / `Recipe` / `Analysis`), `Cone`,
  `Ingredients: [{ID, Name, Percentage, Additional}]`,
  `Percent Analysis: {оксид: %, LOI: %}`. Материалы хранятся как прокалённые
  оксиды + LOI (сумма ≈ 100); карбонаты уже разложены (Dolomite =
  `MgO 21.91 / CaO 30.48 / LOI 47.61`), у фритт LOI 0. В дампе ~7300
  материалов и ~35000 рецептов с ингредиентами.
- **Разбор**: материалы (`Type: Material`, `Percent Analysis` → наша
  `formula`, LOI отбросить) и рецепты (`Type: Recipe` с `Ingredients`,
  флаг `Additional` → модель ступени 6 с `include_additions=True` —
  конвенция дампа: добавки входят в химию). Рецепты с неразрешимыми
  материалами (приватные/удалённые, ~1% дампа) — отфильтровать.
Два сценария; практическая задача солвинга всегда одна — «сделать доступную
глазурь из текущих компонентов», но «доступные компоненты» регион-зависимы
(США — фритты, РФ — сырьё), поэтому сценарии тестируют разное.

**Сценарий A — воспроизведение своими же материалами** (заведомо достижимо,
тестирует качество решения):

- **Выборка**: детерминированная (фиксированный seed), ~300 рецептов,
  стратифицированная по числу материалов (2–4 / 5–7 / 8+).
- **Прогон**: inventory = материалы самого рецепта (через шов 7.2(б));
  target = наш `forward(merged)` — благодаря этому конвенция флюсов и
  glazy-нормировка не влияют; движок — iterative на всей выборке, classic —
  на подвыборке 50 (медленный).
- **Критерии — двухуровневые** (7.1), оригинальный рецепт дампа — baseline:
  1. химия: `calculate_umf_error ≤ 0.1`;
  2. качество (`solution_quality` против оригинала): `count_delta ≤ +1`,
     junk решения ≤ junk оригинала, `min_portion` по правилу 7.3,
     `rounding_drift ≤ 0.02`; cost/priority в сценарии A не считаются
     (цен и приоритетов для Glazy-материалов нет).

  Доля кейсов, прошедших **оба** уровня — **≥ 90%** (стартовый порог,
  зафиксировать по первому прогону); отдельно репортить долю прошедших
  только химию — разрыв между цифрами и есть мера «плохих, но химически
  верных» решений. Провалы логировать (id, name, уровень, метрика,
  значение).

**Сценарий B — чужая химия из нашего инвентаря** (реальный сценарий
использования: увидел фриттовый рецепт — повтори из своего сырья):

- **Выборка**: подвыборка ~100 UMF из сценария A (тот же seed).
- **Прогон**: inventory = наши inInventory-материалы (как в бою);
  target — тот же `forward(merged)` от дампового рецепта. Сначала
  `check_feasibility` (ступень 2): недостижимые из нашего инвентаря цели
  (нет Li-сырья и т.п.) попадают в корзину «честно недостижимо» — это
  **не** провал, это правильный ответ.
- **Критерии** для достижимых целей: жёсткий гейт — только химия
  (`calculate_umf_error ≤ 0.1`) и доля «решено ИЛИ честно недостижимо»
  ≥ 90%; качество (`assembly_score`, `min_portion`, `rounding_drift`,
  `priority_ratio`) не гейтится абсолютными порогами, а записывается в
  снапшот и отслеживается относительно baseline (7.7). Мисклассификации
  (feasibility сказал «достижимо», солвер не решил) логировать отдельно —
  это прямой баг-репорт на солвер или на LP.

Полный прогон обоих сценариев ≤ ~10 минут.

**Зависимость**: дамп — YAML, парсер нужен. Разрешённое исключение из
правила «без новых зависимостей»: `requirements-dev.txt` с `pyyaml`,
используется только тестами уровня корпуса; runtime `requirements.txt`
не трогать.

### 7.7 Baseline качества и регрессионный дифф

Смысл: качество решений не гейтится числами с потолка — вместо этого весь
корпус один раз прогоняется солвером, результат фиксируется как baseline,
и дальше любое изменение солвера измеряется диффом против него.

**Снапшот `bench/quality_baseline.json`** (коммитится в репозиторий):

- по каждому кейсу — **сырые компоненты**, не только свёртка: `glazy_id`,
  сценарий (A/B), статус (solved / infeasible / failed),
  `calculate_umf_error`, `len(recipe)`, `cost_abs`, `assembly_score`,
  `min_portion`, `junk_count`, `rounding_drift`. Свёртка пересчитывается
  на лету при диффе — смена формулы `assembly_score` не обнуляет baseline;
- метаданные прогона: seed и список id выборки, версия солвера (git-коммит),
  **хэши входных данных** — `materials.json`, `prices.json`,
  `oxide_classification.json`. Хэши обязательны: они отделяют «солвер
  изменился» от «данные изменились» (обновление цен сдвигает cost-метрики
  без единой правки солвера — это не регрессия).

**Дифф-скрипт `bench/diff_baseline.py`**:

- прогоняет ту же выборку текущим солвером, сравнивает покейсово с baseline;
- отчёт: improved / worsened / unchanged (по каждой метрике) и **полный
  профиль распределения** по каждой метрике, не только среднее: min / p10 /
  медиана / среднее / p90 / p99 / max, «было → стало» по каждому агрегату.
  Среднее прячет хвост: тюнинг может улучшить медиану и одновременно
  угробить несколько кейсов — ловится именно по p90/p99/max. Плюс доля
  solved и топ-10 ухудшившихся кейсов с деталями (id, метрика, было → стало);
- перцентили считать на **пересечении** множеств решённых кейсов обоих
  прогонов (иначе кейс, перешедший из solved в failed, молча сдвигает
  распределение); изменения самого множества solved — отдельной строкой
  («решалось → перестало» и наоборот, со списком id);
- при несовпадении хэшей данных — крупное предупреждение «изменились данные,
  не только солвер» вместо молчаливого сравнения;
- режим `--check`: exit 1, если ухудшились больше чем на 5% (именованная
  константа) медиана ИЛИ p90 `assembly_score`, либо упала доля solved, либо
  вырос max химической ошибки — хвост гейтится наравне с центром; для
  ручного запуска перед мержем изменений солвера, в `unittest discover`
  не входит;
- перезапись baseline — только явной командой `--rebaseline`, отдельным
  коммитом с объяснением, почему уровень сдвинут.

### 10.9 `rounding_drift` — не детектор вырожденности (метрика заменена)

Утверждение §7.3 «`rounding_drift` — главная анти-вырожденность» **опровергнуто
измерением** и отменяется. Проверено исчерпывающим перебором химически
эквивалентного семейства решений (все расщепления массы шпата по
почти-коллинеарному двойнику с шагом 0.1: 39 двухкомпонентных и 83 845
трёхкомпонентных вариантов): максимальный drift вырожденного решения —
**0.0153**, порога 0.02 оно не достигает в принципе.

Причина структурная, а не в подборе чисел: при неотрицательных весах и
неотрицательных анализах отображение «веса → химия» липшицево с умеренной
константой, поэтому ограниченное возмущение весов (±0.25% на компонент от сетки
0.5%) даёт ограниченное возмущение химии **независимо** от обусловленности
обратной задачи. Коллинеарность делает плохо определёнными **веса**, а химия
при этом остаётся устойчивой — перенос 0.25 г между материалами, отличающимися
на 0.5 абс.% по оксиду, меняет замес на 0.00125 г этого оксида.

Хуже того, гейт `≤ 0.02` бракует честные решения: тот же рецепт с неудачными
десятыми (41.3 / 28.7 / 19.4 / 10.6 вместо 41.1 / 28.9 / 19.5 / 10.5) даёт
**0.027** без всякой вырожденности. Метрика доминируется расстоянием долей до
сетки 0.5%, то есть точностью печати решателя, а не качеством решения.

**Что реально работает — обусловленность матрицы использованных материалов**
(измерено на тех же трёх рецептах):

| рецепт | cond(A_used) | rounding_drift |
| --- | --- | --- |
| честный | 15.1 | 0.0052 |
| честный, неудачные десятые | 15.1 | 0.0271 |
| вырожденный (компенсирующая пара шпатов) | **3668.8** | 0.0145 |

Различение в 240 раз, не зависит от десятых долей, и порог `1e3` из
`matrix_diagnostics` (§2.2) ложится ровно между. Правки:

1. В `quality_metrics.solution_quality` добавляется метрика `conditioning`:
   `cond` матрицы «оксиды × использованные материалы» (та же
   `create_oxide_matrix`, сингулярные числа), плюс `rank` и
   `redundancy = len(recipe) − rank`. Порог — именованная константа
   `MAX_CONDITION_NUMBER = 1e3`, общая по смыслу со ступенью 2.
   Это и есть анти-вырожденность.
2. `rounding_drift` **остаётся**, но переводится в диагностику: он честно
   измеряет «можно ли этот рецепт взвесить на грубых весах», абсолютного
   гейта у него больше нет, значение пишется в baseline и отслеживается
   как остальные.
3. §7.5 (стресс коллинеарности): ассерт `rounding_drift ≤ 0.02` заменяется на
   `conditioning.cond ≤ 1e3` — то есть решатель не должен возвращать решение,
   держащееся на компенсирующей паре. Это ровно то, что тест и должен ловить.
4. §7.6 сценарий A: `rounding_drift ≤ 0.02` убирается из критериев качества,
   вместо него `conditioning.ok`.

### 10.10 `assembly_score` без цен — `null`, а не число компонентов

Формулировка §7.3 «`assembly_score` = cost_abs × len(recipe); без цен —
`len(recipe)`» **отменяется**: она кладёт в одно отслеживаемое поле числа в
разных единицах. Живой пример, на котором это и вскрылось (recipe_04,
итеративный решатель, наш инвентарь):

| вариант | покрытие цен | cost_abs | assembly_score |
| --- | --- | --- | --- |
| решение с древесной золой | 0.86 | `null` | **5.0** (штуки) |
| решение без золы | 1.00 | 248.93 | **995.7** (руб×штуки) |
| оригинал рецепта | 1.00 | 107.80 | 431.2 (руб×штуки) |

Дифф baseline сравнил бы 5.0 с 431.2 и отчитался о «улучшении в 86 раз».
Правки:

1. `assembly_score.value` = `cost_abs × len(recipe)`, а при неизвестной
   стоимости — **`None`**. Никакого молчаливого падения в другие единицы.
2. Число компонентов и без того отслеживается отдельной метрикой (`count`),
   поэтому при `assembly_score = None` информация не теряется: в baseline
   сравниваются `count`, `junk`, `min_portion`, `conditioning`, а
   `assembly_score` просто не участвует в агрегатах по этому кейсу.
3. Дифф-скрипт (§7.7) считает перцентили `assembly_score` только по кейсам,
   где он определён в **обоих** прогонах — то же правило пересечения, что уже
   принято для множества solved.

Побочно тот же замер показал, зачем цена вообще нужна в метрике: оригинал
recipe_04 (мел 40 + кварц 20 + каолин 10 + нефелин 30) стоит 107.8 ₽/кг, а
решатель выдаёт ту же химию через волластонит 57.8% за 248.9 ₽/кг — в 2.3 раза
дороже, потому что волластонит (343 ₽/кг) заменяет мел (79) с кварцем (126).
Химически безупречно, экономически глупо, и без цены невидимо.

### 10.11 Стартовый набор и порог отсева следовых компонентов

`database/priorities.json` держал «Древесную золу» и «Костную золу» в
приоритете **1**, то есть впереди базовых материалов. `_priority_start_set`
набирает целыми группами, поэтому стартовый набор итеративного решателя был
7 материалов, начинаясь с двух зол. Ни один из 11 эталонных рецептов золу не
использует, и цену древесной золы вообще невозможно найти — её не продают.

Правки в данных: обе золы **убраны из `priorities.json` полностью** (получают
`DEFAULT_PRIORITY = 100`, как бентонит и бура — «не приоритетный материал
вообще», гарантированно вне стартового набора и в хвосте ранжирования
кандидатов); «Мел, CaCO3» поднят 10 → 2, «Полевой шпат FFF» 5 → 2. Стартовый
набор стал: волластонит / каолин / кварц / мел / нефелин-сиенит / полевой
шпат / улексит.

Один только этот сдвиг ухудшил дело, и это оказалось диагностично: расширенный
стартовый набор дал решателю больше возможностей навесить **следовый**
компонент ради четвёртого знака оксида (полевой шпат 0.37% в рецепте 01).
Ровно то, что ловит метрика `junk`. Поэтому `MIN_MATERIAL_WEIGHT` в
`solver_iterative.py` поднят **0.1 → 1.0**: один процент от замеса в 100 г —
это 1 г, граница доверия студийным весам.

Итог по всем 11 эталонным рецептам:

| | как закоммичено | приоритеты + порог 1.0 |
| --- | --- | --- |
| суммарная UMF-ошибка | 115.6420 | **115.5467** |
| точное совпадение набора материалов с оригиналом | 6/11 | **7/11** |
| следовых компонентов (< 2%) | 6 | **0** |
| `assembly_score` хуже оригинала | — | ни одного, лучше на 3 |

Порог 2.0 даёт результат, идентичный 1.0, — то есть это не подогнанное число,
а нижняя граница. Суммарная ошибка при этом не выросла, а уменьшилась.
