# ТЗ: LP-слой, унификация UMF-математики, пошаговый режим и интервальный режим (LIPGLOSS)

## 0. Контекст

Проект — решатель рецептов глазурей по UMF-формуле: `common.py` (математика UMF),
`solver_classic.py` (NNLS по случайным подмножествам), `solver_iterative.py`
(итеративный приоритетный beam search), `api_server.py` (Flask API + отдача UI),
`UI/` (vanilla JS, без фреймворков). Предыдущий рефакторинг завершён
(см. `REFACTORING.md`), обе ветки решателя работают, тесты зелёные.

Это ТЗ — следующий шаг, по результатам исследования отраслевых практик
(LIPGLOSS, Insight-live, glass batch calculation). Пять ступеней:

| Ступень | Что | Зачем |
| --- | --- | --- |
| 1 | Единая классификация оксидов + фиксы математики + детерминизм | Сейчас три расходящиеся копии списков флюсов и искажённая ошибка классика |
| 2 | Feasibility-LP + диагностика + валидация базы | Пользователь должен видеть «цель недостижима, виноват оксид X», а не молчаливый плохой фит |
| 3 | Взвешенная невязка NNLS | Следовые оксиды и молярные массы искажают метрику |
| 4 | Пошаговый режим (trace + playback в UI) | Наблюдать вживую, как итеративный решатель сходится |
| 5 | Интервальный режим а-ля LIPGLOSS | Цели-диапазоны, достижимые min/max по каждому оксиду |
| 6 | Модель additional-компонентов (isAddition) | Стандарт Glazy: добавки поверх базы 100%; данные уже в recipes.json, код их игнорирует |
| 7 | Тесты обратной задачи (UMF → рецепт) | Точные внешние оракулы + метрики качества решения + корпусная регрессия на дампе Glazy |

Ступени выполнять по порядку: каждая опирается на предыдущую. Исключение:
ступень 6 независима и может делаться в любой момент; ступень 7 требует
ступеней 1, 2 (feasibility для сценария B корпуса) и 6. После каждой
ступени — все тесты зелёные, атомарные коммиты.

**Жёсткие правила:**

- Python 3.13, **новых зависимостей не добавлять**: всё LP — через
  `scipy.optimize.linprog(method='highs')` (scipy>=1.7 уже в requirements).
- Комментарии в коде — только английские.
- UI — vanilla JS без библиотек (никаких chart.js и т.п.).
- Таргетные правки; существующие сигнатуры функций не ломать — только
  расширять опциональными параметрами со значениями по умолчанию,
  сохраняющими текущее поведение.
- Контракт `POST /api/solve` меняется (см. 2.4) — UI обновляется в той же
  ступени, ничего не остаётся сломанным между коммитами.

## Ступень 1 — единая классификация оксидов и фиксы математики

### 1.1 Проблема

Три расходящихся источника правды о том, что считать флюсом:

- `common.oxides_classification()` (`common.py:19-25`): RO включает MnO, FeO,
  CoO, NiO, CuO («extended»-стиль), **PbO отсутствует вовсе**;
- `common.calc_ratios_umf()` (`common.py:356-357`): RO — только
  MgO/CaO/SrO/BaO/ZnO, т.е. отношение R2O:RO считается в другой конвенции,
  чем нормировка UMF;
- `common.calculate_umf_from_recipe()` (`common.py:389-390`): собственные
  inline-копии списков;
- `UI/js/app.js:72-76` (`oxide_groups`): четвёртая копия, опять другая
  (PbO/CdO есть, MnO2 в RO2, P2O5 в R2O3).

Плюс: `solver_classic.solve_recipe()` (`solver_classic.py:121-139`) после
`weights_to_umf` (уже unity-нормированного результата!) дополнительно
масштабирует фактический UMF так, чтобы он совпал с целью по **наименьшему**

репортуемую ошибку; итеративный решатель этим путём не пользуется, поэтому

## Ступень 2 — feasibility-LP, диагностика, валидация базы

### 2.1 Новый модуль `feasibility.py` (чистая математика, без Flask)

Работаем в **молярном пространстве** с нормировкой на unity флюсов — это
делает ограничения линейными (UMF дробно-линеен, но однородно-линеен:
`lo <= n_i/S_flux <= hi  <=>  n_i - hi*S_flux <= 0  и  lo*S_flux - n_i >= 0`).
Этот же аппарат переиспользует ступень 5.

```python
    ...

def check_feasibility(target_umf, materials, tol=DEFAULT_FEASIBILITY_TOL):

```

`check_feasibility` — Чебышёв-LP (минимакс) через
`scipy.optimize.linprog(method='highs')`:

- Переменные: `x` (n материалов, сырые граммы) и `t` (максимальное отклонение).
- Нормировка масштаба: `S_flux(x) = f·A·x = 1` (равенство).
- Для каждого оксида i целевой формулы: `|(A x)_i - b_i| <= t * s_i`,
  где `b_i` — целевое UMF-значение, `s_i = max(b_i, 0.1)` — масштаб оксида
  (чтобы SiO2~3 и MgO~0.05 давали сопоставимый относительный допуск).
- Оксиды, которые материалы могут принести, но которых нет в цели
  (загрязнение), включаются в задачу с `b_i = 0` — как `_expand_target`
  в итеративном решателе.
- `x >= 0`, минимизировать `t`.
- Константы модуля: `DEFAULT_FEASIBILITY_TOL = 0.05` (5% относительных),
  `OXIDE_SCALE_FLOOR = 0.1` — с комментариями, что это настраиваемые пороги.

Возврат:

```python
{
  "feasible": bool,              # t* <= tol
  "max_relative_deviation": t_star,
  "per_oxide": [                 # sorted by |delta| desc
    {"oxide": "SiO2", "target": 3.151, "closest": 3.149, "delta": -0.002,
     "relative": 0.0006, "reachable": True},
    ...
  ],
  "unreachable_oxides": ["Li2O", ...],   # relative > tol
  "closest_recipe": {"Material": pct, ...}  # x* renormalized to sum 100
}
```

`closest_recipe` — бесплатный побочный продукт LP: `x*`, нормированный к 100%,
материалы < 0.1% отброшены. Это «ближайшая достижимая точка» для пользователя.

Если LP вернул `status != 0` (не сошёлся) — `{"feasible": None, "error": ...}`,
решатели при этом работают как раньше (feasibility — диагностика, не блокер).

## Ступень 3 — взвешенная невязка NNLS

### 3.1 Суть

NNLS сейчас минимизирует невязку в весовых %, что неявно взвешивает оксиды
молярной массой, а следовые оксиды либо тонут, либо шумят. Добавляем механизм
пооксидных весов важности: строки матрицы и целевого вектора домножаются на
`w_i` перед `nnls` — стандартный приём взвешенного МНК.

### 3.2 Правки

- `solver_classic.solve_recipe(oxide_matrix, target_umf, material_names,
  available_materials=None, oxide_weights=None)`:
  - `oxide_weights: dict[str, float] | None` — None = текущее поведение;
  - перед `nnls`: `A_w = diag(w) @ A`, `b_w = w * b`, где `w_i =
    oxide_weights.get(oxide, 1.0)`;
  - ошибка решения по-прежнему считается НЕвзвешенно (`calculate_umf_error`) —
    веса влияют только на оптимизацию, не на репортинг.
- Прокинуть `oxide_weights` через `solve_glaze_recipe`,
  `find_multiple_solutions`, `solver_iterative._solve_material_set` /
  `find_best_recipe` (опциональный сквозной параметр).
- API: опциональное поле `"oxide_weights": {"SiO2": 1.0, "Fe2O3": 0.2, ...}`
  в `POST /api/solve` и `POST /api/solve_iterative`.
- UI в этой ступени не трогать (веса — API-фича; появятся в UI при
  необходимости отдельной задачей).

### 3.3 Тесты

В `tests/test_solver_classic.py`: синтетический кейс из 3-4 материалов, где
целевой SiO2 систематически недобирается; с `oxide_weights={"SiO2": 10}`
абсолютная невязка по SiO2 в решении должна уменьшиться по сравнению с
невзвешенным запуском (и тест на то, что `oxide_weights=None` даёт байт-в-байт
прежний результат при том же seed).

## Ступень 4 — пошаговый режим (trace + playback в UI)

### 4.1 Архитектурное решение

Итеративный решатель сходится за секунды (сотни маленьких NNLS), поэтому
**никакого SSE/WebSocket**: решатель записывает полный trace своей работы,
UI получает его одним ответом и проигрывает как анимацию с перемоткой
(автовоспроизведение включено по умолчанию — визуально это и есть «вживую»,
плюс возможность отмотать назад, которой у настоящего стрима не было бы).

### 4.2 Правки `solver_iterative.py`

Ввести класс-регистратор:

```python
class SolverTrace:
    """Records solver states and events for step-by-step playback"""
    def __init__(self): self.states = []; self.events = []
    def add_state(self, parent_id, iteration, added, state) -> int: ...
    def add_event(self, event: dict) -> None: ...
    def as_dict(self) -> dict: ...
```

- `find_best_recipe(..., trace: SolverTrace | None = None)` — при `None`
  поведение и производительность не меняются (все вызовы трейсера под
  `if trace is not None`).
- Точки записи:
  - `start`: инвентарь, `target_umf`, `full_target`, стартовый набор
    (имена + приоритеты), стартовое состояние (id=0);
  - `_expand_state`: событие `expand` — `parent_id`, `iteration`,
    `focus_oxide`, топ кандидатов из `ranked` (имя, score, priority,
    ограничиться `TOP_CANDIDATES * 3`), результаты проб `trials`
    (имя, error, id нового state или null, попал ли в beam, stalled);
  - `_shrink_to_limit`: событие `shrink` (какой материал выброшен);
  - завершения веток: `branch_converged` / `branch_stalled`;
  - `finish`: список решений с их `state_id`.
- Каждый state в трейсе: `id`, `parent`, `iteration`, `added` (материал),
  `recipe`, `result_umf`, `error`, `materials_count`, `focus_oxide`
  (худший оксид этого состояния), `residual_umf` ({оксид: target-actual},
  только |значение| > 0.001).
- Новая обёртка:

```python
def find_best_recipe_traced(*args, **kwargs) -> dict:
    # {"solutions": [...], "trace": {...}}; each solution carries "state_id"
```

Путь сходимости решения восстанавливается по `parent`-ссылкам от
`state_id` до корня — это и есть таймлайн для playback.

### 4.3 Правки `api_server.py`

**Новый `POST /api/solve_iterative`:**

Запрос: `{"umf": {...}, "inventory": [...], "max_materials": 10,
"max_solutions": 5, "error_threshold": 0.1, "trace": false,
"oxide_weights": null}` (все кроме umf — опциональны).

Ответ: `{"solutions": [...], "feasibility": {...}, "trace": {...} | null}`.
Весь ответ прогонять через `make_json_safe` (в трейсе возможны inf/NaN).

### 4.4 UI: пошаговый режим

Файлы: новый `UI/js/steps.js`, правки `index.html` (подключение скрипта,
разметка панели), `styles.css`, минимальные правки `app.js`.

- **Рефакторинг для переиспользования**: `create_umf_element(recipe_umf)`
  (`app.js:552`) читает глобальный `current_umf` — переделать в
  `create_umf_element(actual_umf, target_umf)`, все текущие вызовы передают
  `current_umf` явно. Пошаговый режим вызывает её же для каждого шага.
- **Вход в режим**: переключатель «Пошаговый режим» рядом с существующим
  `min_materials_toggle`. При включении панель решений заменяется панелью
  playback; запрос уходит на `/api/solve_iterative` с `trace: true` и тем же
  инвентарём, что собирает `index.html`.
- **Панель playback:**
  - селектор решения («Решение #1 (ошибка 0.8%, 5 материалов)», ...) — по
    `solutions[].state_id` строится путь состояний от корня;
  - контролы: ⏮ назад, ▶/⏸ автоплей (интервал ~800 мс), ⏭ вперёд,
    ползунок `input[type=range]` по шагам; автоплей стартует сам при
    получении трейса;
  - заголовок шага: «Итерация k/N — добавлен {материал} — ошибка E»
    (стрелкой показать изменение ошибки против прошлого шага);
  - рецепт шага: таблица материал/вес%, добавленный на этом шаге материал
    подсвечен, у остальных — дельта веса против предыдущего шага серым;
  - UMF шага: `create_umf_element(state.result_umf, trace.target_umf)` —
    существующая раскраска расхождений работает из коробки;
  - блок «почему»: «хуже всего сходится: {focus_oxide}; кандидаты:
    name (score), name (score), ...; выбран: {added}» — из событий `expand`
    для перехода к этому состоянию;
  - прогресс ошибки: простая полоска-график из div-ов (высота ~40px, столбик
    на шаг, текущий шаг подсвечен) — без библиотек.
- **Прочее**: при изменении UMF-инпутов в пошаговом режиме — обычный debounce
  и перезапрос трейса; при выключении режима — возврат к обычному списку
  решений без повторного запроса (`current_solutions` сохраняются).

## Ступень 5 — интервальный режим (LIPGLOSS)

### 5.1 Суть

Пользователь задаёт **диапазоны** по оксидам (и опционально по материалам),
а система через LP отвечает: какие значения каждого оксида/материала вообще
достижимы при всех остальных ограничениях одновременно. Пользователь сужает
диапазоны, пока интервалы не схлопнутся в рецепт. Это главный рабочий режим
LIPGLOSS (два LP — min и max — на каждую величину).

### 5.2 Новый модуль `lp_intervals.py`

Использует `build_molar_matrix` и `flux_row` из `feasibility.py`.

Математика (ключ к корректности — однородность ограничений):

- Все ограничения записываются однородно-линейно и потому верны при любой
  нормировке масштаба:
  - оксид i в UMF-диапазоне `[lo_i, hi_i]`:
    `(A x)_i - hi_i * S_flux(x) <= 0` и `lo_i * S_flux(x) - (A x)_i <= 0`;
  - материал j в диапазоне весовых процентов `[lo_j, hi_j]`:
    `100 * x_j - hi_j * sum(x) <= 0` и `lo_j * sum(x) - 100 * x_j <= 0`;
  - `x >= 0`.
- Для min/max **UMF оксида i**: нормировка-равенство `S_flux(x) = 1`,
  целевая функция `±(A x)_i` (значение UMF линейно при этой нормировке).
- Для min/max **процента материала j**: нормировка-равенство `sum(x) = 100`,
  целевая функция `±x_j`.
- LP `status == 3` (unbounded) — верхняя граница бесконечна (реальный случай:
  max SiO2 не ограничен, пока в инвентаре есть чистый кварц и нет верхней
  границы SiO2) → в ответе `null`, UI показывает «∞».
- LP `status == 2` (infeasible) — ограничения несовместимы →
  `{"feasible": false}` для всего запроса (достаточно обнаружить на первом же
  LP; остальные не считать).

```python
def compute_intervals(oxide_constraints, materials,
                      material_constraints=None) -> dict:
    # oxide_constraints: {"SiO2": [3.0, 3.5], "Al2O3": [0.3, 0.5], ...}
    #   (UMF units; an oxide missing from the dict is unconstrained)
    # material_constraints: {"Nepheline Syenite": [0, 40], ...} (weight %)
    return {
      "feasible": True,
      "oxide_intervals": {"SiO2": [3.05, 3.42], "MgO": [0.0, None], ...},
      "material_intervals": {"Каолин КЖФ-1": [0.0, 55.3], ...},
      "example_recipe": {"Material": pct, ...},   # x from any solved LP,
    }                                             # renormalized to 100%
```

Какие оксиды включать в `oxide_intervals`: все из `oxide_constraints` плюс
все оксиды, которые могут принести материалы инвентаря (незаданные — без
ограничений, но их достижимый интервал тоже интересен — это и есть
«ползучее загрязнение» в цифрах). Материалы с нулевой формулой — исключать
(как в ступени 2). Число LP: 2×(оксиды + материалы), при ~20 материалах и
~15 оксидах это ~70 крошечных LP — быстро, оптимизировать не нужно.

### 5.3 `api_server.py`: новый `POST /api/intervals`

Запрос:

```json
{
  "oxide_constraints": {"SiO2": [3.0, 3.5], "Al2O3": [0.35, 0.42]},
  "material_constraints": {"Улексит (Химпэк)": [0, 20]},
  "inventory": ["...", "..."]
}
```

Ответ — результат `compute_intervals` через `make_json_safe`.
`inventory` опционален (default — `resolve_inventory()`), ограничения
материалов опциональны.

### 5.4 UI: режим интервалов

Файлы: новый `UI/js/intervals.js`, правки `index.html`, `styles.css`.

- **Вход в режим**: третье положение переключателя режимов (обычный /
  пошаговый / интервалы) — реализовать как группу кнопок-табов над панелью
  решений.
- **Ввод**: в интервальном режиме у каждой строки оксида вместо одного
  input — два (`min`/`max`). При входе в режим текущее точечное значение V
  разворачивается в `[V*0.9, V*1.1]` (пустые/нулевые — без ограничения).
  Debounce 500 мс → `POST /api/intervals`.
- **Вывод**:
  - в каждой строке оксида рядом с инпутами — достижимый интервал
    «⇒ [3.05 … 3.42]» (или «⇒ [0 … ∞]»); интервал уже, чем 0.01 —
    подсветить зелёным (схлопнулся); заданный диапазон, не пересекающийся
    с достижимым, — красным;
  - в панели материалов (чекбоксы инвентаря в `index.html`) — у каждого
    отмеченного материала серым его достижимый диапазон «0–55%»;
  - блок «пример рецепта из допустимой области» — `example_recipe`
    (рендер тем же кодом, что рецепт решения);
  - `feasible: false` — красный блок «Ограничения несовместимы — расширьте
    диапазоны» вместо интервалов.
- Ограничения по материалам в UI v1 не редактируются (только отображение
  достижимых диапазонов); redактирование — задел на следующую итерацию.
  URL-hash в интервальном режиме не трогать (persist только точечного UMF,
  как сейчас).

## Ступень 6 — модель additional-компонентов (isAddition)

### 6.1 Данные и проблема

Стандарт Glazy: база рецепта нормирована к 100%, добавки (колоранты,
глушители, SiC) задаются как +X% сверх базы с флагом `isAddition`.
В `database/recipes.json` эти данные **уже лежат** в Glazy-формате:

```json
{"recipeId": ..., "name": ..., "type": ...,
 "includeAdditionsIntoCalculations": false,
 "recipe": [{"material": {"id": ..., "name": "..."}, "value": 30, "isAddition": false}, ...]}
```

Факты (проверены):

- 11 рецептов, база каждого суммируется ровно в 100, добавки поверх (до 13%);
- у 5 рецептов реальные добавки: «Матовая кальциевая» (TiO2 4), «Флотинг»
  (TiO2 5, Fe2O3 3), «Пенная» (TiO2 10, SiC 0.5), «Белая глянцевая»
  (циркон 7, SnO2 6), «Марганцевый металлик» (CuCO3 8, CoCO3 2, Fe2O3 3);
- `includeAdditionsIntoCalculations` у всех 11 — `false`;
- `common.load_recipes()` никем не вызывается — форму возврата можно менять;
- фикстуры `tests/fixtures/reference_recipes.json` — те же 11 рецептов, но
  добавки при создании **выброшены**, а UMF посчитан по базе.

Семантика флага: `include_additions == false` → добавки — чистые метаданные,
химия (UMF) считается по базе; `true` → добавки участвуют в химии
(конвенция дампа Glazy: нормировка по полному весу рецепта — для UMF это
чистый масштаб, отдельной математики не требуется, достаточно включить
добавки в суммирование оксидов).

**Жёсткий инвариант ступени:** все текущие флаги false ⇒ ни один эталонный
UMF и ни одно поведение существующих тестов не меняется.

### 6.2 `common.py`: модель рецепта

- `load_recipes()` — переписать, возвращать нормализованные записи:

```python
{
  "recipeId": ...,
  "name": ...,
  "type": ...,
  "include_additions": bool,   # from includeAdditionsIntoCalculations, default False
  "base": {material_name: value},        # entries with falsy isAddition
  "additional": {material_name: value},  # entries with truthy isAddition
}
```

  Имя — из `entry["material"]["name"]`; повтор материала внутри одной части —
  суммировать; отсутствующие флаги трактовать как false.

- `merge_recipe_components(base, additional)` — плоский `{имя: вес}`,
  пересекающиеся материалы суммируются; аргументы не мутируются.
- `recipe_for_chemistry(recipe)` — для нормализованной записи: merged, если
  `include_additions`, иначе копия `base`.
- `fixture_chemistry_recipe(reference)` — то же правило для записи фикстуры
  (`reference["recipe"]` + `reference.get("additional", {})` при

## Ступень 7 — тесты обратной задачи (UMF → рецепт)

### 7.1 Принцип: два уровня проверки

У обратной задачи нет единственного решения, поэтому веса рецепта ассертятся
**только** в определённых системах (материалов ≈ оксидов, матрица
невырождена — там решение единственно; кейсы 7.4). Для всех остальных
кейсов проверка двухуровневая:

1. **Химия** (необходимое условие): `forward(solver(UMF, materials)) ≈ UMF`,
   судья — наш прямой расчёт. Само по себе это тест достижимости, а не
   качества — солвер его уже проходит.
2. **Качество** (главный уровень): решение сравнивается с оригинальным
   рецептом по метрикам 7.3. Оригинал — не «правильный ответ»
   (решений много), а **доказательство существования**: эту химию можно
   получить вот таким числом материалов, такими долями и такой стоимостью.
   Требование к солверу — «не хуже оригинала по каждой оси», а не
   «совпасть с оригиналом».

Все нужные эталонные числа вшиты в эту ступень — внешних документов для
выполнения не требуется.

### 7.2 Предусловия

- **(а) Пресеты конвенций флюсов.** Наш набор unity — это конвенция
  ceramicscalc-2018; современный Glazy считает иначе (без FeO/CoO/NiO/CuO,
  с MnO и PbO), поэтому на рецептах с колорантами таргеты из Glazy
  разъезжаются с нашими на ~20% по всем оксидам сразу (проверено на рецепте
  с 4.77% CuO: лишние 0.06 моль CuO в знаменателе unity раздувают его в
  1.22 раза и пропорционально проседают весь UMF). В
  `database/oxide_classification.json` (из ступени 1) добавить:

```json
"unity_presets": {
  "legacy": ["Na2O", "K2O", "Li2O", "MgO", "CaO", "SrO", "BaO", "ZnO", "PbO", "MnO", "FeO", "CoO", "NiO", "CuO"],
  "glazy":  ["Na2O", "K2O", "Li2O", "PbO", "SrO", "BaO", "ZnO", "CaO", "MgO", "MnO"]
}
```

  `weights_to_umf()` / `calculate_umf_from_recipe()` получают опциональный
  параметр `convention="legacy"` (default — текущее поведение). Тесты,
  сравнивающие с опубликованными Glazy-числами, используют `"glazy"`;
  корпусные round-trip тесты конвенции не касаются (таргет считается нашим
  же forward-расчётом).

- **(б) Тестовый шов — инъекция материалов.** Оба решателя жёстко грузят
  `database/materials.json`. Добавить опциональный параметр
  `materials=None` в `find_multiple_solutions` / `solve_glaze_recipe` /
  `find_best_recipe`: None → как сейчас, иначе — использовать переданный
  список записей материалов (той же структуры, что materials.json).

### 7.3 Метрики качества решения: модуль `quality_metrics.py`

Новый чистый модуль (без Flask), используется корпусным тестом,
`compare_solvers.py` и юнит-тестами:

```python
def solution_quality(recipe, original, materials,
                     prices=None, priorities=None) -> dict:
    # recipe, original: flat {material: weight percent} dicts (each sums to ~100)
    # materials: material records (formulas, for LOI and clay detection)
    # prices: optional {material: price per kg}; priorities: optional {material: int}
```

Метрики (для каждой возвращать значение решения, значение оригинала и
дельту/отношение; пороги — именованные константы модуля):

| Метрика | Как считается | Порог «не хуже» (default) |
| --- | --- | --- |
| `count_delta` | len(recipe) − len(original) | ≤ +1 |
| `junk_count` | число компонентов легче 2.0 вес.% | junk решения ≤ junk оригинала |
| `min_portion` | наименьший вес компонента | ≥ 1.0%, если у оригинала минимум ≥ 1.0% |
| `cost_ratio` | Σ price·w/100 решения ÷ то же оригинала | ≤ 1.2 |
| `priority_ratio` | Σ priority·w/100 решения ÷ то же оригинала | ≤ 1.2 |
| `rounding_drift` | UMF-ошибка решения после округления долей до 0.5% и перенормировки к 100 | ≤ 0.02 |
| `assembly_score` | «собираемость»: cost_abs × len(recipe); без цен — len(recipe) | абсолютного порога нет — отслеживается против baseline (7.7) |
| `set_jaccard`, `share_delta` | пересечение множеств материалов; сумма abs(Δ долей) по общим | без порога, диагностика |
| `clay_content` | суммарная доля глинистых материалов (ключевые слова в имени: каолин/глина/бентонит/kaolin/clay/bentonite) | warning, если < min(5%, половина от оригинала) |
| `loi_delta` | abs(LOI замеса решения − оригинала); LOI замеса = 100 − Σ вкладов оксидов на 100 г сырья | без порога, диагностика |

Пояснения:

- `rounding_drift` — главная анти-вырожденность: решение на компенсирующей
  паре коллинеарных материалов разваливается от ±0.5% погрешности весов,
  честный рецепт устойчив. Считается через `calculate_recipe_composition` +
  `weights_to_umf` до и после округления, ошибка — `calculate_umf_error`.
- `cost_ratio` считается только когда цены покрывают **все** материалы обеих
  сторон; иначе `null` + поле `cost_coverage` (доля покрытых материалов).
  Цены регион-зависимы (США — фритты, РФ — сырые компоненты), поэтому
  `cost_ratio` осмыслен только когда решение и оригинал живут в одной
  снабженческой реальности; для чужого оригинала (Glazy) считать вместо
  ratio **абсолютную** стоимость нашего решения `cost_abs` (руб/кг замеса).
- `assembly_score` — «легко ли это собрать» для случаев без сопоставимого
  оригинала (сценарий B корпуса; доступность там гарантирована
  конструкцией — инвентарь только наш, собираемость вырождается в цену и
  число позиций): `cost_abs × len(recipe)`; пока цен нет —
  `len(recipe)` с пометкой `cost_abs = null`. Абсолютного порога у метрики
  **нет** — она отслеживается относительно baseline-прогона (7.7): смотрим,
  не стала ли хуже после изменений солвера, и видим, когда тюнинг начал
  оптимизировать лучше. Внутри одного прогона скор дополнительно ранжирует
  несколько решений одной цели.
- `priority_ratio` — прокси дешевизны/доступности для нашей базы
  (`priorities.json`, меньше = базовее; материал без записи = DEFAULT_PRIORITY);
  для дампа Glazy не применяется.
- `clay_content` — технологичность: глазурь без глинистых материалов не
  держится в суспензии, даже если химия идеальна.

Новый файл `database/prices.json` — формат `{"Каолин КЖФ-1": 90}` (цена
руб/кг). Заполняется **один раз** агентной разметкой: агент собирает цены
российских поставщиков по нашей базе материалов (в первую очередь
inInventory и материалы из `priorities.json`, остальные по мере надобности),
результат проверяется человеком и коммитится; дальше файл просто живёт в
репозитории и правится руками при смене цен. Материал без записи выпадает
из cost-метрики (см. `cost_coverage`). Сбор цен — разовая задача вне кода
солвера, в ступень входит только формат файла и его потребление метриками.

`compare_solvers.py` дополнить колонками `junk`, `drift` и `cost` (при
наличии цен) — сравнение движков становится сравнением качества, а не
только химии.

Юнит-тесты `tests/test_quality_metrics.py` (синтетика, без солвера):
junk/min_portion детектятся на рукотворном рецепте; `rounding_drift` на
паре почти-коллинеарных материалов с компенсирующими долями заметно больше,
чем на однозначном рецепте; `cost_ratio == null` при неполном покрытии цен.

Задел на будущее (в этой ступени НЕ делать): те же метрики затем включаются
в сам солвер — parsimony уже есть (сортировка по числу материалов),
least-cost режим — это целевая функция `min Σ price·x` на LP-аппарате
ступени 5.

### 7.6 Корпусный бенчмарк на дампе Glazy

`tests/test_inverse_corpus.py`, медленный, по умолчанию скипается:

- **Данные**: официальный дамп Glazy — репозиторий
  `github.com/derekphilipau/glazy-data`, файл `glazy_20260531.yaml.gz`
  (~8 МБ gz; имя пиновать; актуальное имя опубликовано в файле `LATEST`
  того же репозитория). Путь — env `GLAZY_DUMP_PATH`; если не задан —
  скачать raw-файл в кэш `~/.cache/glazy_solver/` (requests уже в
  зависимостях); нет файла и сети → `skipTest`. Дамп в git **не коммитить**
  (CC BY-NC-SA; в кэш — можно, политика Glazy этот сценарий прямо разрешает).
- **Формат дампа** — плоские YAML-записи с полями `ID`, `Parent ID`, `Name`,
  `Type` (`Material` / `Recipe` / `Analysis`), `Cone`,
  `Ingredients: [{ID, Name, Percentage, Additional}]`,
  `Percent Analysis: {оксид: %, LOI: %}`. Материалы хранятся как прокалённые
  оксиды + LOI (сумма ≈ 100); карбонаты уже разложены (Dolomite =
  `MgO 21.91 / CaO 30.48 / LOI 47.61`), у фритт LOI 0. В дампе ~7300
  материалов и ~35000 рецептов с ингредиентами.
- **Разбор**: материалы (`Type: Material`, `Percent Analysis` → наша
  `formula`, LOI отбросить) и рецепты (`Type: Recipe` с `Ingredients`,
  флаг `Additional` → модель ступени 6 с `include_additions=True` —
  конвенция дампа: добавки входят в химию). Рецепты с неразрешимыми
  материалами (приватные/удалённые, ~1% дампа) — отфильтровать.
Два сценария; практическая задача солвинга всегда одна — «сделать доступную
глазурь из текущих компонентов», но «доступные компоненты» регион-зависимы
(США — фритты, РФ — сырьё), поэтому сценарии тестируют разное.

**Сценарий A — воспроизведение своими же материалами** (заведомо достижимо,
тестирует качество решения):

- **Выборка**: детерминированная (фиксированный seed), ~300 рецептов,
  стратифицированная по числу материалов (2–4 / 5–7 / 8+).
- **Прогон**: inventory = материалы самого рецепта (через шов 7.2(б));
  target = наш `forward(merged)` — благодаря этому конвенция флюсов и
  glazy-нормировка не влияют; движок — iterative на всей выборке, classic —
  на подвыборке 50 (медленный).
- **Критерии — двухуровневые** (7.1), оригинальный рецепт дампа — baseline:
  1. химия: `calculate_umf_error ≤ 0.1` — **отменено, см. 10.18**: гейт
     переведён на относительное отклонение `max |a − b| / max(b, 0.1) ≤ 0.05`,
     ту же величину и тот же допуск, которыми меряет feasibility-LP;
  2. качество (`solution_quality` против оригинала): `count_delta ≤ +1`,
     junk решения ≤ junk оригинала, `min_portion` по правилу 7.3,
     `rounding_drift ≤ 0.02`; cost/priority в сценарии A не считаются
     (цен и приоритетов для Glazy-материалов нет).

  Доля кейсов, прошедших **оба** уровня — **≥ 90%** (стартовый порог,
  зафиксировать по первому прогону; после смены прибора в 10.18 порог
  пересчитан в **0.78**, решатель при этом не менялся); отдельно репортить
  долю прошедших только химию — разрыв между цифрами и есть мера «плохих, но химически
  верных» решений. Провалы логировать (id, name, уровень, метрика,
  значение).

**Сценарий B — чужая химия из нашего инвентаря** (реальный сценарий
использования: увидел фриттовый рецепт — повтори из своего сырья):

- **Выборка**: подвыборка ~100 UMF из сценария A (тот же seed).
- **Прогон**: inventory = наши inInventory-материалы (как в бою);
  target — тот же `forward(merged)` от дампового рецепта. Сначала
  `check_feasibility` (ступень 2): недостижимые из нашего инвентаря цели
  (нет Li-сырья и т.п.) попадают в корзину «честно недостижимо» — это
  **не** провал, это правильный ответ.
- **Критерии** для достижимых целей: жёсткий гейт — только химия
  (`calculate_umf_error ≤ 0.1`) и доля «решено ИЛИ честно недостижимо»
  ≥ 90% — **оба пункта отменены, см. 10.18**: химия меряется тем же
  относительным отклонением при 0.05, а доля «решено ИЛИ недостижимо»
  гейтом быть не может (недостижимая корзина сама по себе даёт 90 пунктов,
  порог непадаем) и заменена на долю решённых **среди достижимых**;
  качество (`assembly_score`, `min_portion`, `rounding_drift`,
  `priority_ratio`) не гейтится абсолютными порогами, а записывается в
  снапшот и отслеживается относительно baseline (7.7). Мисклассификации
  (feasibility сказал «достижимо», солвер не решил) логировать отдельно —
  это прямой баг-репорт на солвер или на LP.

Полный прогон обоих сценариев ≤ ~10 минут.

**Зависимость**: дамп — YAML, парсер нужен. Разрешённое исключение из
правила «без новых зависимостей»: `requirements-dev.txt` с `pyyaml`,
используется только тестами уровня корпуса; runtime `requirements.txt`
не трогать.

### 7.7 Baseline качества и регрессионный дифф

Смысл: качество решений не гейтится числами с потолка — вместо этого весь
корпус один раз прогоняется солвером, результат фиксируется как baseline,
и дальше любое изменение солвера измеряется диффом против него.

**Снапшот `bench/quality_baseline.json`** (коммитится в репозиторий):

- по каждому кейсу — **сырые компоненты**, не только свёртка: `glazy_id`,
  сценарий (A/B), статус (solved / infeasible / failed),
  `calculate_umf_error`, `len(recipe)`, `cost_abs`, `assembly_score`,
  `min_portion`, `junk_count`, `rounding_drift`. С 10.18 к ним добавлены
  `max_relative` (метрика, которой рисуется вердикт), `worst_oxide`,
  `dropped_oxides`, а сам снапшот несёт `run.chemistry_gate` — правило,
  которым посчитан `chemistry_ok`; `calculate_umf_error` остаётся в списке
  как диагностика, гейтом он больше не является. Свёртка пересчитывается
  на лету при диффе — смена формулы `assembly_score` не обнуляет baseline;
- метаданные прогона: seed и список id выборки, версия солвера (git-коммит),
  **хэши входных данных** — `materials.json`, `prices.json`,
  `oxide_classification.json`. Хэши обязательны: они отделяют «солвер
  изменился» от «данные изменились» (обновление цен сдвигает cost-метрики
  без единой правки солвера — это не регрессия).

**Дифф-скрипт `bench/diff_baseline.py`**:

- прогоняет ту же выборку текущим солвером, сравнивает покейсово с baseline;
- отчёт: improved / worsened / unchanged (по каждой метрике) и **полный
  профиль распределения** по каждой метрике, не только среднее: min / p10 /
  медиана / среднее / p90 / p99 / max, «было → стало» по каждому агрегату.
  Среднее прячет хвост: тюнинг может улучшить медиану и одновременно
  угробить несколько кейсов — ловится именно по p90/p99/max. Плюс доля
  solved и топ-10 ухудшившихся кейсов с деталями (id, метрика, было → стало);
- перцентили считать на **пересечении** множеств решённых кейсов обоих
  прогонов (иначе кейс, перешедший из solved в failed, молча сдвигает
  распределение); изменения самого множества solved — отдельной строкой
  («решалось → перестало» и наоборот, со списком id);
- при несовпадении хэшей данных — крупное предупреждение «изменились данные,
  не только солвер» вместо молчаливого сравнения;
- режим `--check`: exit 1, если ухудшились больше чем на 5% (именованная
  константа) медиана ИЛИ p90 `assembly_score`, либо упала доля solved, либо
  вырос max химической ошибки — хвост гейтится наравне с центром; для
  ручного запуска перед мержем изменений солвера, в `unittest discover`
  не входит;
- перезапись baseline — только явной командой `--rebaseline`, отдельным
  коммитом с объяснением, почему уровень сдвинут.

### 10.9 `rounding_drift` — не детектор вырожденности (метрика заменена)

Утверждение §7.3 «`rounding_drift` — главная анти-вырожденность» **опровергнуто
измерением** и отменяется. Проверено исчерпывающим перебором химически
эквивалентного семейства решений (все расщепления массы шпата по
почти-коллинеарному двойнику с шагом 0.1: 39 двухкомпонентных и 83 845
трёхкомпонентных вариантов): максимальный drift вырожденного решения —
**0.0153**, порога 0.02 оно не достигает в принципе.

Причина структурная, а не в подборе чисел: при неотрицательных весах и
неотрицательных анализах отображение «веса → химия» липшицево с умеренной
константой, поэтому ограниченное возмущение весов (±0.25% на компонент от сетки
0.5%) даёт ограниченное возмущение химии **независимо** от обусловленности
обратной задачи. Коллинеарность делает плохо определёнными **веса**, а химия
при этом остаётся устойчивой — перенос 0.25 г между материалами, отличающимися
на 0.5 абс.% по оксиду, меняет замес на 0.00125 г этого оксида.

Хуже того, гейт `≤ 0.02` бракует честные решения: тот же рецепт с неудачными
десятыми (41.3 / 28.7 / 19.4 / 10.6 вместо 41.1 / 28.9 / 19.5 / 10.5) даёт
**0.027** без всякой вырожденности. Метрика доминируется расстоянием долей до
сетки 0.5%, то есть точностью печати решателя, а не качеством решения.

**Что реально работает — обусловленность матрицы использованных материалов**
(измерено на тех же трёх рецептах):

| рецепт | cond(A_used) | rounding_drift |
| --- | --- | --- |
| честный | 15.1 | 0.0052 |
| честный, неудачные десятые | 15.1 | 0.0271 |
| вырожденный (компенсирующая пара шпатов) | **3668.8** | 0.0145 |

Различение в 240 раз, не зависит от десятых долей, и порог `1e3` из
`matrix_diagnostics` (§2.2) ложится ровно между. Правки:

1. В `quality_metrics.solution_quality` добавляется метрика `conditioning`:
   `cond` матрицы «оксиды × использованные материалы» (та же
   `create_oxide_matrix`, сингулярные числа), плюс `rank` и
   `redundancy = len(recipe) − rank`. Порог — именованная константа
   `MAX_CONDITION_NUMBER = 1e3`, общая по смыслу со ступенью 2.
   Это и есть анти-вырожденность.
2. `rounding_drift` **остаётся**, но переводится в диагностику: он честно
   измеряет «можно ли этот рецепт взвесить на грубых весах», абсолютного
   гейта у него больше нет, значение пишется в baseline и отслеживается
   как остальные.
3. §7.5 (стресс коллинеарности): ассерт `rounding_drift ≤ 0.02` заменяется на
   `conditioning.cond ≤ 1e3` — то есть решатель не должен возвращать решение,
   держащееся на компенсирующей паре. Это ровно то, что тест и должен ловить.
4. §7.6 сценарий A: `rounding_drift ≤ 0.02` убирается из критериев качества,
   вместо него `conditioning.ok`.

### 10.10 `assembly_score` без цен — `null`, а не число компонентов

Формулировка §7.3 «`assembly_score` = cost_abs × len(recipe); без цен —
`len(recipe)`» **отменяется**: она кладёт в одно отслеживаемое поле числа в
разных единицах. Живой пример, на котором это и вскрылось (recipe_04,
итеративный решатель, наш инвентарь):

| вариант | покрытие цен | cost_abs | assembly_score |
| --- | --- | --- | --- |
| решение с древесной золой | 0.86 | `null` | **5.0** (штуки) |
| решение без золы | 1.00 | 248.93 | **995.7** (руб×штуки) |
| оригинал рецепта | 1.00 | 107.80 | 431.2 (руб×штуки) |

Дифф baseline сравнил бы 5.0 с 431.2 и отчитался о «улучшении в 86 раз».
Правки:

1. `assembly_score.value` = `cost_abs × len(recipe)`, а при неизвестной
   стоимости — **`None`**. Никакого молчаливого падения в другие единицы.
2. Число компонентов и без того отслеживается отдельной метрикой (`count`),
   поэтому при `assembly_score = None` информация не теряется: в baseline
   сравниваются `count`, `junk`, `min_portion`, `conditioning`, а
   `assembly_score` просто не участвует в агрегатах по этому кейсу.
3. Дифф-скрипт (§7.7) считает перцентили `assembly_score` только по кейсам,
   где он определён в **обоих** прогонах — то же правило пересечения, что уже
   принято для множества solved.

Побочно тот же замер показал, зачем цена вообще нужна в метрике: оригинал
recipe_04 (мел 40 + кварц 20 + каолин 10 + нефелин 30) стоит 107.8 ₽/кг, а
решатель выдаёт ту же химию через волластонит 57.8% за 248.9 ₽/кг — в 2.3 раза
дороже, потому что волластонит (343 ₽/кг) заменяет мел (79) с кварцем (126).
Химически безупречно, экономически глупо, и без цены невидимо.

### 10.11 Стартовый набор и порог отсева следовых компонентов

`database/priorities.json` держал «Древесную золу» и «Костную золу» в
приоритете **1**, то есть впереди базовых материалов. `_priority_start_set`
набирает целыми группами, поэтому стартовый набор итеративного решателя был
7 материалов, начинаясь с двух зол. Ни один из 11 эталонных рецептов золу не
использует, и цену древесной золы вообще невозможно найти — её не продают.

Правки в данных: обе золы **убраны из `priorities.json` полностью** (получают
`DEFAULT_PRIORITY = 100`, как бентонит и бура — «не приоритетный материал
вообще», гарантированно вне стартового набора и в хвосте ранжирования
кандидатов); «Мел, CaCO3» поднят 10 → 2, «Полевой шпат FFF» 5 → 2. Стартовый
набор стал: волластонит / каолин / кварц / мел / нефелин-сиенит / полевой
шпат / улексит.

Один только этот сдвиг ухудшил дело, и это оказалось диагностично: расширенный
стартовый набор дал решателю больше возможностей навесить **следовый**
компонент ради четвёртого знака оксида (полевой шпат 0.37% в рецепте 01).
Ровно то, что ловит метрика `junk`.

**Первая попытка лечения была неверной.** `MIN_MATERIAL_WEIGHT` подняли
0.1 → 1.0 (пол по весу). Это тупое отсечение: оно одинаково выбрасывает и шум
подгонки, и нужный подпроцентный краситель. Замер на цели, построенной из
рецепта шпат 39.5 / кварц 30 / мел 20 / каолин 10 / **карбонат кобальта 0.5**:

```text
порог 0.1:  ошибка 0.0030, кобальт на месте
порог 1.0:  ошибка 0.0575, кобальта нет
```

0.0575 **ниже** порога приемлемости 0.1, то есть синяя глазурь молча
становится прозрачной, и в ответе нет ни одного признака потери компонента.

Отдельно: числа, которыми это изменение обосновывалось в первой редакции этого
раздела, были получены при `max_solutions=1` — не тот режим, в котором работают
тесты и API. Правильный замер (`max_solutions=5`, exhaustive):

| конфигурация | ошибка | точный набор | мусор | средняя цена |
| --- | --- | --- | --- | --- |
| старые приоритеты, порог 0.1 (база) | 115.5447 | 10/11 | 0 | 193.2 |
| новые приоритеты, порог 0.1 | 115.5479 | 4/11 | 5 | 186.5 |
| новые приоритеты, порог 1.0 | 115.5447 | 9/11 | 0 | 189.2 |
| старые приоритеты, порог 1.0 | 115.5447 | 10/11 | 0 | 193.2 |

Порог 1.0 на старых приоритетах — полный no-op. Он не улучшает базу, он лишь
компенсирует ущерб от расширения стартового набора, и платит за это
красителями.

**Правильное лечение — обратный проход (backward elimination).** Компонент
выбрасывается не потому что он лёгкий, а потому что его удаление **ничего не
стоит по химии**: пробуем убрать каждый материал, принимаем удаление, если
ошибка не выросла больше чем на `PRUNE_ERROR_TOLERANCE`. Шум подгонки уходит
бесплатно, кобальт стоит 0.0545 и остаётся. `MIN_MATERIAL_WEIGHT`
возвращается к 0.1 в роли чисто численного пола.

| вариант | вызовов NNLS | ошибка | точный набор | мусор | компонентов | кобальт |
| --- | --- | --- | --- | --- | --- | --- |
| порог 1.0 | 774 | 115.5447 | 9/11 | 0 | 53 | **потерян** |
| порог 0.1 | 789 | 115.5479 | 4/11 | 5 | 58 | сохранён |
| порог 0.1 + обратный проход | 2586 | **115.5447** | **9/11** | **0** | **53** | **сохранён** |

Top-1 рецепт побайтово совпадает с поведением при пороге 1.0 на всех 11
эталонах — то есть обратный проход не «другое решение», а то же самое, но без
потери нужных малых компонентов. Плата — 3.34× вызовов NNLS; худший случай
(вся база из 216 материалов) — 1012 вызовов, 0.15 с.

Тем же механизмом чинится вырожденность из §7.5: вместо расщепления массы по
двум почти-коллинеарным двойникам (cond 1849.6) остаётся один шпат — 4
материала, ошибка 0.0033, **cond 14.8**. Один проход закрывает три разные
болезни: следовой мусор, потерю красителей и компенсирующие пары. Классический
движок обратного прохода не имеет и вырожденное решение по-прежнему выдаёт —
его `expectedFailure` в §7.5 остаётся.

**Известный остаток (не чинится обратным проходом).** У потери красителя есть
вторая, независимая причина: при `max_solutions=1` ветка объявляется сошедшейся
на ошибке 0.0575 (ниже дефолтного `error_threshold=0.1`) раньше, чем кобальт
вообще будет опробован. Это правило приёмки, а не отбор компонентов;
`error_threshold=0.01` его снимает. Задел на отдельную задачу.

### 10.12 Эталонные тесты переведены на двухуровневый критерий

После 10.11 `tests/test_individual_recipes.py` уронил recipe_03 — и это тест
был неправ, а не решатель. Оригинал использует волластонит 15 (343 ₽/кг),

### 10.13 `MnO2` — флюс (баг классификации, найден сверкой с SegerLab)

### 10.14 Конвенция `Fe2O3`: дефолт не меняем, добавлен пресет `segerlab`

Все наши UMF систематически больше SegerLab ровно в 1.0022 раза, и причина одна:
они держат `Fe2O3` в знаменателе unity, мы — в R2O3 (классический UMF). Проверено
на «Прозрачной △6»: их сумма флюсов 1.002 против нашей 1.000, и `3.151 / 1.002 =
3.1447` — их опубликованные 3.144, тем же множителем воспроизводятся все прочие
оксиды.

**Дефолт остаётся классическим.** Смена basis сдвинула бы каждое число проекта на
0.2% и потребовала перегенерации всех фикстур ради совместимости с одним внешним
инструментом. Вместо этого в `unity_presets` добавлен третий пресет `segerlab`
(19 оксидов, сверен с их `oxide_roles.json` — совпал до оксида), и появился
регрессионный тест: наш forward против всех 11 опубликованных формул под этим
пресетом, допуск 0.005. Результат — **11/11, худшее отклонение 0.001**.

Тест ловит ровно два класса ошибок: расползание конвенции unity и опечатку в
молярной массе. Он **не** проверяет достоверность анализов материалов — обе
стороны происходят из одного дампа, и единственные настоящие внешние оракулы в
проекте это Leach 4321 и задача Arbuckle из §7.4, где материалы заданы числами
прямо в фикстуре.

### 10.16 Пересмотр объёма: ступени 4 и 5 (решение по `UI_DECISIONS.md`)

Параллельная ветка `feature/sensitivity` принесла `UI_DECISIONS.md` — решения по
интерфейсу и постановке задач солвера. Два из них меняют объём этого ТЗ.

**Ступень 4 (пошаговый режим) — снята.** Кейса нет: керамисту не нужно смотреть,
как сходится NNLS. Доверие обеспечивается объяснением на финальном решении —
колонка «ради какого оксида взят материал» в таблице рецепта.

**Ступень 5 (интервальный режим) — сжата до одной функции.** Петля «сужай
диапазоны, пока не схлопнется» — инструмент исследования без точной цели, а
приходят к нам с точной. Но **достижимые доли материалов** из неё сохраняются и
переезжают в обычный режим: «улексита можно 9–19%» — второй по частоте вопрос.

Это тот же LP-аппарат, что и feasibility ступени 2: те же однородно-линейные
ограничения, только целевая функция `±x_j` по столбцу материала при нормировке
`sum(x) = 100` вместо `±(A x)_i` по оксиду при `S_flux = 1`. Поэтому:

- отдельный модуль `lp_intervals.py`, эндпоинт `POST /api/intervals` и
  `UI/js/intervals.js` из §5.2–5.4 **не делаются**;
- функция min/max по материалу добавляется в `feasibility.py` ступени 2 и
  отдаётся в существующем ответе `POST /api/solve` рядом с `feasibility`;
- тесты §5.5 сокращаются до случаев по материалам (включая unbounded → `null`).

Ступень 2 из-за этого перестаёт быть чисто диагностической: она становится
несущей для этой функции.

Также сняты (детали и причины — в `UI_DECISIONS.md` §6): панель настроек
решателя, показ `cond`/`rank` в интерфейсе, закрепление решений, phantom, КТР,
зоны на графике Сталла. **`conditioning` при этом остаётся тестовым гейтом**
(§10.9): в интерфейсе его и не было, а как гейт он поймал реальный дефект —
расщепление массы по паре почти-коллинеарных шпатов.

### 10.17 Точки стыковки с `feature/sensitivity`

1. **`weights_to_umf`** расширяют обе линии: здесь `convention=None` (в теле,
   выбор набора флюсов), там `round_digits=3` (на выходе, округление).
   Совмещается как
   `weights_to_umf(weight_composition, convention=None, round_digits=3)` —
   участки не пересекаются, слияние трёхстрочное. **Сигнатуру этой функции на
   нашей линии больше не трогать**, чтобы конфликт остался тривиальным.
   Аргумент про округление бьёт и по нам: расхождения `native` против `umfErr`
   в classic (≤ 3.8e-5), списанные при ревью на косметику, — это ровно
   квантование шагом 0.001 внутри `weights_to_umf`.
2. **Ветка `if sum_fluxes == 0`** (нормировка по минимальному оксиду) жива на
   обеих линиях. Это не «запасной вариант», а молчаливая подмена базиса:
   формула без плавней — не UMF, и отдавать её под тем же именем нельзя.
   Правильно бросать исключение (прецедент типа — `ClassificationError`,
   который решатели намеренно не ловят), а не обходить в одном потребителе.
   Чинить **после слияния**, на одной линии.
3. **`inventory: null`** в `POST /api/sensitivity` означает «вся база», а не
   «дефолтный инвентарь», в отличие от `/api/solve`. Осознанное отступление;
   при объединении документации назвать различие явно.

### 10.18 Одна шкала на всю систему: химический гейт бенчмарка — это вердикт LP

Проект отвечал на один и тот же вопрос — «воспроизводит ли рецепт целевую
химию?» — **двумя несовместимыми измерениями**, и на 29 из 100 кейсов
сценария B они противоречили друг другу:

* `feasibility.check_feasibility()` ограничивает худшее **ОТНОСИТЕЛЬНОЕ**
  отклонение оксида, `|achieved − target| / max(target, 0.1)`, и принимает при
  `DEFAULT_FEASIBILITY_TOL = 0.05`;
* `bench/corpus.py` гейтил по `solver_classic.calculate_umf_error()` — это
  **L2-норма АБСОЛЮТНЫХ** отклонений по оксидам цели, порог `0.1`.

Абсолютная норма слепа ровно к тем оксидам, которые дороже всего стоят на
единицу: полностью потерянный кобальт 0.02 стоит 0.02 в норме с порогом 0.1,
то есть рецепт, выбросивший краситель, гейт проходит. Это та же слепота,
которая уже дала два починенных бага этой ветки (метрика `junk` и порог
`MIN_MATERIAL_WEIGHT`, §10.11). Это не второе мнение, это неверный прибор.

**Замер (решатель не тронут, те же 300/100 кейсов, пересчёт по разным
метрикам):**

```text
=== A: 300 кейсов, 300 с рецептом
  l2 <= 0.1 (было)         284
  rel <= 0.05  251     rel <= 0.1  263     rel <= 0.2  274
  худший оксид при rel > 0.05 (все 49 провалов, 16 оксидов, сумма сходится):
      MgO 11, Na2O 6, Fe2O3 5, B2O3 4, SnO2 4, P2O5 3, Li2O 3, CuO 2, Cr2O3 2,
      SrO 2, K2O 2, TiO2 1, MnO2 1, Al2O3 1, CoO 1, ZrO2 1

=== B: 100 кейсов, 100 с рецептом
  l2 <= 0.1 (было)          39
  rel <= 0.05    6     rel <= 0.1    9     rel <= 0.2   16
  гейт rel<=0.05:       unreachable_solved  0, reachable_unsolved 4
  гейт rel<=0.1:        unreachable_solved  1, reachable_unsolved 2
  гейт rel<=0.2:        unreachable_solved  6, reachable_unsolved 0
  гейт l2<=0.1 (было):  unreachable_solved 29, reachable_unsolved 0
```

Три следствия, и они решают дизайн.

1. **На допуске 0.05 все 29 расхождений схлопываются в ноль.** Расхождений и
   не было — были два разных вопроса. Остаётся 4 `reachable_unsolved`: LP
   доказал, что точка внутри 0.05 по каждому оксиду существует, а поиск её не
   нашёл (id 1374, 4682, 227981, 459155). Это настоящий баг-репорт против
   решателя (известная проблема локального оптимума), и впервые это число
   означает именно и только это.
2. **`unreachable_solved = 0` — проверка LP на состоятельность, а не число
   качества.** Оптимум LP — нижняя граница худшего относительного отклонения,
   поэтому решатель, систематически обходящий её, означал бы, что LP неверен.
   Ни разу не случилось. **Но «любое ненулевое значение — баг LP» было бы
   сильнее измеренного:** вердикт LP несёт слак `BOUND_EPS`, а достигнутый UMF
   квантован — `weights_to_umf` округляет до 3 знаков, шаг 0.001, что у пола
   шкалы даёт 0.01, то есть **20 % допуска 0.05**. Округлённый рецепт способен
   показать 0.0499 там, где непрерывный оптимум равен 0.0501, без всякой
   несостоятельности. Что это не теория, видно в данных: два из шести проходов
   сценария B стоят ровно на `max_relative = 0.049999999999999996`. Честная
   формулировка: ненулевое значение — либо баг LP, либо кейс на границе внутри
   кванта округления, и разбирать надо глазами.
3. **Множество «только оксиды цели» против «цель ∪ всё, что несёт ответ»
   вердикт не меняет.** На сценарии A совпадение 251/251, на B — 6/6, ни один
   кейс не переворачивается (в первой редакции этого раздела ожидалось
   расхождение на 3 кейсах B — измерение это не подтвердило). Загрязнение эту
   картину не двигает; объединение всё равно берётся, потому что оно и есть
   правильное определение, и стоит оно ноль.

**Решение: одна шкала на всю систему** — относительное отклонение UMF против
`s_i = max(target_i, OXIDE_SCALE_FLOOR)`, `OXIDE_SCALE_FLOOR = 0.1`. Химический
гейт бенчмарка становится той же метрикой И тем же числом, что вердикт
feasibility, — **импортируется из него, а не копируется**.

1. `common.OXIDE_SCALE_FLOOR` — единственное определение. Константа была
   объявлена трижды (`feasibility.py:74`, `sensitivity.py:69` и неявно в каждом
   рукописном `max(value, 0.1)`), причём обе явные копии несли комментарий
   «намеренно то же значение, что и в соседнем модуле». Оба локальных
   присваивания удалены, модули импортируют одно.
2. `common.umf_deviation(target, actual, *, floor)` — канонический замер:
   `max_relative` (заголовочное число), `worst_oxide`, `l2_absolute`
   (диагностика), `per_oxide`, `dropped`. Множество оксидов —
   `set(target) | set(actual)` минус `NON_OXIDE_KEYS`; оксид, которого нет с
   одной стороны, сравнивается с 0.0 и получает пол — ровно так его считает
   feasibility. **Исключения намеренные, их два, и оба про `l2_absolute`,**
   который обязан побитово воспроизводить `solver_classic.calculate_umf_error`
   — иначе сохранённые серии `bench/history.jsonl` и `quality_baseline.json`
   перестают быть сравнимыми сами с собой. Он суммирует квадраты (а) только по
   оксидам ЦЕЛИ и (б) **в порядке ключей цели, а не по алфавиту**. Второе не
   педантизм: сложение float неассоциативно, и сортированный порядок сдвигает
   `umf_error` в младшем бите на **27 из 300** кейсов корпуса и переписывает
   **55 из 450** строк `quality_baseline.json`. Первая редакция этой правки
   именно это и сделала; страж в тестах был вакуумным, потому что во всех 11
   фикстур `reference_recipes.json` ключи UMF уже отсортированы и переставлять
   было нечего. Тест переписан на кейс 423584, где два порядка дают разные
   double. Ещё два отличия от `calculate_umf_error` задокументированы в
   докстринге и через `weights_to_umf` недостижимы: `Loi` в цели тот считает,
   а `umf_deviation` игнорирует, и нефинитное значение тот превращает в NaN, а
   здесь оксид уходит в `dropped` под своим именем.
   **`dropped` — не диагностика, а часть вердикта:** пропущенный оксид значит,
   что формулу сравнили не целиком, поэтому `chemistry_ok` при непустом
   `dropped` — `False`, причём эта проверка стоит **выше записанного вердикта**,
   а не под ним: неполное сравнение не должно проносить проход мимо неё даже
   из старой записи. Путь достижим не гипотетически: один NaN в анализе
   материала доходит до **всех** оксидов результата, потому что `weights_to_umf`
   делит на уже отравленную сумму флюсов, и `feasibility.py` держит для такого
   входа отдельную ветку `nonfinite_analysis`.
   **И `max_relative`/`l2_absolute` при этом равны `None`, а не 0.0.** Обе
   метрики — «меньше лучше», их распределения пишутся в baseline, а их максимум
   гейтится; ноль был бы **лучшим значением в выборке**, то есть кейс, который
   не удалось прочитать, обгонял бы прочитанный и верный, а гейт по максимуму
   прочитал бы это как улучшение. Отставная метрика в этой ситуации давала NaN
   — заметный и ломающий перцентили. То же правило действует при частичной
   потере: максимум по части оксидов — нижняя оценка, и в одном распределении
   с честными ей не место. Пустой вход и полностью выброшенный различаются по
   `dropped`. Само поле `dropped_oxides` пишется в снапшот, печатается в диффе
   и гейтится на рост — иначе оно не читалось бы никем.
3. `common.calc_error()` удалён — четвёртое, самое старое определение «ошибки
   между двумя UMF», ничем в дереве не вызывалось.
4. `bench/corpus.CHEMISTRY_TOL = FEASIBILITY_TOL` — **одно присваивание, а не
   второе обращение к той же константе feasibility**: иначе достаточно
   перенастроить `FEASIBILITY_TOL` для эксперимента, и «одна шкала» тихо
   становится двумя, то есть ровно тем дефектом, который здесь чинится.
   `MAX_UMF_ERROR = 0.1` остаётся **отставным** гейтом: только для того, чтобы
   снапшоты, записанные до этой правки, читались по правилу, по которому были
   написаны.
5. **Отметка гейта в записи.** `chemistry_ok` — единственное сохранённое поле,
   которое **сменило смысл**, а `bench_corpus.chemistry_ok()` первой ступенью
   безоговорочно доверяет записанному значению (и это правильно), поэтому без
   отметки старый и новый снапшот сравниваются как одно измерение. Отметка
   `{'metric': 'max_relative', 'tol': …}` пишется из одного определения
   `bench_corpus.CHEMISTRY_GATE` в оба места: в строку журнала
   (`thresholds.chemistry_gate`) и в снапшот (`run.chemistry_gate`). Печать
   журнала помечает переход `!! CHEMISTRY GATE CHANGED`, дифф — строкой
   провенанса, и **гейт `accounted_share` при смене правила не срабатывает, а
   печатается в блоке `NOT GATED`**: пересчёт прибора не регрессия, а `--check`
   с ненулевым кодом на ней научил бы читателя игнорировать единственный гейт,
   который ловит реальную потерю покрытия. Версию формата снапшота
   (`BASELINE_FORMAT_VERSION`) при этом **не поднимаем**, хотя политика в
   комментарии предусматривала бамп при смене смысла поля: бамп сделал бы
   старый снапшот нечитаемым целиком и уничтожил бы сравнение сырых компонентов
   (`count`, `cost_abs`, `min_portion`, `cond`), которые смысла не меняли.
   Отметка несёт ровно ту информацию, которую бамп уничтожил бы, и потому
   строго информативнее. Прежняя политика такого случая **не предусматривала**
   — она говорила «бампать при смене смысла поля», — поэтому в комментарии она
   не «уточнена», а дополнена новым пунктом, и это отмечено там явно.
   Лестница `chemistry_ok(row)` — записанное поле → `dropped_oxides` →
   `max_relative` против `CHEMISTRY_TOL` → `umf_error` против `MAX_UMF_ERROR` —
   гейты **не примиряет** и не должна: ступень 1 отвечает за все снапшоты,
   которые это дерево когда-либо коммитило, ступень 2 недостижима по построению
   (поле и вердикт введены одним изменением), а до ступени 3 доходят только
   baseline'ы `a463647` и `096a12d`, у которых поля `chemistry_ok` ещё не было.

**Что изменилось в числах, и что не изменилось.** Решатель не тронут ни строкой,
и дифф это доказывает: 0 кейсов сдвинулось по `umf_error`, `count`, `cost_abs`,
`assembly_score`, `min_portion`, `junk_count`, `rounding_drift`, `cond` — на
всех трёх сериях. Сдвинулся только вердикт:

| A / classic (50) | 100.00% | 100.00% | 98.00% | 98.00% |
| B / iterative (100) | 39 | **6** | — | — |

Классический движок гейт не заметил вовсе: на своих 50 кейсах он ни разу не
выходит за относительное отклонение **0.02**. Все 49 провалов сценария A — у

(«решено ИЛИ честно недостижимо») 100.00% → **96.00%**.

Пороги тестов пересчитаны по измеренной реальности, а не ослаблены на глаз.
Разброс по пяти сидам (20260531, 1, 42, 999, 20260101) перемерен под новым
гейтом:

**Сценарий A: `MIN_BOTH_LEVELS_SHARE` 0.90 → 0.78.** Закреплённый сид
по-прежнему самый неудачный из пяти, 0.78 перекрывает весь разброс и даёт
4.67 пункта запаса против прежних 3.33.

**Сценарий B: гейтом становится доля решённых СРЕДИ ДОСТИЖИМЫХ,
`MIN_SOLVED_AMONG_REACHABLE = 0.40`, а `accounted_share` остаётся печатаемым
числом без порога.** Причина — чувствительность: учтённую долю определяет
недостижимая корзина (90 из 100 целей), поэтому потеря одного достижимого
кейса двигает её на **1 пункт**, а долю решённых среди достижимых — на **10**.

Чем на самом деле был старый гейт. Его пол — не константа 0.90, а
`|unreachable| / 100`: **undecided**-кейс, на котором LP не смог ответить,
уходит из недостижимой корзины и уносит пункт учтённой доли. При 7 undecided
получается 83 + 6 = 89% и старые 0.90 срабатывали. То есть это был детектор
массового отказа LP — и, потеряв его, мы вернули его **явно и точнее**:
ассертом на число undecided рядом с ассертом на `crashed`. Он срабатывает на
ПЕРВОМ неотвеченном кейсе, а не на седьмом; измерено 0 из 100 на всех пяти
сидах.

Порог берётся от **закреплённого сида**, а кросс-сидовый разброс к делу не
относится: сид прибит намертво (`_shared_corpus` строит выборку по
`DEFAULT_SEED`, переопределения нет), так что единственный прогон, который этот
ассерт когда-либо увидит, — тот, где достижимых 10 и решено 6. При n = 10
метрика квантована шагом в 10 пунктов, поэтому порог ставится на два кейса
ниже измеренного: **0.40** требует 4 из 10 и ловит потерю третьего кейса.
Прежние 0.15 просыпались только после потери пяти успехов из шести —
то есть были гейтом катастрофы.

**Это число обязано расти вместе с поиском.** 6 из 10 — не то, чем стоит быть
довольным: LP ДОКАЗАЛ, что рецепт существует для всех десяти. Ступень 3
(относительная невязка NNLS) должна поднять это к 10/10, и в тот же коммит
порог надо поднимать, иначе 0.40 сам станет гейтом катастрофы.

**Целевая функция поиска осталась на СТАРОЙ абсолютной шкале** — эта правка
меняет прибор, а не решатель, и вся её ценность в том, что распределения
решателя вышли из диффа побитово теми же.

И дело не только в целевой функции. У `find_best_recipe` дефолт
`error_threshold = 0.1`, а `bench/corpus._solve` зовёт его **без
переопределения** — то есть поиск объявляет ветку сошедшейся и перестаёт
улучшать ответ ровно на отставном гейте `MAX_UMF_ERROR`. Это четвёртая копия
«достаточно близко», причём на другой шкале, чем вердикт, и она встроена в
сам критерий останова, а не только в скоринг: решателю буквально сказано
останавливаться там, где новый гейт ещё не пройден. Поэтому **251/300 не
является потолком решателя** — это потолок решателя, которому велели
остановиться раньше. Перевод целевой функции и порога останова на ту же шкалу
— следующий шаг.

### 10.19 Ступень 3: поиск переведён на ту же относительную шкалу, что вердикт

§10.18 перевёл на относительную шкалу **прибор** и явно оставил решатель на
старой абсолютной: «251/300 — это потолок решателя, которому велели
остановиться раньше». Здесь на ту же шкалу переводится **сам поиск**, в трёх
местах, где он мерил в абсолютных единицах:

* NNLS минимизировал невязку в **весовых процентах оксидов** без весов
  (`solver_classic.solve_recipe`, `weights_array` из `umf_to_weights`);
* `solver_iterative._objective_error` был простой L2 абсолютных отклонений UMF
  плюс задемпфированное загрязнение;
* `error_threshold`, `PRUNE_ERROR_TOLERANCE` и `SOLUTION_ERROR_TIE_ABS` —
  абсолютные числа, откалиброванные под эту целевую функцию.

#### Вывод весов строк

Невязка строки *i* — в весовых процентах. Отклонение `d` весовых процентов
оксида *i* — это `d / (M_i · S)` в единицах UMF, где `M_i` — молярная масса, а
`S` — молярная сумма флюсов, по которой нормируется UMF
(`weights_to_umf`: `umf_i = (w_i / M_i) / S`). `S` одна на все строки одного
рецепта, то есть общий множитель всей невязки, и из `argmin` выпадает. Деление
на `s_i = max(target_i, OXIDE_SCALE_FLOOR)` переводит отклонение UMF в то самое
относительное, по которому выносится вердикт. Итого

```text
w_i = penalty_i / (M_i · s_i),   penalty_i = 1.0 для запрошенного оксида
                                            unlisted_weight для незапрошенного
```

`penalize_unlisted` при этом сохраняет **ровно** прежний смысл: он множитель
поверх невязки, которая уже приведена к относительной шкале, а не замена ей.
Оксид без молярной массы остаётся с одним штрафом (прежнее поведение) и
логируется; ветка **оборонительная, а не политика** — ни один из 216 материалов
поставляемой базы такого оксида не несёт, а `usable_target` выбрасывает такой
оксид из цели ещё раньше.

**Ловушка §10.5 закрыта в одном месте.** `_solve_material_set` домножал матрицу
**снаружи** `solve_recipe`, и это было точным взвешенным МНК только потому, что
у всех масштабируемых строк `b_i = 0` (незапрошенные оксиды). Как только вес
получает запрошенный оксид, правая часть обязана ехать вместе со строкой.
Теперь `solve_recipe(row_weights=...)` масштабирует **и** `A`, **и** `b`, длина
вектора проверяется ассертом (`ValueError` **вне** `try`, иначе широкий
`except` превратил бы ошибку размерности в «у этого набора нет решения»), а
внешнее домножение убрано. Оценка состава в ветке `if not available_materials`
читает **немасштабированную** матрицу: масштабируется локальная копия. Сегодня
эта ветка недостижима из `solver_iterative` — он всегда передаёт материалы, —
именно поэтому порча там прошла бы незамеченной.

#### Мёртвая зона

```text
residual_i = max(0, |target_i − actual_i| / s_i − OBJECTIVE_DEADBAND)
objective  = sqrt(Σ residual_i²)
```

то же для незапрошенных оксидов (отклонение от нуля, штраф `unlisted_weight`).
`OBJECTIVE_DEADBAND = 0.02` — **настраиваемая политика, не физика**.

Зачем она. Дожимать оксид, который уже внутри своего допуска, до нуля стоит
материала: **27 из 300** кейсов сценария A платили компонентом ровно за это —
отклонение переезжало с 0.04 на 0.02, улучшение, которого не видит ни один
порог и ни один гончар. Это обобщение «пассажира» из `UI_DECISIONS.md` §2.2 с
незапрошенных оксидов на все.

**Каждая таблица свипа ниже называет ВЕСЬ закреплённый набор**, иначе она не
воспроизводится: первая редакция первой таблицы была снята при
`SOLUTION_ERROR_TIE_ABS = 0.01`, а в шапке стоял только бюджет отсечения, и
читатель, закрепивший поставляемые 0.02, получал медиану `min_portion` 2.70 там,
где в таблице 2.35. Умолчание — «всё остальное на поставляемом значении»,
отклонения выписаны явно. Все таблицы пересняты на финальном коде и спарены
по кейсам с ответами коммита `1f521c9`.

Свип ширины, 300 кейсов сценария A, `max_solutions=5`, exhaustive, при
`PRUNE_OBJECTIVE_TOLERANCE = PRUNE_ERROR_TOLERANCE = 0.005` и
`SOLUTION_ERROR_TIE_ABS = 0.01` — это до-10.19 бюджет, и так измеряется одна
мёртвая зона, отдельно от расширения прохода отсечения:

| --- | --- | --- | --- | --- |

и он же со всем остальным на поставляемых значениях:

| зона | rel ≤ 0.05 | ср. count | медиана min_portion | хуже/лучше | B решено |
| --- | --- | --- | --- | --- | --- |
| нет | 296 | 5.797 | 2.960 | 52 / 9 | 10/10 |

Зона **обязана быть уже допуска приёмки** (0.05, общего у LP и гейта), потому
что проход отсечения тратит свой бюджет **поверх** неё: внутри зоны любое
удаление уже читается как бесплатное. При старом бюджете обрыв на 0.05, при
новом — уже на 0.03. То есть безопасная ширина зависит от того, сколько
разрешено потратить после неё, и читать эти два числа порознь нельзя.

**Правило «зона + бюджет ≤ 0.05» — не закон, и это проверено, а не принято на
веру.** Пять разбиений, дающих в сумме ровно 0.05, всё остальное на
поставляемых значениях:

| --- | --- | --- |
| 0.00 + 0.05 | 294 | 7/10 |

| 0.04 + 0.01 | 290 | 10/10 |

Сумма — полезный потолок; где внутри него стоит граница, решает измерение, и
0.02 + 0.03 — лучшая точка на этой прямой.

#### Константы, у которых сменились единицы

`STALL_IMPROVEMENT` и `SOLUTION_ERROR_TIE_REL` — отношения целевой функции к
самой себе, смена шкалы их не трогает. Остальные перемерены.

**`PRUNE_ERROR_TOLERANCE` пришлось разделить надвое, и это находка, а не
расширение задания.** Одна константа стояла в двух воротах прохода отсечения —
на `objective_error` и на `error`. До этой правки обе величины были одной и той
же абсолютной нормой (целевая = ошибка + загрязнение), поэтому одно число было
корректным. Теперь целевая функция относительная, а `error` осталась абсолютной
L2, которую получает вызывающий, — одна линейка на две шкалы. Разделено на:

* `PRUNE_OBJECTIVE_TOLERANCE = 0.03` (относительная),
* `PRUNE_ERROR_TOLERANCE = 0.03` (абсолютная, прежнее имя за прежней величиной).

Свип по каждой оси, всё остальное на поставляемых значениях, кроме явно
закреплённой второй оси:

| допуск | по целевой (абс. закреплён 0.005) | по `error` (цел. поставляемые 0.03) |
| --- | --- | --- |
| 0.005 | 296 / 5.817 / 2.905 | 296 / 5.813 / 2.905 |
| 0.01 | 296 / 5.817 / 2.905 | 296 / 5.777 / 2.925 |
| 0.02 | 296 / 5.817 / 2.905 | 296 / 5.737 / 3.030 |
| **0.03** | **296 / 5.813 / 2.905** | **296 / 5.730 / 3.050** |
| 0.04 | 295 / 5.807 / 2.910 | — |
| 0.05 | 293 / 5.800 / 2.910 | 296 / 5.717 / 3.075 |
| 0.1 | 293 / 5.800 / 2.910 | 296 / 5.713 / 3.075 |

(`rel ≤ 0.05` / средний count / медиана `min_portion`.)

Оси делают разное, и это и есть довод за разделение: **химию держит
относительная**, у неё обрыв за 0.03; **взвешиваемость покупает абсолютная**,
и по химии она не двигает ничего вплоть до 0.1, а насыщается на 0.03. Одно
число это спрятало бы: поднявший «допуск отсечения» до 0.05 потерял бы
одиннадцать кейсов и две достижимые цели сценария B, не узнав, какая половина
их съела.

Прежнее обоснование 0.005 («0.005 абсолютной ошибки в обожжённой глазури не
видно, это меньше 0.0033, которые уже стоит округление опубликованных процентов
до одного знака») — верное и ровно поэтому эти ворота не могут быть главными:
0.005 абсолютной L2 — это 0.17 % от SiO2 = 3.0 и 10 % от MgO = 0.05, одно число
про два совершенно разных количества химии. На 0.03 потолок даёт не больше 1 %
от SiO2 = 3.0, пятую часть допуска, который система принимает.

**Следовой компонент относительные ворота защищают лучше, чем абсолютные —
измерено.** Та же база и те же красители, что в таблице под
`PRUNE_ERROR_TOLERANCE` (пересняты под новыми весами: они меняют сам фит):

| материал | % | Δ error | Δ objective |
| --- | --- | --- | --- |
| Карбонат кобальта, CoCO3 | 1.0 | 0.1196 | 0.2815 |
| Карбонат кобальта, CoCO3 | 0.2 | 0.0242 | 0.0400 |
| Оксид никеля зеленый, NiO | 0.3 | 0.0545 | 0.1300 |
| Оксид хрома, Cr2O3 | 1.0 | 0.0230 | 0.2200 |
| Оксид хрома, Cr2O3 | 0.3 | 0.0063 | 0.0500 |
| Хромат железа, FeCr2O4 | 0.5 | 0.0064 | 0.0424 |
| Оксид железа красный, Fe2O3 | 0.3 | 0.0034 | 0.0400 |

Последняя строка — суть: 0.3 % красного железа стоят 0.0034 по абсолютной
норме, то есть меньше прежних 0.005, и выбрасывались; по относительной они
стоят 0.0400, то есть больше 0.03, и остаются. Правилом это по-прежнему не
становится (см. `_prune_solution`: краситель защищает правило единственного
носителя, а не порог), но дыра сузилась на порядок.

**`error_threshold` перемерен и оставлен на 0.1** — с явной оговоркой в
докстринге, что теперь это относительные единицы. Свип: 0.02, 0.05 и 0.1 дают
**побитово одинаковый прогон** (296 из 300, средний count 5.73), потому что при
относительной целевой функции ветка почти никогда не опускается так низко и
правило досрочной сходимости практически не срабатывает; 0.2 стоит трёх кейсов
и одной достижимой цели сценария B, 0.3 — семи, 0.5 — девятнадцати и
возвращает сценарий B к исходным 6 из 10. То есть 0.1 — наибольшее значение,
которое не стоит ничего, а меньшее ничего не покупает.

**`SOLUTION_ERROR_TIE_ABS` 0.01 → 0.02.** Свип, всё остальное на поставляемых
значениях:

| tie_abs | rel ≤ 0.05 | ср. count | медиана min_portion | B решено |
| --- | --- | --- | --- | --- |
| 0.0 | 296 | 5.743 | 3.030 | 10/10 |
| 0.01 | 296 | 5.733 | 3.050 | 10/10 |
| **0.02** | **296** | **5.730** | **3.050** | **10/10** |
| 0.05 | 286 | 5.670 | 3.160 | 8/10 |
| 0.1 | 259 | 5.563 | 3.375 | 7/10 |

От 0 до 0.02 — одна плоская область, выбор внутри неё **не измеряется**, и
утверждать обратное значило бы придумать результат. Измерен обрыв на 0.05 —
это сам допуск приёмки: полоса такой ширины объявляет «не хуже» рецепт,
промахнувшийся по оксиду на весь допуск, и затем предпочитает его за краткость.
0.02 взято внутри плоской области как **равное мёртвой зоне**: разница целевой
функции меньше того, что модуль уже объявил бесплатным, — не разница. 0.01
меряет то же самое; это не лучшее число, это старая цифра с новым смыслом.

#### Что вылезло сверх задания

**1. Точное равенство в сортировке стало нормой, и его разрешал порядок пула.**
С мёртвой зоной множество состояний получают целевую функцию **ровно 0**, все
попадают в одну полосу, и `_solution_sort_key` ранжирует их по числу
материалов — это ожидалось и записано. Не ожидалось, что и число материалов
совпадёт. Эталонный рецепт 09: оксид цинка и карбонат цинка несут один и тот же
оксид, оба рецепта попадают в цель точно, отличаются на 0.001 чистого шума
округления процентов, и порядок решал тот, кто раньше попал в пул. Вернулся
карбонат цинка — приоритет 100 против 10 у оксида, — и эталонный тест упал по
метрике `priority`.

Добавлена **последняя** ступень сортировки: взвешенный приоритет материалов
(та же величина, что считает `quality_metrics._priority_metric`). Приоритет —
собственное предпочтение модуля между химически взаимозаменяемыми материалами
(`PRIORITY_WEIGHT`, `_priority_start_set`); когда химия — ничья, предпочитать
больше нечем. Именно последняя: рецепт никогда не делается хуже по химии и не
удлиняется ради предпочтительного материала.

**Измерять это надо там, где приоритеты настоящие, и первая редакция мерила не
там.** «На корпусе нейтрально, сдвинулся один кейс» — это сценарий A, где
приоритеты синтезированы из популярности Glazy, и ступень двигает 1 верхний
ответ из 300. На сценарии B — боевая конфигурация, наши 19 материалов и
настоящий `priorities.json` — она двигает **10 верхних ответов из 100**, и все
десять именно то, что заявлено, а не размен: `objective_error`,

взвешенный приоритет строго улучшается.

Проверялась и другая гипотеза — что виновата грануляция `round(objective, 4)` в

**2. Второй способ потерять следовой компонент исчез.** Докстринг
`TestTraceIngredient` описывал его так: при `max_solutions=1` тот же целевой
рецепт возвращался без красителя, потому что ответ без кобальта набирал 0.0575
против дефолтного `error_threshold = 0.1`, ветка объявлялась сошедшейся и поиск
останавливался раньше, чем краситель пробовали. Перемерено: тот же ответ теперь
набирает **0.1300** (CoO промахивается на 0.15 своей шкалы, из которых зона
съедает 0.02), это выше порога, ветка не сходится, и краситель возвращается при
`max_solutions=1` со всеми аргументами по умолчанию. Добавлены два теста, один
на поведение и один на его предпосылку.

**3. `objective_error ≥ error` больше не инвариант.** Тест это утверждал и
проходил только потому, что на его фикстуре доминирует загрязнение. На корпусе
**340** возвращённых решений имеют целевую функцию ниже своей `error`, самое
широкое расхождение 13.8: относительное отклонение большого оксида делится на
сам оксид. Тест заменён на то, что действительно верно и проверяемо —
`penalize_unlisted` нагружает целевую функцию тем, чего `error` не видит.

**4. Ключ без молярной массы получал строку NNLS, и относительные веса сделали
её главной.** `_expand_target` добавлял в цель ключ **любой** формулы материала.
Пока веса были единичными, лишний ключ был незаметной мелочью — строка с нулевой
правой частью и весом 1.0 наравне со всеми, то есть тихая инструкция
«минимизировать эту величину». С относительными весами настоящий оксид получает
`1/(M·s)`: по этой базе от **0.0055** (SiO2 при цели 3.0) и максимум до
**0.5264** (фтор у пола шкалы — самый лёгкий ключ `molar_masses.json`), а ключ
без молярной массы остаётся на голом штрафе 1.0, то есть **тяжелее любой
химической строки, какая тут вообще возможна**: в 1.9 раза в самом
благоприятном случае и в 182 раза в обычном. Фит начинает определяться им.

Поймано не тестом, а логом: ветка «нет молярной массы» предупредила
одиннадцать раз подряд на прогоне одиннадцати эталонных рецептов по полному
каталогу.

**Первая правка чинила экземпляр, а не механизм**, и это отдельная запись,
потому что ошибка типичная: `_expand_target` стал пропускать
`common.NON_OXIDE_KEYS`, то есть список имён. Список имён не защищает от ключа,
которого в нём нет. Демонстрация на документированном шве `materials=` — та же
полка, отличающаяся одним неанализированным ключом на одном материале:

```text
CLEAN Ash = {CaO 30, SiO2 30, P2O5 5}
DIRTY Ash = {CaO 30, SiO2 30, P2O5 5, Carbon 35}
цель {SiO2 3.0, Al2O3 0.4, CaO 0.7, P2O5 0.05}

clean : {Ash 40.57, Kaolin 31.16, Silica 28.27}   objective 0.0117
dirty : {Kaolin 33.51, Silica 43.49, Whiting 23.0} objective 0.4800
```

Единственный носитель запрошенного P2O5 выброшен целиком, целевая функция
выросла в 41 раз, единственный признак — одна строка `logger.warning`. Заодно
опора на `NON_OXIDE_KEYS` была ложной: `bench/corpus.LOI_KEYS` несёт третье
написание `'loi'`, которого в `common.NON_OXIDE_KEYS` нет, так что «единственное
определение» им не было.

**Правило теперь по свойству:** ключ, которого нет в `molar_masses.json`, не
создаёт строки NNLS вообще — то же правило, которое `usable_target` уже
применяет на стороне цели, и оно принципиально верное: величину, которую система
не умеет выразить в UMF, нельзя сделать слагаемым UMF-относительной невязки, а
в весовых процентах её вес произволен. Отказанные ключи логируются поимённо.
`NON_OXIDE_KEYS` перестал быть несущей конструкцией.

**Правка не доходила до остаточной невязки и фокусного оксида.**
`state['weight_composition']` приходит из `calculate_recipe_composition`,
которая ППП сохраняет, а `_weight_residual` объединял ключи цели и факта — и
пускал их обратно с чёрного хода:

```text
problem['oxides'] = ['SiO2','Al2O3','CaO']
residual = {SiO2 +10.010, Al2O3 +2.266, CaO +2.177, LOI −4.356, Loi −10.097}
_focus_oxide(residual) -> 'Loi'
```

Дальше `_score_candidate` штрафовал каждый материал, несущий ППП: `residual.get`
возвращает 0.0, |0.0| внутри `MATCHED_OXIDE_TOLERANCE`, и ключ попадал в член
`disturbance`. Плюс `_normalize_to_100` нормировал фактический состав вместе с
массой ППП, из-за чего невязки **всех** настоящих оксидов были смещены вверх
систематически — те +10.0 по SiO2 выше и есть этот артефакт, на точно решённом
рецепте. Одно правило применено в обоих местах: `_weight_residual` фильтрует по
`problem['oxides']` и нормирует **после** фильтра, `_score_candidate` пропускает
ключ, которого нет в невязке, но **оставляет его в знаменателе** — 100 г мела
дают 56.1 г CaO, и деление на одни оксиды перевернуло бы смещение в
предпочтение материалов, которые выгорают. После правки та же фикстура даёт
невязку ~0 по всем трём оксидам и фокус `CaO`.

**Насколько это часто, измерено — первая редакция угадала и ошиблась в
семьдесят раз.** Ключ `Loi` несут **3 из 216** материалов
`database/materials.json` — Дисульфид Молибдена, Метакаолин BMK-45,
Нефелин-сиенит А-270 — и **все три `inInventory: false`**. Именно поэтому строка
появляется только при явном инвентаре или инъецированном каталоге, и именно
поэтому ни один из двух замерочных стендов её не видит: дефолтный инвентарь из
19 материалов все три исключает, а у формул корпуса Glazy ППП срезает
`bench/corpus._clean_formula`.

На корпусе правка двигает **ноль** кейсов на всех трёх сериях (по построению),
на полном каталоге все 11 эталонных рецептов держатся до последнего знака.
После исключения ключей без молярной массы **ни один** из 51 различного ключа
формул 216 материалов не отсутствует в `molar_masses.json`, так что ветка
«нет молярной массы» в `_build_problem` не оборонительная, а **удалена**:
`molar_masses[oxide]` индексируется, и `KeyError` там означал бы сломанный
инвариант, а не проблему данных.

**5. Фикстуру `TestPruningChecksBothErrors` пришлось перестроить.** Механизм,
который она демонстрировала — удаление, удешевляющее целевую функцию за счёт
снятого загрязнения и удорожающее `error`, — ослаб: член загрязнения теперь
тоже относительный и растёт вместе с остальными. Легко строится другой и более
актуальный: удаление, двигающее большой оксид на процент **от него самого**,
почти бесплатно по относительной целевой и дорого по абсолютной норме. Ворота
нужны ровно так же; изменилось, каким рычагом их проверять.

**6. Два теста ограничивали `objective_error` абсолютной половиной константы.**
`tests/test_solver_inverse.py` в двух местах сравнивал целевую функцию с
`PRUNE_ERROR_TOLERANCE`. Зелёными они были только потому, что обе половины
сегодня равны 0.03 — то есть проверяли не те ворота. Исправлено на
`PRUNE_OBJECTIVE_TOLERANCE` вместе с докстрингами. Проверено фальсификацией,
прогоном всего набора с подменённой константой:

| подмена | до правки | после правки |
| --- | --- | --- |
| `PRUNE_ERROR_TOLERANCE` 0.03 → 0.05 | зелено (не те ворота) | зелено |
| `PRUNE_ERROR_TOLERANCE` 0.03 → 0.005 | **красно, не на ту константу** | зелено |
| `PRUNE_OBJECTIVE_TOLERANCE` 0.03 → 0.005 | зелено | **красно, по существу** |

Последняя строка — то, чего добивались: при 0.005 падают ровно два теста, и оба
своим стражем предпосылки («этот краситель больше не контрпример допуску»), то
есть громко сообщают, что фикстура перестала демонстрировать то, ради чего
написана, вместо тихого прохода.

**7. `_focus_oxide` остался на абсолютной весовой шкале.** Единственное
непереведённое место поиска, и это решение, а не недосмотр: при
`candidate_search='exhaustive'` (дефолт) решаются все кандидаты, поэтому фокус
упорядочивает только ничью между наборами, чья целевая совпадает с точностью до
`CANDIDATE_TIE_STEP`. При `'heuristic'` он действительно фильтрует. Регрессии
нет — по 300 кейсам сценария A через 10.19: `heuristic` 253 → **294**,
`exhaustive` 251 → **296**. Перевод и этого места — отдельная правка со своим
замером, а не бесплатная уборка; в докстринге это записано.

Десять — ровно то число, которое LP называет достижимым, так что **поиск и LP

**Абсолютная норма на сценарии B ухудшилась намеренно.** `umf_error` — отставная
метрика §10.18, поиск перестал её оптимизировать, её максимум вырос
3.31 → 6.52, и `check_regressions` на это сработал — правильно сработал. Гейт
не ослаблен и метрика не убрана; baseline перенесён с запиской, которая
называет и регрессию, и число, заменившее её в роли вердикта: на том же прогоне
`max_relative` улучшился (медиана 0.72 → 0.55, улучшилось 59 / ухудшилось 7).
На сценарии A `umf_error` улучшился и без всякой оговорки (среднее
0.0184 → 0.0062, максимум 0.596 → 0.230).

**Счёт за материалы реален и оплачен сознательно.** Попарно по кейсам,
сценарий A: `count` 47 хуже / 22 лучше (медиана 5 → 6, p90 8 → 9),
`min_portion` 85 хуже / 73 лучше (медиана 3.185 → 3.050), `junk_count` 12 хуже
/ 13 лучше. Сценарий B: `count` 26 хуже / 24 лучше, `min_portion` 36 хуже /
62 лучше, `junk_count` 2 хуже / 6 лучше, `assembly_score` медиана +17.1 %.
Регрессия в основном несущая: цель, называющая MgO, требует носителя MgO, а
самый дешёвый мешок на полке его не несёт. Дефицит взвешиваемости мёртвая зона
уже отыграла на две трети (76 / 0 без неё против 47 / 22 с ней), остаток —
цена химии, которой раньше просто не было.

Число альтернатив не изменилось: среднее 3.70 → 3.74, «только одна» 41 → 42,
«все пять» 166 → 168. Одиночные ответы: 0.3 % на сценарии A (как было) и
1.0 % против 1.7 % на 19 материалах. Проход отсечения больше не выводит ни один
ответ за `error_threshold` (было 1 из 300), наибольший рост целевой функции под
ним — 0.0346.

#### Известное расхождение, которое чинить не здесь

Старый `UI/js/app.js:886-901` пересортировывает ответы по отставной абсолютной
`error`, делит их порогом `error < 0.01` в отставных единицах, выбрасывает
порядок решателя вместе с новой ступенью приоритета и подписывает `error * 100`
как «Погрешность, %». Этот интерфейс выбрасывается целиком следующей задачей, и
чинить его смысла нет; расхождение записано в `UI_DECISIONS.md` §7.2.1, чтобы
логика не уехала в UI-v2 вместе с кодом.
