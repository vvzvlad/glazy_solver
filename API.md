# API документация Glazy Solver

## Базовая информация

API-сервер доступен по адресу `http://localhost:5000/api` при локальном запуске
(`python api_server.py`). Тот же процесс отдаёт статические файлы веб-UI из
директории `UI/` по корневому пути `/`.

Все API-методы принимают и возвращают данные в формате JSON.

## Движки решателя

Рецепт можно считать одним из двух движков, выбор — параметром `solver` в
`POST /api/solve`.

- **`iterative`** (по умолчанию, `solver_iterative.py`) — итеративный решатель
  по приоритетам материалов (`database/priorities.json`). Стартует с наиболее
  приоритетных материалов, на каждой итерации добавляет материал, лучше всех
  закрывающий самый дефицитный оксид, и пересчитывает NNLS. **Детерминирован**:
  один и тот же запрос всегда даёт один и тот же ответ. На эталонных рецептах
  (см. `compare_solvers.py`) точнее воспроизводит исходный набор материалов и
  обходится меньшим их числом.
- **`classic`** (`solver_classic.py`) — старое проверенное ядро. Решает NNLS на
  полном наборе материалов инвентаря, а затем перебирает случайные подмножества
  материалов, отбирая варианты с приемлемой ошибкой. Перебор случайный, но
  генератор свой и засеян фиксированным seed'ом
  (`find_multiple_solutions(seed=0)`; `/api/solve` его не переопределяет и
  параметра для этого не имеет), поэтому через API движок тоже
  **детерминирован**: два одинаковых запроса дают побитово одинаковый ответ.
  Смена seed'а меняет набор перебираемых подмножеств и, как следствие, выдачу.

Итеративный движок выбран дефолтным по замерам на 11 эталонных рецептах
(`compare_solvers.py`, сводка в `REFACTORING.md`, раздел 8): медиана суммарной
ошибки 0.0020 против 0.0030, время решения втрое меньше, точный исходный состав
восстановлен в 10 рецептах из 11 против 2 у классики.

Порядок этот **зависит от размера инвентаря**, и на корпусном бенчмарке
(`tests/test_inverse_corpus.py`, 300 рецептов дампа Glazy) он обратный: когда
решателю выдают инвентарь из 2–12 материалов самого рецепта, классика проходит
химический гейт на 100% против 94.67% у итеративного и работает примерно в 30
раз быстрее — там её решение по полной матрице и есть ответ. Итеративный движок
выигрывает на боевом инвентаре из 19 материалов, который сервер и обслуживает.

Формат ответа у обоих движков одинаковый: у `iterative` он дополнен полями
`objective_error`, `unlisted_weight` и `unity_scale`.

В веб-UI движок выбирается радиокнопками в карточке «Настройки расчета»;
выбор запоминается в `localStorage` браузера.

## Endpoints

### Расчет рецепта глазури

**Endpoint:** `POST /api/solve`

**Описание:** Подбирает рецепты по заданной UMF-формуле из доступных материалов.

**Input:**
```json
{
  "umf": {
    "SiO2": 4,
    "Al2O3": 1,
    "Na2O": 0.5,
    "K2O": 0.5
  },
  "max_solutions": 3,
  "min_materials": true,
  "error_tolerance": 0.01,
  "solver": "iterative",
  "inventory": ["Нефелин-сиенит VR13", "Каолин КЖФ-1"]
}
```

**Параметры:**
- `umf` (обязательный): UMF формула глазури в виде словаря оксид:значение
- `max_solutions` (опциональный, по умолчанию 3): максимальное количество возвращаемых решений
- `min_materials` (опциональный, по умолчанию true): предпочитать решения с меньшим количеством материалов; используется только движком `classic`, движок `iterative` параметр игнорирует
- `error_tolerance` (опциональный, по умолчанию 0.01): допустимое увеличение ошибки для решений с меньшим числом материалов; используется только движком `classic`, движок `iterative` параметр игнорирует
- `solver` (опциональный, по умолчанию `"iterative"`): движок расчёта, `"iterative"` или `"classic"`. Неизвестное значение → `400 unknown_solver`
- `penalize_unlisted` (опциональный, по умолчанию 1.0): насколько сильно оксид, не указанный в `umf`, прижимается к нулю. `1.0`/`true` — «не указан значит должен быть нулём», `0.0`/`false` — «всё равно», между ними мягкий вес. Используется только движком `iterative`
- `inventory` (опциональный): список имён доступных материалов. Если не передан, берутся материалы с флагом `inInventory: true` из базы

**Output:** объект из двух полей.

```json
{
  "solutions": [ /* решения, лучшее первым, формат ниже */ ],
  "warnings": ["оксиды цели не распознаны и не учтены: Unobtainium"]
}
```

Раньше эндпоинт отдавал голый массив решений. Формат изменён ради `warnings`:
оксид, который сервер не смог посчитать, из ответа просто исчезал, и узнать об
этом было неоткуда — а `/api/feasibility` на ту же самую цель отвечал этой
фразой с самого начала. В массиве полю неоткуда взяться, а внутри решений оно
жить не может: цель из одних нераспознанных оксидов даёт **ноль решений**, и
это ровно тот запрос, которому предупреждение нужнее всего. Единственный живой
потребитель, `UI/`, переведён на новый формат в этой же правке и понимает оба
(`unpack_solve_response` в `UI/js/app.js`); прототип `UI-v2/` работает на моках
и в API вообще не ходит.

**Формат одного решения:**

```json
{
  "recipe": {
    "Нефелин-сиенит VR13": 29.78,
    "Каолин КЖФ-1": 22.7,
    "Улексит (Химпэк)": 28.26,
    "Древесная зола": 19.26
  },
  "error": 0.0,
  "materials_count": 4,
  "target_composition": {
    "SiO2": 4,
    "Al2O3": 1,
    "Na2O": 0.5,
    "K2O": 0.5
  },
  "actual_composition": {
    "SiO2": 4.0,
    "Al2O3": 1.0,
    "Na2O": 0.5,
    "K2O": 0.5,
    "CaO": 1.1751,
    "B2O3": 1.0508,
    "MgO": 0.3452,
    "P2O5": 0.1294,
    "Fe2O3": 0.0812,
    "SrO": 0.0203,
    "TiO2": 0.0076
  },
  "recipe_umf": {
    "SiO2": 4.0,
    "Al2O3": 1.0,
    "Na2O": 0.5,
    "K2O": 0.5,
    "CaO": 1.1751,
    "B2O3": 1.0508,
    "MgO": 0.3452,
    "P2O5": 0.1294,
    "Fe2O3": 0.0812,
    "SrO": 0.0203,
    "TiO2": 0.0076
  },
  "weight_composition": {
    "SiO2": 34.36,
    "Al2O3": 14.57,
    "Na2O": 4.43,
    "K2O": 6.73,
    "CaO": 9.42,
    "B2O3": 10.46,
    "MgO": 1.99,
    "P2O5": 2.63,
    "Fe2O3": 1.83,
    "SrO": 0.28,
    "TiO2": 0.09
  }
}
```

**Предупреждения (`warnings`):** список строк о самом запросе, не о конкретном
решении. Пустой, когда предупреждать не о чем. Поле есть **в любом ответе этого
эндпоинта**, включая все ошибки: поле, которое есть при 200 и пропадает при 400,
пришлось бы обходить проверкой на каждом вызове, а запрос вполне может быть
неправильным дважды. Сейчас в списке бывает одна фраза, и она дословно — вплоть
до порядка имён — совпадает с той, которой на ту же цель отвечает
`/api/feasibility`: один вход, один вердикт, каким эндпоинтом ни спроси.

- `оксиды цели не распознаны и не учтены: <имена>` — в `umf` пришло имя,
  которого нет в `database/molar_masses.json`, либо значение, которое не число,
  отрицательное, `NaN` или бесконечность. Имена перечислены **по алфавиту**, а
  не в порядке, в котором их прислал клиент. Предупреждение выдаётся **один раз
  на запрос**, а не на шаг поиска, и приходит даже когда решений ноль. Ключ
  `Loi` в цели выбрасывается молча: это не оксид, а бухгалтерия анализа
  материала, и `/api/feasibility` молчит о нём по той же причине.

**Цель чистится один раз, до выбора движка** (`solver_iterative.usable_target`),
и обоим движкам уходит уже очищенная. Это не деталь реализации: движки чистят
по-разному — `classic` выбрасывает только неизвестное **имя** (в
`umf_to_weights`), а отрицательное **значение** честно скармливает своему NNLS.
Пока чистка жила внутри движков, ответ на `{"Fe2O3": -0.5, "solver": "classic"}`
нёс фразу «оксид не учтён» рядом с рецептом, посчитанным **по** `-0.5`, — и
рецепт этот отличался от рецепта на ту же цель без ключа целиком, всеми
материалами. Отрицательный или `NaN` UMF не является законным входом ни для
одного движка, так что ничего осмысленного этой чисткой не потеряно, а
`warnings`, `target_composition` и то, по чему реально идёт фит, теперь
описывают одну и ту же цель по построению.

Если после чистки от цели ничего не осталось, ответ — `422 empty_target` с теми же
`warnings`, и ни один движок не запускается. Сам `umf`, если он не непустой объект,
отбивается ещё раньше — `400 missing_umf`, как и в `/api/feasibility`. Если цель пережила чистку, но состоит из одних
нулей — `422 zero_target` по той же схеме: причины разные, сообщения разные.

**Поля решения:**
- `recipe`: рецепт в виде словаря материал:весовой процент, сумма — 100
- `error`: метрика расхождения полученной UMF с целевой (меньше — лучше)
- `materials_count`: количество материалов в рецепте
- `target_composition`: целевая UMF — очищенная, та, с которой реально работали: оксиды с неизвестным именем или некорректным значением из неё выброшены, какие именно — сказано в `warnings`. Это верно для **обоих** движков: цель чистится до выбора движка (см. выше), а не внутри `iterative`, как было раньше
- `actual_composition`: фактическая UMF рецепта. Содержит и оксиды, которых не было в целевой формуле — они приходят с материалами
- `recipe_umf`: копия `actual_composition`, отдельным полем для удобства фронтенда
- `weight_composition`: фактический оксидный состав рецепта в весовых процентах. Сумма меньше 100: в формулах материалов не учитываются летучие компоненты (CO2, вода)

Движок `iterative` (дефолтный) добавляет к каждому решению ещё три поля:
- `objective_error`: то, что реально минимизировал поиск, и это **не та же величина, что `error`**: L2-норма ОТНОСИТЕЛЬНЫХ отклонений по оксидам, `|target − actual| / max(target, 0.1)`, где каждому оксиду прощается мёртвая зона 0.02, плюс штраф за неуказанные оксиды. Сравнивать его следует с допуском 0.05, на котором отвечает `/api/feasibility`, а не с `error` — числа отличаются в разы в обе стороны
- `unlisted_weight`: применённый `penalize_unlisted`
- `unity_scale`: во сколько раз UMF рецепта пришлось пересчитать на базис целевой формулы

**Пример запроса с cURL (движок по умолчанию, `iterative`):**
```bash
curl -X POST http://localhost:5000/api/solve \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 4, "Al2O3": 1, "Na2O": 0.5, "K2O": 0.5}}'
```

**Пример запроса с итеративным движком и явным инвентарём:**
```bash
curl -X POST http://localhost:5000/api/solve \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 4, "Al2O3": 1, "Na2O": 0.5, "K2O": 0.5}, "solver": "iterative", "max_solutions": 2, "inventory": ["Нефелин-сиенит VR13", "Каолин КЖФ-1", "Кварцевая мука Кварцверке W12"]}'
```

**Пример запроса со старым классическим движком:**
```bash
curl -X POST http://localhost:5000/api/solve \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 4, "Al2O3": 1, "Na2O": 0.5, "K2O": 0.5}, "solver": "classic", "min_materials": true}'
```

Оба движка на одинаковый запрос отвечают одинаково: `iterative` детерминирован
по построению, `classic` — потому что его перебор подмножеств засеян
фиксированным seed'ом (см. «Движки решателя» выше).

### Достижимость формулы и достижимые диапазоны

**Endpoint:** `POST /api/feasibility`

**Описание:** Отвечает на вопрос «а получится ли вообще эта формула из этих
материалов»: достижима ли цель, какой оксид виноват, если нет, и в каких
пределах может гулять каждый оксид и каждый материал, пока цель держится
(«улексита можно 0–17%»).

Решатель здесь не запускается. Вердикт — свойство пары «цель + инвентарь», а не
рецепта, поэтому интерфейс может показать его ещё до того, как рецепт появился,
пока пользователь набирает формулу.

Почему отдельный эндпоинт, а не блок в ответе `POST /api/solve`, как просил §2.4
ТЗ: вердикт не зависит от рецепта и нужен раньше него — интерфейс показывает его,
пока пользователь ещё набирает формулу, и запрашивает заново при смене инвентаря,
а не при смене решения. Это разные запросы с разным временем жизни ответа, а не
экономия одного round-trip'а.

(Изначально здесь стоял и второй довод — что ответ `/api/solve` голый список и
заворачивать его в объект значит сломать работающий `UI/`. Этот довод больше не
действует: `/api/solve` теперь отвечает объектом ради `warnings`, а `UI/`
переведён на новый формат. Довод выше от этого не зависит.)

**Как это считается.** UMF — дробно-линейная величина (оксид, делённый на сумму
плавней), но **однородно-линейная**, и это делает всю задачу линейной:
ограничение `lo <= n_i/S_flux <= hi` переписывается как
`n_i - hi*S_flux <= 0` и `lo*S_flux - n_i <= 0`, а если зафиксировать масштаб
равенством `S_flux(x) = 1`, то UMF оксида — это буквально `(A x)_i`. Матрица `A`
молярная: `A[i,j]` — моли оксида i на 100 г материала j.

Вердикт — чебышёвский (минимаксный) LP: минимизировать `t` при
`|(A x)_i - b_i| <= t * s_i`, где `s_i = max(b_i, 0.1)` — масштаб оксида (иначе
MgO 0.05 и SiO2 3 несопоставимы). Достижимо — это `t* <= tol`. Следом идёт
второй LP: минимакс задаёт только худший оксид, а остальные внутри `t*` вольны
уехать куда угодно бесплатно, поэтому `t` замораживается на `t*` и минимизируется
**сумма** отклонений. Без этого шага в ближайшей формуле оксиды промахивались как
попало — на эталонной глазури с добавленным ZrO2 мимо шли семь оксидов там, где
недостижим один.

Третий вид LP решает, **кто попадёт в `unreachable_oxides`**, потому что второй
шаг список не стабилизирует, а только улучшает. На 250 правдоподобных целях 60
из 132 недостижимых ответов всё ещё называли оксид, который мог бы остаться в
допуске и без изменения `t*`. Поэтому на каждый оксид, промахнувшийся в
отчётной точке, решается отдельный LP: «а мог ли он уложиться в `tol`, пока `t`
держится на `t*`?». Несовместимо — оксид действительно обречён; совместимо —
это артефакт выбранной точки, и в вердикт он не идёт. На тех же 250 целях после
этого артефактов не осталось ни одного (552 названных оксида, проверено
независимым путём — через `achievable_ranges` на грани `t*`).

Из-за этого `per_oxide` и `unreachable_oxides` говорят о разном, и намеренно:
`per_oxide` — это одна конкретная ближайшая формула, где оксид может выйти за
`tol`, не будучи обречённым (промахи можно перераспределять между оксидами, и
показана та раскладка, где их сумма минимальна). Поле `reachable` в строке
следует вердикту, а не собственным числам строки.

Оксиды, которых в цели нет, но которые могут приехать с материалами, входят в
задачу с `b_i = 0` — как `_expand_target` в итеративном решателе. Исключение —
**пассажиры**, см. ниже.

Цель с суммой плавней, отличной от 1, не объявляется недостижимой, а приводится
к единице: та же формула в другом масштабе — та же глазурь. В ответе про это
будет строчка в `warnings`. Цель вообще без плавней — это не UMF, нормировать не
на что, ответ `no_target_fluxes` (422).

**Input:**
```json
{
  "umf": {"SiO2": 3.151, "Al2O3": 0.379, "CaO": 0.718, "Na2O": 0.143, "K2O": 0.086},
  "inventory": ["Нефелин-сиенит VR13", "Каолин КЖФ-1"],
  "passengers": {"Fe2O3": 0.03},
  "material_constraints": {"Улексит (Химпэк)": [0, 20]},
  "tol": 0.05,
  "ranges": true
}
```

- `umf` (обязательный): целевая формула. Нераспознанные имена, отрицательные значения, NaN и бесконечности отбрасываются со строчкой в `warnings`; явный `0.0` — это ограничение «железа не надо», а не отсутствие мнения, и он сохраняется. Значение больше `1e6` **после** приведения к единице плавней — это уже не формула, ответ `degenerate_target` (422)
- `inventory` (опциональный): список доступных материалов. `null` или отсутствие параметра — **дефолтный инвентарь** (материалы с `inInventory`), ровно как в `/api/solve`
- `passengers` (опциональный): `{оксид: верхняя граница}` в единицах UMF. Чистятся один раз и одинаково для вердикта и для диапазонов: непонятное имя, отрицательное значение или NaN выбрасываются со строчкой в `warnings`, а не действуют в одной половине ответа и не действуют в другой
- `material_constraints` (опциональный): `{материал: [min, max]}` в весовых процентах, любой конец — `null` для «без границы». Влияет только на `achievable_ranges`
- `tol` (опциональный, 0.05): порог вердикта, он же половина ширины коробки, вокруг которой считаются диапазоны
- `ranges` (опциональный, `true`): считать ли `achievable_ranges`. `false` — только вердикт, и это разница между ~2 мс и ~52 мс на боевом инвентаре. Интерфейсу, который дёргает эндпоинт на каждое нажатие клавиши, нужен именно `false`

**Ограничение на размер.** Диапазоны стоят `1 + 2 * (оксиды + материалы)` LP, и
цена одного LP сама растёт с размером задачи: 19 материалов — 63 LP и 52 мс, 60
материалов — 167 LP и 317 мс, вся база из 216 — 459 LP и **4.3 секунды** на
однопоточном Flask. Поэтому запрос с диапазонами, которому потребовалось бы
больше 180 LP, отклоняется с `inventory_too_large` (413); в сообщении названы и
спроецированное число LP, и потолок. Вердикт сам по себе такого потолка не имеет
— он стоит два LP и на всей базе занимает 31 мс, так что `"ranges": false`
работает с любым инвентарём.

`inventory: null` здесь означает дефолтный инвентарь, а в `POST /api/sensitivity`
то же слово означает **всю базу**. Различие намеренное: чувствительность
анализирует готовый рецепт, который сам называет свои материалы, а достижимость
отвечает на вопрос «что можно собрать из того, что у меня есть», и считать её по
216 материалам, которых у пользователя нет, значит вынести вердикт о чужой
полке.

**Пассажиры — главный параметр этого эндпоинта.** Оксид, которого не просили, —
не ошибка, которую надо загнать в ноль: он приезжает с материалами, хочет того
кто-нибудь или нет (Fe2O3 с каолином, TiO2 с волластонитом, SrO с улекситом).
Поэтому пассажир получает **одностороннюю верхнюю границу** `Fe2O3 <= 0.03`, без
нижней границы и без вклада в `t`. Двусторонняя цель на такое число заставляет
решатель гнаться за величиной, которую никто не выбирал, и платить за это
мусорным компонентом (`UI_DECISIONS.md` §2.2).

На синтетическом наборе (кремнезём, кальцит и единственный источник глинозёма,
который несёт 10% железа) разница в числах такая:

| Fe2O3 в запросе | вердикт | макс. отклонение | Al2O3 в ответе |
| --- | --- | --- | --- |
| не упомянут (гонится в 0) | недостижимо | 0.176 | 0.247 вместо 0.3 |
| пассажир `<= 0.05` | достижимо | 0.000 | 0.300 |
| обычная цель `0.05` | недостижимо | 0.237 | 0.371 — перелёт |

Оксид, названный и в `umf`, и в `passengers`, считается пассажиром: верхняя
граница — более слабое и более честное из двух утверждений. Об этом тоже будет
строчка в `warnings`.

**Output:**
```json
{
  "feasible": true,
  "max_relative_deviation": 0.00162,
  "per_oxide": [
    {"oxide": "B2O3", "target": 0.266, "closest": 0.26643, "delta": 0.00043,
     "relative": 0.00162, "reachable": true}
  ],
  "unreachable_oxides": [],
  "why": {},
  "passengers": [{"oxide": "Fe2O3", "limit": 0.03, "closest": 0.0021, "within_limit": true}],
  "closest_recipe": {"Волластонит МИВОЛЛ": 19.97, "Каолин КЖФ-1": 14.89},
  "warnings": [],
  "diagnostics": {"cond": 488.92, "ill_conditioned": false, "rank": 12, "n_oxides": 12},
  "achievable_ranges": {
    "feasible": true,
    "oxide_ranges": {"SiO2": [2.99345, 3.30855], "TiO2": [0.0, 0.008]},
    "material_ranges": {"Улексит (Химпэк)": [0.0, 16.66]},
    "example_recipe": {"Волластонит МИВОЛЛ": 23.77},
    "lp_count": 63,
    "warnings": []
  }
}
```

- `feasible`: `t* <= tol`
- `max_relative_deviation`: то самое `t*` — оптимум минимакса, а не худшая строка отданной точки. Второй LP не может улучшить `t*` (это и есть наименьшее возможное худшее отклонение), он может только добавить сверху свою численную погрешность, и вердикт, вынесенный по ней, расходился с `achievable_ranges` при том же `tol`
- `per_oxide`: отсортировано по `relative` по убыванию — вердикт живёт в относительных единицах, и сортировка по `|delta|` ставила SiO2, промахнувшийся на 1% себя, выше CoO, промахнувшегося втрое. Оксиды цели — всегда; оксид-загрязнитель — только если ближайшая формула его действительно несёт (иначе шестьдесят строк «просили 0, получили 0» хоронят ответ). Поле `reachable` следует `unreachable_oxides`, а не собственному `relative` строки
- `unreachable_oxides`: оксиды, **обречённые** промахнуться, — по одному LP на каждого (см. выше). Не «те, у кого `relative > tol` в отчётной точке»: это свойство точки, а не задачи
- `why`: короткая человеческая причина на каждый недостижимый оксид, **выведенная, а не угаданная**. Три случая: (1) ни один материал набора не содержит оксид — читается прямо из матрицы; (2) содержит, но не дотягивает — отдельным LP считается достижимый экстремум, и он же называется в сообщении («достижимо максимум 0.0207»); (3) всё остальное — «достижим сам по себе, но не одновременно с остальными оксидами цели». Назвать, с каким именно оксидом идёт конфликт, третий случай не может: для этого нужны двойственные переменные, а двойственные минимакса указывают на активные ограничения, а не на химию
- `passengers`: где на самом деле оказался каждый пассажир и уложился ли он в свою границу
- `closest_recipe`: ближайшая достижимая точка как рецепт, нормированный к 100%; материалы легче 0.1% выброшены, остальные перенормированы, так что сумма остаётся 100. Это та же точка, что и в колонке `closest`, но округлённая до 0.01% и без следов, так что пересчёт UMF из неё сходится с `closest` примерно до 3e-3, а не до последнего знака: это рецепт, который отвешивают, а не четвёртый знак после запятой
- `diagnostics`: обусловленность матрицы «оксиды × материалы» инвентаря. `cond: null` означает вырожденный набор — это не «не измерили», а «бесконечно плохо обусловлен». Порог `ill_conditioned` тот же `1e3`, что и в `quality_metrics`
- `achievable_ranges`: min и max каждой величины при **всех остальных ограничениях одновременно**. Границу получает каждый оксид: названный целью — коробку `[b - tol*s, b + tol*s]`, не названный — потолок `tol * 0.1`, ровно тот, по которому вердикт меряет загрязнение. Так область и есть та, которую принимает вердикт. Без второго правила ответ врал в самом главном месте: на боевом инвентаре получалось «костной золы можно до 19.9%», а при 19.9% костной золы смесь несёт P2O5 0.198 — отклонение 1.98 при допуске 0.05, то есть тот же модуль этот рецепт отвергает. `lp_count` — сколько LP реально решено, `1 + 2*(оксиды + материалы)` при успехе
- Верхняя граница `null` означает бесконечность и появляется, только когда оксид оставлен свободным явно (`oxide_constraints: {"SiO2": [null, null]}` на уровне библиотеки). Через этот эндпоинт такого не бывает: цель, пассажиры и потолок загрязнения ограничивают сверху каждый оксид, поэтому все концы конечны

Если ограничения противоречивы, `achievable_ranges` отвечает
`{"feasible": false}` и останавливается на первом же LP (`lp_count` 1 или 2), а
не перемалывает оставшиеся семьдесят, чтобы семьдесят раз повторить одно и то
же. Вердикт при этом считается отдельно и остаётся в силе.

Про стоимость на боевом инвентаре (19 материалов, 12 оксидов): блок диапазонов —
63 LP и около 52 мс; вердикт достижимой цели — 2 LP и 2.1 мс; вердикт
недостижимой — плюс по одному LP на каждый промахнувшийся оксид, 3.2 мс когда
обречён один и 8.4 мс на цели, где кандидатов пять.

Диагностика не должна ронять расчёт, поэтому ошибка внутри `achievable_ranges`
не роняет запрос целиком: в этом поле придёт `{"feasible": null, "error": ...}`,
а вердикт останется на месте.

**Коды ошибок эндпоинта:** `missing_umf` (400), `invalid_parameter` (400),
`empty_target` (422), `no_target_fluxes` (422), `degenerate_target` (422),
`no_usable_materials` (422), `inventory_too_large` (413),
`no_fluxes` (422 — ни один материал набора не несёт плавня, нормировать не на
что), `nonfinite_analysis` (500 — в `formula` материала NaN или бесконечность),
`lp_not_converged` (500), `feasibility_failed` (500), `server_error` (500).

**Пример запроса с cURL:**
```bash
curl -X POST http://localhost:5000/api/feasibility \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 3.151, "Al2O3": 0.379, "CaO": 0.718, "B2O3": 0.266, "Na2O": 0.143, "K2O": 0.086, "MgO": 0.048}}'
```

**Пример с пассажиром и ограничением по материалу:**
```bash
curl -X POST http://localhost:5000/api/feasibility \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 3.0, "Al2O3": 0.35, "CaO": 0.6, "Na2O": 0.25, "K2O": 0.15}, "passengers": {"Fe2O3": 0.03}, "material_constraints": {"Улексит (Химпэк)": [0, 20]}}'
```

### Импорт рецепта с glazy.org

**Endpoint:** `POST /api/glazy_import`

**Описание:** Загружает рецепт с glazy.org через публичное API Glazy и
возвращает его целевую UMF-формулу вместе с исходным составом (материалы и
проценты) для показа в интерфейсе.

Работает **только с публичными рецептами**: запрос к Glazy идёт анонимно, без
логина. Приватный рецепт отдаёт `403 glazy_forbidden`.

Материалы Glazy **не сопоставляются** с локальной базой `database/materials.json`
— они возвращаются как справка. Рецепт под импортированную формулу подбирается
обычным `POST /api/solve` из своих материалов.

**Input:**
```json
{
  "recipe": "https://glazy.org/recipes/72382"
}
```

**Параметры:**
- `recipe` (обязательный, если нет `recipe_id`): ссылка на рецепт или его ID. Понимает `72382`, `"72382"`, `https://glazy.org/recipes/72382`, `glazy.org/recipes/72382` без схемы, ссылку со слагом, query или якорем. Хост должен быть `glazy.org`, `www.glazy.org` или `api.glazy.org`, а `recipes/<id>` — первым сегментом пути: ссылка на поиск или на страницу материала со списком рецептов даёт `invalid_recipe_id`, а не молчаливый импорт чужого рецепта
- `recipe_id` (опциональный): числовой ID рецепта, альтернатива `recipe`

**Output:**
```json
{
  "id": 72382,
  "name": "OVO Perfect Matte (40-25-10)",
  "url": "https://glazy.org/recipes/72382",
  "umf": {"SiO2": 2.583, "Al2O3": 0.577, "CaO": 0.742},
  "umf_source": "weights",
  "umf_glazy": {"SiO2": 2.5824, "Al2O3": 0.577, "CaO": 0.7418},
  "umf_basis_diff": 0.0006,
  "weight_percent": {"SiO2": 48.5952, "Al2O3": 18.4238, "CaO": 13.0286},
  "components": [
    {"name": "Полевой шпат FFF", "percentage": 40.0, "is_additional": false, "glazy_material_id": 20668},
    {"name": "Rutile", "percentage": 5.0, "is_additional": true, "glazy_material_id": 15393}
  ],
  "cone_from": "5½",
  "cone_to": "7",
  "thermal_expansion": 7.934
}
```

**Поля ответа:**
- `umf`: целевая формула для `POST /api/solve`
- `umf_source`: откуда взята `umf`. Возможные значения:
  - `"weights"` — пересчитана из весового анализа Glazy нашей функцией `weights_to_umf` (обычный случай)
  - `"glazy_umf"` — взята из Glazy как есть, в его базисе. Так бывает в двух случаях: весового анализа в рецепте нет, либо в нём нет ни одного флюса из `common.oxides_classification()` (`r2o` + `ro`). Во втором случае `weights_to_umf` нормировала бы формулу «по наименьшему оксиду» — произвольный базис, который решатель для своих кандидатов не воспроизводит, поэтому такой пересчёт не используется. Если и `umfAnalysis` пуст — `no_analysis` (422)
- `umf_glazy`: UMF по данным самого Glazy, для показа рядом. Производные ключи (`SiO2Al2O3Ratio`, `R2OTotal`, `ROTotal`, `xAl2O3`, `SiO2xAl2O3Ratio`) и `loi` отфильтрованы — в ответе только оксиды из `database/molar_masses.json`
- `umf_basis_diff`: максимальная разница по оксидам между `umf` и `umf_glazy` (по объединению их ключей, отсутствующий оксид считается нулём). `null`, если `umf_glazy` пуст и сравнивать не с чем. Интерфейс читает это число: до 0.01 молчит, до 0.5 показывает мягкую заметку, выше 0.5 (или при `umf_source: "glazy_umf"`) — заметное предупреждение о разных базисах. Пороги — `UMF_BASIS_DIFF_NOTE` / `UMF_BASIS_DIFF_WARNING` в `glazy_import.py` и их зеркало в `UI/js/app.js`
- `weight_percent`: оксидный анализ рецепта в весовых процентах. Сумма меньше 100: LOI в него не входит
- `components`: исходный состав рецепта в порядке Glazy. `is_additional: true` — добавка сверх 100% основы
- `cone_from` / `cone_to`: диапазон конусов обжига, HTML-сущности Glazy (`5&#189;`) раскрыты на сервере. `null`, если не указаны
- `thermal_expansion`: КТР по данным Glazy, `null`, если не указан

**Почему `umf` может отличаться от чисел на glazy.org:** UMF нормируется на сумму
флюсов, а наборы флюсов у проекта и у Glazy разные —
`common.oxides_classification()` считает флюсами FeO/CoO/NiO/CuO и не знает PbO,
современный Glazy наоборот. Поэтому таргет пересчитывается из весового анализа в
нашей конвенции, а не берётся из `umfAnalysis`: иначе на рецептах с колорантами
целевая формула была бы в чужом базисе и решатель не смог бы её повторить. На
рецептах без таких колорантов расхождение — порядка 0.0006 (см. `umf_basis_diff`).

На свинцовых рецептах расхождение большое и это **нормально**: PbO у нас не флюс,
поэтому формула нормируется на ту небольшую щёлочь, что есть в рецепте, и числа
получаются в другом масштабе, чем на glazy.org (например `SiO2: 315.9` вместо
`2.5`). Решатель считает кандидатов теми же функциями, так что таргет остаётся
внутренне согласованным и рецепт воспроизводится — но только если в инвентаре
включены свинцовые материалы (в `database/materials.json` они по умолчанию с
`inInventory: false`). Величина расхождения отдаётся в `umf_basis_diff`, чтобы
интерфейс мог об этом предупредить.

**Коды ошибок эндпоинта:** `missing_recipe` (400), `invalid_recipe_id` (400),
`glazy_forbidden` (403), `glazy_not_found` (404), `no_analysis` (422),
`glazy_unavailable` (502), `glazy_timeout` (504), `server_error` (500).

**Пример запроса с cURL:**
```bash
curl -X POST http://localhost:5000/api/glazy_import \
  -H "Content-Type: application/json" \
  -d '{"recipe": "https://glazy.org/recipes/72382"}'
```

### Чувствительность рецепта к разбросу паспортов

**Endpoint:** `POST /api/sensitivity`

**Описание:** Отвечает на вопрос «на чём держится этот рецепт»: насколько
неопределённость паспортных анализов материалов двигает итоговую UMF и какой
материал двигает её сильнее всех.

Прямой расчёт формулы исходит из того, что числа в `formula` точны, а на деле
паспорта расходятся и партии плывут: у одного нефелина бывает два разных
сертификата, фритты меняются от варки к варке, у гидратов (улексит, бура) гуляет
степень гидратации. Этот эндпоинт ранжирует материалы по произведению
**чувствительность × неопределённость**, а не по одной чувствительности: у
кварцевой муки огромное плечо по SiO2, но её анализ (99–100% SiO2) не врёт
никогда, а у улексита плечо меньше — и опасен именно он.

Как считается: базовая UMF рецепта, затем для каждой пары (материал, оксид)
одна ячейка анализа возмущается на свою сигму `A[i][j] → A[i][j] * (1 + σ)`, и
формула пересчитывается целиком. Погрешность по оксиду результата —
квадратичная сумма откликов, вклад материала — та же сумма, нормированная на
масштаб оксида `max(UMF, 0.1)`. Возмущённая формула материала намеренно **не**
перенормируется: формулы в базе суммируются меньше 100, остаток — неявные ППП,
так что рост одного оксида съедает именно его. Это модель «в партии чуть больше
бора и чуть меньше воды».

Разброс берётся из `database/material_tolerance.json` (классовые дефолты плюс
переопределения по конкретным оксидам). Файл рассчитан на ручную правку
пользователем — см. `database/material_tolerance.md`; он перечитывается на
каждый запрос, так что правка действует сразу, без перезапуска сервера.

Расчёт вынесен в отдельный эндпоинт, а не добавлен в `/api/solve`, потому что он
опциональный и стоит одного полного пересчёта UMF на каждую пару
(материал, оксид).

**Input:**
```json
{
  "recipe": {
    "Нефелин-сиенит VR13": 30,
    "Кварцевая мука Кварцверке W12": 20,
    "Волластонит МИВОЛЛ": 20,
    "Улексит (Химпэк)": 15,
    "Каолин КЖФ-1": 15
  }
}
```

- `recipe` (обязательный): рецепт в весовых процентах, ключ — имя материала точно как в `database/materials.json`

Доля материала должна быть положительным конечным числом не больше `1e6`. Это
проценты, всё что выше — не рецепт; и дело не только в здравом смысле:
погрешность копится как **квадрат** отклика, так что доля порядка `1e157`
(сама по себе вполне конечная) даёт `sigma`, равную бесконечности. Материал с
негодной долей выбрасывается из расчёта с записью в `warnings`; если так
отбракован весь рецепт — ответ `no_known_materials` (422).

Параметра `inventory` здесь нет, в отличие от `/api/solve`: имена материалов
всегда ищутся по **всей** базе. Рецепт называет свои материалы сам, искать
нечего, а выбросить материал только потому, что его нет в инвентаре, значит
посчитать чувствительность урезанного рецепта и вернуть её вместе с `umf`,
которая уже не совпадает с анализируемой формулой. Запрос, который всё ещё
присылает `inventory`, обрабатывается как обычно, а сам параметр
игнорируется — с предупреждением в `warnings`, потому что числа в ответе такому
клиенту приходят уже не те, что раньше.

**Output:**
```json
{
  "umf": {"SiO2": 3.151, "Al2O3": 0.379, "CaO": 0.718, "B2O3": 0.266},
  "per_oxide": [
    {"oxide": "B2O3", "value": 0.266, "sigma": 0.02779, "relative": 0.1044},
    {"oxide": "SiO2", "value": 3.1511, "sigma": 0.10561, "relative": 0.0335}
  ],
  "by_material": [
    {"material": "Улексит (Химпэк)", "share": 0.700380805, "via_oxide": "B2O3",
     "sigma_used": 0.1, "affects": ["B2O3", "MgO"]},
    {"material": "Волластонит МИВОЛЛ", "share": 0.225718449, "via_oxide": "CaO",
     "sigma_used": 0.05, "affects": ["SiO2", "Al2O3", "B2O3"]}
  ],
  "warnings": [],
  "error": null
}
```

- `umf`: базовая формула рецепта, для сверки с тем, что показывает интерфейс
- `per_oxide`: погрешность по каждому оксиду результата, отсортировано по `relative` (`sigma / value`) по убыванию — то есть «какому оксиду формулы верить меньше всего»
- `by_material`: вклады материалов, отсортировано по `share` по убыванию. `share` — доля материала в суммарном вкладе; сумма по всем материалам равна 1.0 везде, кроме вырожденного случая ниже, когда все доли нулевые. `via_oxide` — через какой свой оксид материал вносит основной вклад, `sigma_used` — какая сигма для него взята, `affects` — 1–3 оксида результата, которые он двигает сильнее всего. Читается как фраза: «улексит → через B2O3 → двигает B2O3 и MgO»
- `warnings`: что пошло не так, но не помешало посчитать. Полный перечень: материал не найден в базе; доля материала не число, не конечное число или больше 1e6; подозрительно малая сумма флюсов; ранжирование идёт только по плечу (все материалы получили одну и ту же сигму); база допусков не прочитана; `default_relative` в ней непригоден и заменён на 0.05; часть базы допусков выброшена — секция неверного типа, запись материала неверного типа, ссылка на класс без пригодной сигмы, секция `oxides` неверного типа, непригодное переопределение по оксиду, сигма больше 100%; нулевая сумма вкладов; сумма вкладов не является конечным числом; проигнорированный параметр `inventory`
- `error`: `null` при успешном расчёте

Материал с пустой `formula` (пигменты, SiC, КМЦ, вода, гипс — таких в базе 37)
попадает в `by_material` с `share: 0.0` и `via_oxide: null`: он не влияет на
формулу вообще, и это тоже ответ.

Вырожденный случай: если в UMF рецепта остался единственный оксид (например
`{"Мел, CaCO3": 100}` — это ровно `CaO 1.0`), то сдвинуть формулу не может ни
один материал, все `share` равны нулю и в сумме дают 0, а не 1.0. Расчёт при
этом успешен, а объяснение лежит в `warnings`.

Если все материалы рецепта получили **одну и ту же** сигму, расчёт не падает, но
ранжировать их разбросу паспортов нечем — ответ вырождается в «по одному плечу»,
то есть ровно в тот бесполезный ответ, ради ухода от которого эндпоинт и
написан. Это состояние всегда видно в `warnings`, вместе с самой сигмой.

Определяется оно **по самому ответу**, а не по виду файла допусков: пригодность
сигмы зависит не только от файла, но и от рецепта и от `database/materials.json`.
И сравниваются применённые сигмы **друг с другом**, а не с `default_relative`:
плоским ответ делает то, что материалы ничем не различаются, а на каком именно
числе они сошлись — неважно. Под предупреждение попадают и недоступный файл, и
пустой `{}`, и опечатка в ключе (`class` вместо `classes`), и здоровый файл,
который просто не описывает материалы этого рецепта или разошёлся с ними в
именах (поставщик переименовал материал), и переопределение на оксид, которого у
материала нет, — и, чаще всего, совершенно исправный файл на рецепте, все
материалы которого сидят в одном классе или в классах с одинаковым числом
(`feldspar` и `silica` — оба 0.02, обе золы — 0.20, оба карбоната — 0.01, рецепт
из одного материала). Все эти случаи дают одинаковый по смыслу ответ, поэтому и
сообщение у них одно.

Само сообщение — это **факт**, а не диагноз файлу: «все материалы этого рецепта
получили одну и ту же сигму X». Причина к нему приписывается только тогда, когда
расчёт может её проверить прямо здесь, — сейчас такая причина одна: «ни одно имя
из базы допусков не совпало с материалами рецепта».

Если выброшена только часть файла (скажем, `classes` списком, а `materials` целы:
переопределения по оксидам ещё работают, классовые сигмы уже нет), расчёт
остаётся содержательным, а в `warnings` попадает описание того, что именно
выброшено: секция или запись неверного типа, ссылка на несуществующий класс,
непригодное значение внутри `oxides`, сигма больше 100%. Описывается только
**содержимое файла**, без вывода о том, что из-за этого взяли материалы:
выброшенная запись могла относиться к материалу, которого в рецепте нет вовсе.
Здоровый файл не добавляет в ответ ничего.

Все числа в ответе всегда конечные. Если расчёт дал бесконечность или NaN —
например, в `materials.json` руками вписали в `formula` бесконечность или NaN —
эндпоинт отвечает `nonfinite_result` (422), а не отдаёт `"Infinity"` строкой в
поле, документированном как число. Нечисловая ячейка (`"много"`, `null`) — это
не этот случай: она роняет расчёт на `TypeError` и отвечает `server_error` (500).

Если сумма флюсов рецепта нулевая, UMF не на что нормировать (`weights_to_umf`
в этом случае берёт за единицу наименьший оксид — произвольный базис), и
чувствительность считать бессмысленно: эндпоинт отвечает `no_fluxes` (422), а не
выдаёт числа. Если сумма флюсов просто мала — расчёт выполняется, но в
`warnings` попадает предупреждение о том, что формула стоит на следовых оксидах.

**Коды ошибок эндпоинта:** `missing_recipe` (400), `no_fluxes` (422),
`no_known_materials` (422), `empty_composition` (422), `nonfinite_result` (422),
`server_error` (500) — последний, в частности, на нечисловой ячейке в `formula`
материала.

**Пример запроса с cURL:**
```bash
curl -X POST http://localhost:5000/api/sensitivity \
  -H "Content-Type: application/json" \
  -d '{"recipe": {"Нефелин-сиенит VR13": 30, "Кварцевая мука Кварцверке W12": 20, "Волластонит МИВОЛЛ": 20, "Улексит (Химпэк)": 15, "Каолин КЖФ-1": 15}}'
```

### Классификация оксидов по группам

**Endpoint:** `GET /api/oxide_groups`

**Описание:** Возвращает содержимое `database/oxide_classification.json` —
единственный источник правды о том, к какой структурной группе относится оксид
и какие группы входят в unity-нормировку UMF. Ключ `unity` перечисляет **имена
групп** (не оксиды), сумма которых принимается за единицу; сейчас это флюсы
`r2o + ro`. Отдаётся та же провалидированная копия, по которой считают
решатели, а не отдельное чтение файла.

Ключ `unity_presets` — именованные конвенции флюсов: плоские списки оксидов,
которыми `common.flux_oxides(convention)` подменяет базис, собранный по группам.
`legacy` — наша конвенция (ceramicscalc-2018), совпадает по составу с `unity`;
`glazy` — конвенция современного Glazy, без `FeO/CoO/NiO/CuO`; `segerlab` —
конвенция segerlab.ru, откуда взяты наши материалы и рецепты, она дополнительно
считает флюсами `Fe2O3`, `SnO2`, `Cu2O`, `CdO` и `V2O5`. На рецепте с
колорантом знаменатель unity у них разный, и весь UMF съезжает целиком, поэтому
сравнивать наши числа с опубликованными в Glazy можно только через `glazy`, а с
опубликованными в SegerLab — только через `segerlab` (весь их постоянный
множитель 1.0022 — это `Fe2O3` в знаменателе).

`MnO2` лежит в `ro`, то есть входит в unity: два материала базы — это почти
чистый `MnO2`, и вне базиса сумма флюсов марганцевой глазури схлопывается до
следов из каолина, раздувая всю формулу в ~117 раз. Подробности — в докстринге
`common.flux_oxides()`.

**Output:**
```json
{
  "r2o": ["K2O", "Na2O", "Li2O"],
  "ro": ["MgO", "CaO", "SrO", "BaO", "ZnO", "PbO", "MnO", "MnO2", "FeO", "CoO", "NiO", "CuO"],
  "r2o3": ["Al2O3", "B2O3", "Fe2O3", "Cr2O3", "Mn2O3"],
  "ro2": ["SiO2", "TiO2", "ZrO2", "SnO2", "GeO2"],
  "unity": ["r2o", "ro"],
  "unity_presets": {
    "legacy": ["Na2O", "K2O", "Li2O", "MgO", "CaO", "SrO", "BaO", "ZnO", "PbO", "MnO", "MnO2", "FeO", "CoO", "NiO", "CuO"],
    "glazy": ["Na2O", "K2O", "Li2O", "PbO", "SrO", "BaO", "ZnO", "CaO", "MgO", "MnO"],
    "segerlab": ["Na2O", "K2O", "Li2O", "CuO", "Cu2O", "SnO2", "MgO", "CaO", "SrO", "BaO", "ZnO", "PbO", "CdO", "MnO", "MnO2", "FeO", "Fe2O3", "CoO", "V2O5"]
  }
}
```

**Пример запроса с cURL:**
```bash
curl -X GET http://localhost:5000/api/oxide_groups
```

Файл читается и проверяется **один раз, на старте сервера**, и дальше живёт в
памяти. Если он битый — нет группы, нет или пуст ключ `unity`, `unity`
ссылается на несуществующую или пустую группу, группа задана не списком, имена
оксидов не строки — сервер просто не поднимается: в лог пишется `CRITICAL` с
путём к файлу и причиной. Это сделано намеренно: при битой классификации нельзя
посчитать ни одну UMF, и «решений не найдено» вместо ошибки было бы неотличимо
от обычного пустого результата.

Поэтому у работающего сервера этот эндпоинт всегда отвечает `200`: файл заведомо
валиден, а данные берутся из прогретого кэша — удаление файла на ходу ответ уже
не меняет. Ветки `404` (`file_not_found`) и `500` (`server_error`) остаются
страховкой на случай, когда кэш ещё не прогрет (файл удалён или испорчен до
первого чтения), и до них живой сервер не доходит.

## Коды ошибок

### HTTP Status Codes

- `200 OK` - Запрос выполнен успешно
- `400 Bad Request` - Отсутствуют обязательные параметры или неправильный формат запроса 
- `403 Forbidden` - Рецепт на glazy.org не публичный
- `404 Not Found` - Запрашиваемый ресурс не найден
- `422 Unprocessable Entity` - Запрос корректен, но обработать его нельзя: у рецепта на glazy.org нет оксидного анализа, либо рецепт в `/api/sensitivity` не даёт формулы, которую можно проанализировать
- `500 Internal Server Error` - Ошибка при выполнении запроса на сервере
- `502 Bad Gateway` - glazy.org недоступен или ответил непонятным образом
- `504 Gateway Timeout` - glazy.org не ответил за отведённое время

### Error Response Format

```json
{
  "error": "error_code",
  "message": "Detailed error message"
}
```

Возможные значения `error_code`:
- `missing_umf` (400) - Параметр `umf` отсутствует либо не является непустым объектом (`[]`, `0`, строка, `null`, `{}`). Сюда же попадает тело, которое вообще не разобралось как JSON: битый JSON, неверный `Content-Type`, пустое тело. Проверяется до всего остального и одинаково в `POST /api/solve`, `POST /api/feasibility` и `POST /api/umf_to_weights` — тем же кодом и тем же текстом. У `POST /api/weights_to_umf` то же правило под своим кодом `missing_weights`
- `missing_weights` (400) - То же самое для параметра `weights` в `POST /api/weights_to_umf`: отсутствует, не является непустым объектом либо тело не разобралось как JSON. Код свой, потому что свой параметр; правило общее
- `missing_recipe` (400) - В `POST /api/glazy_import` не передан ни `recipe`, ни `recipe_id`; в `POST /api/sensitivity` не передан `recipe` либо он пустой
- `invalid_recipe_id` (400) - Из `recipe` не удалось вытащить ID рецепта Glazy
- `unknown_solver` (400) - В параметре `solver` передано значение, отличное от `classic` и `iterative`
- `glazy_forbidden` (403) - Рецепт Glazy не публичный; импорт работает только с публичными рецептами
- `file_not_found` (404) - Файл базы данных не найден
- `not_found` (404) - Запрашиваемый API-эндпоинт не существует
- `glazy_not_found` (404) - Рецепта с таким ID на glazy.org нет
- `empty_target` (422) - После чистки цели `POST /api/solve` не осталось ни одного пригодного оксида: все имена неизвестны либо все значения отрицательные/`NaN` (пустой `umf` сюда не относится — это `missing_umf` выше). Что именно выброшено — в `warnings`. Отдельный код, а не 400, потому что запрос синтаксически верен и клиент может его починить; движки на такую цель отвечали по-разному (`iterative` — пустым списком, `classic` — падением в numpy), поэтому отвечает эндпоинт
- `zero_target` (422) - Цель `POST /api/solve` пережила чистку, но просит **ноль всего**. Это не UMF: единица, на которую нормируется формула, — сумма её же оксидов, здесь она нулевая, поэтому нормировать не на что и подбирать нечего (`classic` падал на этом делением на ноль, `iterative` отвечал пустым списком). Ноль **рядом с настоящим значением** — обычное ограничение «этого не хочу», такая цель решается как всегда
- `no_analysis` (422) - У рецепта Glazy нет оксидного анализа, импортировать нечего
- `no_fluxes` (422) - В рецепте `POST /api/sensitivity` нет флюсов (R2O/RO): unity-базис UMF не определён, чувствительность считать не на чем
- `no_known_materials` (422) - Ни один материал рецепта `POST /api/sensitivity` не пригоден для расчёта: имени нет в базе либо доля материала отбракована (не число, не конечное число, ноль или больше 1e6). Причина по каждому материалу — в `warnings`
- `empty_composition` (422) - У всех материалов рецепта `POST /api/sensitivity` пустая `formula`
- `nonfinite_result` (422) - Расчёт `POST /api/sensitivity` дал бесконечность или NaN (бесконечность или NaN в ячейке `formula` материала, переполнение при возведении отклика в квадрат). Числа не имеют смысла и не возвращаются; в лог сервера попадает первое нефинитное поле ответа с именем материала или оксида. Нечисловая ячейка (`"много"`, `null`) сюда не относится: она даёт `TypeError` и `server_error` (500)
- `calculation_error` (500) - Ошибка при расчете рецепта
- `server_error` (500) - Внутренняя ошибка сервера
- `glazy_unavailable` (502) - glazy.org недоступен или вернул неожиданный ответ
- `glazy_timeout` (504) - glazy.org не ответил за отведённое время

**Пример ошибки:**
```bash
curl -X POST http://localhost:5000/api/solve \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 4}, "solver": "magic"}'
```

```json
{
  "error": "unknown_solver",
  "message": "unknown solver 'magic', expected one of: classic, iterative",
  "warnings": []
}
```

`warnings` есть и в ответах-ошибках `POST /api/solve` — во всех пяти, пустым
списком в том числе. Если цель при этом ещё и несла нераспознанный оксид, он
будет назван там же.
