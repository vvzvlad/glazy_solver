# API документация Glazy Solver

## Базовая информация

API-сервер доступен по адресу `http://localhost:5000/api` при локальном запуске
(`python api_server.py`). Тот же процесс отдаёт статические файлы веб-UI из
директории `UI/` по корневому пути `/`.

Все API-методы принимают и возвращают данные в формате JSON.

## Движки решателя

Рецепт можно считать одним из двух движков, выбор — параметром `solver` в
`POST /api/solve`.

- **`iterative`** (по умолчанию, `solver_iterative.py`) — итеративный решатель
  по приоритетам материалов (`database/priorities.json`). Стартует с наиболее
  приоритетных материалов, на каждой итерации добавляет материал, лучше всех
  закрывающий самый дефицитный оксид, и пересчитывает NNLS. **Детерминирован**:
  один и тот же запрос всегда даёт один и тот же ответ. На эталонных рецептах
  (см. `compare_solvers.py`) точнее воспроизводит исходный набор материалов и
  обходится меньшим их числом.
- **`classic`** (`solver_classic.py`) — старое проверенное ядро. Решает NNLS на
  полном наборе материалов инвентаря, а затем перебирает случайные подмножества
  материалов, отбирая варианты с приемлемой ошибкой. Из-за случайного перебора
  **недетерминирован**: одинаковые запросы могут дать разные рецепты.

Итеративный движок выбран дефолтным по замерам на 11 эталонных рецептах
(`compare_solvers.py`, сводка в `REFACTORING.md`, раздел 8): медиана суммарной
ошибки 0.0020 против 0.0030, время решения втрое меньше, точный исходный состав
восстановлен в 10 рецептах из 11 против 2 у классики.

Формат ответа у обоих движков одинаковый: у `iterative` он дополнен полями
`objective_error`, `unlisted_weight` и `unity_scale`.

В веб-UI движок выбирается радиокнопками в карточке «Настройки расчета»;
выбор запоминается в `localStorage` браузера.

## Endpoints

### Расчет рецепта глазури

**Endpoint:** `POST /api/solve`

**Описание:** Подбирает рецепты по заданной UMF-формуле из доступных материалов.

**Input:**
```json
{
  "umf": {
    "SiO2": 4,
    "Al2O3": 1,
    "Na2O": 0.5,
    "K2O": 0.5
  },
  "max_solutions": 3,
  "min_materials": true,
  "error_tolerance": 0.01,
  "solver": "iterative",
  "inventory": ["Нефелин-сиенит VR13", "Каолин КЖФ-1"]
}
```

**Параметры:**
- `umf` (обязательный): UMF формула глазури в виде словаря оксид:значение
- `max_solutions` (опциональный, по умолчанию 3): максимальное количество возвращаемых решений
- `min_materials` (опциональный, по умолчанию true): предпочитать решения с меньшим количеством материалов; используется только движком `classic`, движок `iterative` параметр игнорирует
- `error_tolerance` (опциональный, по умолчанию 0.01): допустимое увеличение ошибки для решений с меньшим числом материалов; используется только движком `classic`, движок `iterative` параметр игнорирует
- `solver` (опциональный, по умолчанию `"iterative"`): движок расчёта, `"iterative"` или `"classic"`. Неизвестное значение → `400 unknown_solver`
- `penalize_unlisted` (опциональный, по умолчанию 1.0): насколько сильно оксид, не указанный в `umf`, прижимается к нулю. `1.0`/`true` — «не указан значит должен быть нулём», `0.0`/`false` — «всё равно», между ними мягкий вес. Используется только движком `iterative`
- `inventory` (опциональный): список имён доступных материалов. Если не передан, берутся материалы с флагом `inInventory: true` из базы

**Output:** массив решений, лучшее — первым.
```json
[
  {
    "recipe": {
      "Нефелин-сиенит VR13": 29.78,
      "Каолин КЖФ-1": 22.7,
      "Улексит (Химпэк)": 28.26,
      "Древесная зола": 19.26
    },
    "error": 0.0,
    "materials_count": 4,
    "target_composition": {
      "SiO2": 4,
      "Al2O3": 1,
      "Na2O": 0.5,
      "K2O": 0.5
    },
    "actual_composition": {
      "SiO2": 4.0,
      "Al2O3": 1.0,
      "Na2O": 0.5,
      "K2O": 0.5,
      "CaO": 1.1751,
      "B2O3": 1.0508,
      "MgO": 0.3452,
      "P2O5": 0.1294,
      "Fe2O3": 0.0812,
      "SrO": 0.0203,
      "TiO2": 0.0076
    },
    "recipe_umf": {
      "SiO2": 4.0,
      "Al2O3": 1.0,
      "Na2O": 0.5,
      "K2O": 0.5,
      "CaO": 1.1751,
      "B2O3": 1.0508,
      "MgO": 0.3452,
      "P2O5": 0.1294,
      "Fe2O3": 0.0812,
      "SrO": 0.0203,
      "TiO2": 0.0076
    },
    "weight_composition": {
      "SiO2": 34.36,
      "Al2O3": 14.57,
      "Na2O": 4.43,
      "K2O": 6.73,
      "CaO": 9.42,
      "B2O3": 10.46,
      "MgO": 1.99,
      "P2O5": 2.63,
      "Fe2O3": 1.83,
      "SrO": 0.28,
      "TiO2": 0.09
    }
  }
]
```

**Поля решения:**
- `recipe`: рецепт в виде словаря материал:весовой процент, сумма — 100
- `error`: метрика расхождения полученной UMF с целевой (меньше — лучше)
- `materials_count`: количество материалов в рецепте
- `target_composition`: целевая UMF. У движка `iterative` это очищенная целевая формула, с которой он реально работал: оксиды с неизвестным именем или некорректным значением из неё выброшены
- `actual_composition`: фактическая UMF рецепта. Содержит и оксиды, которых не было в целевой формуле — они приходят с материалами
- `recipe_umf`: копия `actual_composition`, отдельным полем для удобства фронтенда
- `weight_composition`: фактический оксидный состав рецепта в весовых процентах. Сумма меньше 100: в формулах материалов не учитываются летучие компоненты (CO2, вода)

Движок `iterative` (дефолтный) добавляет к каждому решению ещё три поля:
- `objective_error`: то, что реально минимизировал поиск — `error` плюс штраф за неуказанные оксиды
- `unlisted_weight`: применённый `penalize_unlisted`
- `unity_scale`: во сколько раз UMF рецепта пришлось пересчитать на базис целевой формулы

**Пример запроса с cURL (движок по умолчанию, `iterative`):**
```bash
curl -X POST http://localhost:5000/api/solve \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 4, "Al2O3": 1, "Na2O": 0.5, "K2O": 0.5}}'
```

**Пример запроса с итеративным движком и явным инвентарём:**
```bash
curl -X POST http://localhost:5000/api/solve \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 4, "Al2O3": 1, "Na2O": 0.5, "K2O": 0.5}, "solver": "iterative", "max_solutions": 2, "inventory": ["Нефелин-сиенит VR13", "Каолин КЖФ-1", "Кварцевая мука Кварцверке W12"]}'
```

**Пример запроса со старым классическим движком:**
```bash
curl -X POST http://localhost:5000/api/solve \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 4, "Al2O3": 1, "Na2O": 0.5, "K2O": 0.5}, "solver": "classic", "min_materials": true}'
```

Конкретные рецепты в ответе движка `classic` от запуска к запуску отличаются —
поиск идёт по случайным подмножествам материалов. Движок `iterative` (дефолтный)
на одинаковый запрос всегда отвечает одинаково.

### Импорт рецепта с glazy.org

**Endpoint:** `POST /api/glazy_import`

**Описание:** Загружает рецепт с glazy.org через публичное API Glazy и
возвращает его целевую UMF-формулу вместе с исходным составом (материалы и
проценты) для показа в интерфейсе.

Работает **только с публичными рецептами**: запрос к Glazy идёт анонимно, без
логина. Приватный рецепт отдаёт `403 glazy_forbidden`.

Материалы Glazy **не сопоставляются** с локальной базой `database/materials.json`
— они возвращаются как справка. Рецепт под импортированную формулу подбирается
обычным `POST /api/solve` из своих материалов.

**Input:**
```json
{
  "recipe": "https://glazy.org/recipes/72382"
}
```

**Параметры:**
- `recipe` (обязательный, если нет `recipe_id`): ссылка на рецепт или его ID. Понимает `72382`, `"72382"`, `https://glazy.org/recipes/72382`, `glazy.org/recipes/72382` без схемы, ссылку со слагом, query или якорем. Хост должен быть `glazy.org`, `www.glazy.org` или `api.glazy.org`, а `recipes/<id>` — первым сегментом пути: ссылка на поиск или на страницу материала со списком рецептов даёт `invalid_recipe_id`, а не молчаливый импорт чужого рецепта
- `recipe_id` (опциональный): числовой ID рецепта, альтернатива `recipe`

**Output:**
```json
{
  "id": 72382,
  "name": "OVO Perfect Matte (40-25-10)",
  "url": "https://glazy.org/recipes/72382",
  "umf": {"SiO2": 2.583, "Al2O3": 0.577, "CaO": 0.742},
  "umf_source": "weights",
  "umf_glazy": {"SiO2": 2.5824, "Al2O3": 0.577, "CaO": 0.7418},
  "umf_basis_diff": 0.0006,
  "weight_percent": {"SiO2": 48.5952, "Al2O3": 18.4238, "CaO": 13.0286},
  "components": [
    {"name": "Полевой шпат FFF", "percentage": 40.0, "is_additional": false, "glazy_material_id": 20668},
    {"name": "Rutile", "percentage": 5.0, "is_additional": true, "glazy_material_id": 15393}
  ],
  "cone_from": "5½",
  "cone_to": "7",
  "thermal_expansion": 7.934
}
```

**Поля ответа:**
- `umf`: целевая формула для `POST /api/solve`
- `umf_source`: откуда взята `umf`. Возможные значения:
  - `"weights"` — пересчитана из весового анализа Glazy нашей функцией `weights_to_umf` (обычный случай)
  - `"glazy_umf"` — взята из Glazy как есть, в его базисе. Так бывает в двух случаях: весового анализа в рецепте нет, либо в нём нет ни одного флюса из `common.oxides_classification()` (`r2o` + `ro`). Во втором случае `weights_to_umf` нормировала бы формулу «по наименьшему оксиду» — произвольный базис, который решатель для своих кандидатов не воспроизводит, поэтому такой пересчёт не используется. Если и `umfAnalysis` пуст — `no_analysis` (422)
- `umf_glazy`: UMF по данным самого Glazy, для показа рядом. Производные ключи (`SiO2Al2O3Ratio`, `R2OTotal`, `ROTotal`, `xAl2O3`, `SiO2xAl2O3Ratio`) и `loi` отфильтрованы — в ответе только оксиды из `database/molar_masses.json`
- `umf_basis_diff`: максимальная разница по оксидам между `umf` и `umf_glazy` (по объединению их ключей, отсутствующий оксид считается нулём). `null`, если `umf_glazy` пуст и сравнивать не с чем. Интерфейс читает это число: до 0.01 молчит, до 0.5 показывает мягкую заметку, выше 0.5 (или при `umf_source: "glazy_umf"`) — заметное предупреждение о разных базисах. Пороги — `UMF_BASIS_DIFF_NOTE` / `UMF_BASIS_DIFF_WARNING` в `glazy_import.py` и их зеркало в `UI/js/app.js`
- `weight_percent`: оксидный анализ рецепта в весовых процентах. Сумма меньше 100: LOI в него не входит
- `components`: исходный состав рецепта в порядке Glazy. `is_additional: true` — добавка сверх 100% основы
- `cone_from` / `cone_to`: диапазон конусов обжига, HTML-сущности Glazy (`5&#189;`) раскрыты на сервере. `null`, если не указаны
- `thermal_expansion`: КТР по данным Glazy, `null`, если не указан

**Почему `umf` может отличаться от чисел на glazy.org:** UMF нормируется на сумму
флюсов, а наборы флюсов у проекта и у Glazy разные —
`common.oxides_classification()` считает флюсами FeO/CoO/NiO/CuO и не знает PbO,
современный Glazy наоборот. Поэтому таргет пересчитывается из весового анализа в
нашей конвенции, а не берётся из `umfAnalysis`: иначе на рецептах с колорантами
целевая формула была бы в чужом базисе и решатель не смог бы её повторить. На
рецептах без таких колорантов расхождение — порядка 0.0006 (см. `umf_basis_diff`).

На свинцовых рецептах расхождение большое и это **нормально**: PbO у нас не флюс,
поэтому формула нормируется на ту небольшую щёлочь, что есть в рецепте, и числа
получаются в другом масштабе, чем на glazy.org (например `SiO2: 315.9` вместо
`2.5`). Решатель считает кандидатов теми же функциями, так что таргет остаётся
внутренне согласованным и рецепт воспроизводится — но только если в инвентаре
включены свинцовые материалы (в `database/materials.json` они по умолчанию с
`inInventory: false`). Величина расхождения отдаётся в `umf_basis_diff`, чтобы
интерфейс мог об этом предупредить.

**Коды ошибок эндпоинта:** `missing_recipe` (400), `invalid_recipe_id` (400),
`glazy_forbidden` (403), `glazy_not_found` (404), `no_analysis` (422),
`glazy_unavailable` (502), `glazy_timeout` (504), `server_error` (500).

**Пример запроса с cURL:**
```bash
curl -X POST http://localhost:5000/api/glazy_import \
  -H "Content-Type: application/json" \
  -d '{"recipe": "https://glazy.org/recipes/72382"}'
```

### Чувствительность рецепта к разбросу паспортов

**Endpoint:** `POST /api/sensitivity`

**Описание:** Отвечает на вопрос «на чём держится этот рецепт»: насколько
неопределённость паспортных анализов материалов двигает итоговую UMF и какой
материал двигает её сильнее всех.

Прямой расчёт формулы исходит из того, что числа в `formula` точны, а на деле
паспорта расходятся и партии плывут: у одного нефелина бывает два разных
сертификата, фритты меняются от варки к варке, у гидратов (улексит, бура) гуляет
степень гидратации. Этот эндпоинт ранжирует материалы по произведению
**чувствительность × неопределённость**, а не по одной чувствительности.

Что это меняет — измерено на эталонной прозрачной глазури из
`database/recipes.json`, а не выведено из общих соображений. На штатных допусках
первым идёт улексит с долей 0.700. На одной плоской сигме 0.05 для всех (это
ответ недоступного файла допусков) он падает до 0.275 и на третье место — впереди
волластонит 0.327 и нефелин 0.321. Кварцевая мука в обоих случаях последняя,
0.003 и 0.027: среди SiO2-ячеек у неё самое большое плечо в сырых единицах UMF
(+0.011 на 1% анализа против +0.010 у нефелина и +0.003 по B2O3 у улексита), но
вклад считается относительно масштаба того оксида, который двигается, а SiO2
здесь и так 3.15. По всем ячейкам сразу самое большое плечо не у кварца, а у CaO
волластонита, −0.017: он двигает SiO2 не тем, что несёт кремнезём, а тем, что
раздувает unity-базис. То есть цена
отказа от неопределённости — не «наверх вылезет кварц», а «материал с самым
ненадёжным анализом уедет на третье место».

Причём «ранжирование по одному плечу» — это даже не один ответ: отклик не линеен
по сигме (UMF нормируется на базис, который возмущение тоже двигает), так что
плоский ответ зависит от того, на каком именно числе он плоский — на 0.05 первым
идёт волластонит, на 0.2 и выше нефелин (измерено на диапазоне 1e-6…1.0).

Как считается: базовая UMF рецепта, затем для каждой пары (материал, оксид)
одна ячейка анализа возмущается на свою сигму `A[i][j] → A[i][j] * (1 + σ)`, и
формула пересчитывается целиком. Погрешность по оксиду результата —
квадратичная сумма откликов, вклад материала — та же сумма, нормированная на
масштаб оксида `max(UMF, 0.1)`. Возмущённая формула материала намеренно **не**
перенормируется: формулы в базе суммируются меньше 100, остаток — неявные ППП,
так что рост одного оксида съедает именно его. Это модель «в партии чуть больше
бора и чуть меньше воды».

Разброс берётся из `database/material_tolerance.json` (классовые дефолты плюс
переопределения по конкретным оксидам). Файл рассчитан на ручную правку
пользователем — см. `database/material_tolerance.md`; он перечитывается на
каждый запрос, так что правка действует сразу, без перезапуска сервера.

Расчёт вынесен в отдельный эндпоинт, а не добавлен в `/api/solve`, потому что он
опциональный и стоит одного полного пересчёта UMF на каждую пару
(материал, оксид).

**Input:**
```json
{
  "recipe": {
    "Нефелин-сиенит VR13": 30,
    "Кварцевая мука Кварцверке W12": 20,
    "Волластонит МИВОЛЛ": 20,
    "Улексит (Химпэк)": 15,
    "Каолин КЖФ-1": 15
  }
}
```

- `recipe` (обязательный): рецепт в весовых процентах, ключ — имя материала точно как в `database/materials.json`

Доля материала должна быть положительным конечным числом не больше `1e6`. Это
проценты, всё что выше — не рецепт; и дело не только в здравом смысле:
погрешность копится как **квадрат** отклика, так что доля порядка `1e157`
(сама по себе вполне конечная) даёт `sigma`, равную бесконечности. Материал с
негодной долей выбрасывается из расчёта с записью в `warnings`; если так
отбракован весь рецепт — ответ `no_known_materials` (422).

Параметра `inventory` здесь нет, в отличие от `/api/solve`: имена материалов
всегда ищутся по **всей** базе. Рецепт называет свои материалы сам, искать
нечего, а выбросить материал только потому, что его нет в инвентаре, значит
посчитать чувствительность урезанного рецепта и вернуть её вместе с `umf`,
которая уже не совпадает с анализируемой формулой. Запрос, который всё ещё
присылает `inventory`, обрабатывается как обычно, а сам параметр
игнорируется — с предупреждением в `warnings`, потому что числа в ответе такому
клиенту приходят уже не те, что раньше.

**Output:**
```json
{
  "umf": {"SiO2": 3.151, "Al2O3": 0.379, "CaO": 0.718, "B2O3": 0.266},
  "per_oxide": [
    {"oxide": "B2O3", "value": 0.266, "sigma": 0.02779, "relative": 0.1044},
    {"oxide": "SiO2", "value": 3.1511, "sigma": 0.10561, "relative": 0.0335}
  ],
  "by_material": [
    {"material": "Улексит (Химпэк)", "share": 0.700380805, "via_oxide": "B2O3",
     "sigma_used": 0.1, "affects": ["B2O3", "MgO"]},
    {"material": "Волластонит МИВОЛЛ", "share": 0.225718449, "via_oxide": "CaO",
     "sigma_used": 0.05, "affects": ["SiO2", "Al2O3", "B2O3"]}
  ],
  "warnings": [],
  "error": null
}
```

- `umf`: базовая формула рецепта, для сверки с тем, что показывает интерфейс
- `per_oxide`: погрешность по каждому оксиду результата, отсортировано по `relative` (`sigma / value`) по убыванию — то есть «какому оксиду формулы верить меньше всего»
- `by_material`: вклады материалов, отсортировано по `share` по убыванию. `share` — доля материала в суммарном вкладе; сумма по всем материалам равна 1.0 везде, кроме случаев, когда суммарный вклад не оказался положительным конечным числом — тогда все доли нулевые, а в `warnings` сказано, что именно случилось: вырожденный случай ниже или неконечная сумма вкладов. `via_oxide` — через какой свой оксид материал вносит основной вклад, `sigma_used` — какая сигма для него взята, `affects` — 1–3 оксида результата, которые он двигает сильнее всего. Читается как фраза: «улексит → через B2O3 → двигает B2O3 и MgO»
- `warnings`: что пошло не так, но не помешало посчитать. Полный перечень: материал не найден в базе; доля материала не число, не конечное число или больше 1e6; доля материала нулевая или отрицательная — материал в расчёт не входит; подозрительно малая сумма флюсов; ранжирование идёт только по плечу (все применённые сигмы оказались одним и тем же числом); база допусков не прочитана; `default_relative` в ней непригоден и заменён на 0.05; часть базы допусков выброшена — секция неверного типа, запись материала неверного типа, ссылка на класс без пригодной сигмы, секция `oxides` неверного типа, непригодное переопределение по оксиду, сигма больше 100%; нулевая сумма вкладов; сумма вкладов не является конечным числом; проигнорированный параметр `inventory`
- `error`: `null` при успешном расчёте

Материал с пустой `formula` (пигменты, SiC, КМЦ, вода, гипс — таких в базе 37)
попадает в `by_material` с `share: 0.0` и `via_oxide: null`: он не влияет на
формулу вообще, и это тоже ответ.

Вырожденный случай: если в UMF рецепта остался единственный оксид (например
`{"Мел, CaCO3": 100}` — это ровно `CaO 1.0`), то сдвинуть формулу не может ни
один материал, все `share` равны нулю и в сумме дают 0, а не 1.0. Расчёт при
этом успешен, а объяснение лежит в `warnings`.

Сигма берётся не на материал целиком, а на **пару материал-оксид**: применённых
сигм у материала **не больше**, чем оксидов в его `formula`, и совпадать они не
обязаны. У улексита класс `hydrate_borate` даёт 0.08, а переопределение по
`B2O3` — 0.10, то есть даже у него одного применённых сигм две.

Не больше, а не «ровно столько»: пара выпадает из расчёта, если оксида нет в
`database/molar_masses.json` (до UMF он не доходит, так что двигать его нечего),
а также если ячейка `formula` нулевая, не конечная или не число. В штатной базе
так выпадает `Loi`: у «Нефелин-сиенит А-270» 8 оксидов и 7 применённых сигм, у
«Метакаолин BMK-45» — 4 и 3, у «Дисульфид Молибдена» — 2 и 1. Других расхождений
в ней сейчас нет — ни нулевых, ни нечисловых ячеек в `formula` не встречается
(проверено по всем 216 записям).

Предупреждение выдаётся ровно тогда, когда **все применённые сигмы — по всем
парам материал-оксид — оказались одним и тем же числом**. Расчёт при этом не
падает, но ранжировать материалы разбросу паспортов нечем: ответ вырождается в
«по одному плечу», то есть ровно в тот бесполезный ответ, ради ухода от которого
эндпоинт и написан. Это состояние всегда видно в `warnings`, вместе с самой
сигмой.

Крайний случай того же множества — оно пустое: в расчёт не вошла ни одна сигма.
Предупреждение выдаётся и тогда, но числа в нём нет, вместо него написано «ни
одна сигма не вошла в расчёт». На штатной базе материалов такого не бывает;
дорога сюда, которую удалось воспроизвести, — бесконечность, вписанная руками в
`formula`, и сам ответ в этом случае приходит с `nonfinite_result` (422), а
предупреждения отдаются вместе с телом ошибки.

Определяется оно **по самому ответу**, а не по виду файла допусков: пригодность
сигмы зависит не только от файла, но и от рецепта и от `database/materials.json`.
И сравниваются применённые сигмы **друг с другом**, а не с `default_relative`:
плоским ответ делает то, что сигмы ничем не различаются, а на каком именно числе
они сошлись — неважно. Под предупреждение попадают и недоступный файл, и
пустой `{}`, и опечатка в ключе (`class` вместо `classes`), и здоровый файл,
который просто не описывает материалы этого рецепта или разошёлся с ними в
именах (поставщик переименовал материал), и переопределение на оксид, которого у
материала нет, — и, чаще всего, совершенно исправный файл на рецепте, где все
применённые сигмы сошлись на одном числе (`feldspar` и `silica` — оба 0.02, обе
золы — 0.20, оба карбоната — 0.01). Все эти случаи дают одинаковый по смыслу
ответ, поэтому и сообщение у них одно.

Обратного правила нет: ни «рецепт из одного материала», ни «все материалы сидят
в одном классе» предупреждения **не гарантируют**. На штатном файле применённых
сигм две у улексита и у буры: их `B2O3` переопределён на 0.10 поверх классовых
`hydrate_borate` 0.08. Поэтому `{"Улексит (Химпэк)": 100}`,
`{"Бура, Na2O 2 B2O3 10 H2O": 100}` и их смесь отвечают **без** предупреждения,
хотя материал один или класс один. `{"Нефелин-сиенит VR13": 100}` предупреждение
даёт — но потому, что переопределений у нефелина нет и все его оксиды идут по
классовым 0.02, а не потому, что материал в рецепте один.

Само по себе наличие переопределения второй сигмы не создаёт. Проверено на
штатном файле — во всех четырёх случаях предупреждение остаётся:

- переопределение равно классовому числу (`"B2O3": 0.08` при классе 0.08);
- переопределение поставлено на оксид, которого у материала нет (`ZrO2` у
  улексита);
- переопределение поставлено на оксид без молярной массы (`Loi`) — такая пара
  выпадает из расчёта целиком, см. выше;
- значение непригодно (`"десять"`, `0`, `-0.1`, `true`) — оно выбрасывается ещё
  при загрузке файла, и оксид уходит на сигму уровнем выше.

Само сообщение — это **факт**, а не диагноз файлу: «все применённые сигмы
оказались одним числом X». Оно говорит про множество сигм и ни про что больше.
Про материалы — намеренно ничего: материал с пустой `formula` сигмы не получает
вовсе (`sigma_used: null` в его строке), а материал, сигму получивший, всё равно
может не двигать формулу — на `{"Мел, CaCO3": 100}` мел получает свои 0.01, но
формулу не сдвигает, и в том же ответе про это написано отдельное предупреждение
(вырожденный случай выше). Причина к сообщению приписывается только тогда, когда
расчёт может её проверить прямо здесь, — сейчас такая причина одна: «ни одно имя
из базы допусков не совпало с материалами рецепта».

Если выброшена только часть файла (скажем, `classes` списком, а `materials` целы:
переопределения по оксидам ещё работают, классовые сигмы уже нет), расчёт
остаётся содержательным, а в `warnings` попадает описание того, что именно
выброшено: секция или запись неверного типа, ссылка на несуществующий класс,
непригодное значение внутри `oxides`, сигма больше 100%. Описывается только
**содержимое файла**, без вывода о том, что из-за этого взяли материалы:
выброшенная запись могла относиться к материалу, которого в рецепте нет вовсе.
Здоровый файл не добавляет в ответ ничего.

Все числа в ответе всегда конечные. Если расчёт дал бесконечность или NaN —
например, в `materials.json` руками вписали в `formula` бесконечность или NaN —
эндпоинт отвечает `nonfinite_result` (422), а не отдаёт `"Infinity"` строкой в
поле, документированном как число.

Нечисловая ячейка (`"много"`, `null`) в `formula` — это не тот случай, и её
поведение **не является контрактом**: `calculate_recipe_composition` умножает
такую ячейку на долю раньше, чем до неё доберётся чувствительность, и падает на
`TypeError`, а эндпоинт отвечает `server_error` (500). Это известная дыра, а не
обещание: на неё нельзя полагаться, и она будет закрыта отдельно — валидацией
`materials.json` на входе, а не в `sensitivity.py`. Собственная защита модуля
(`material_sigma` пропускает такую ячейку через `except (TypeError, ValueError)`)
на этом пути недостижима именно потому, что расчёт композиции падает раньше; она
работает только при прямом вызове `material_sigma`.

Если сумма флюсов рецепта нулевая, UMF не на что нормировать (`weights_to_umf`
в этом случае берёт за единицу наименьший оксид — произвольный базис), и
чувствительность считать бессмысленно: эндпоинт отвечает `no_fluxes` (422), а не
выдаёт числа. Если сумма флюсов просто мала — расчёт выполняется, но в
`warnings` попадает предупреждение о том, что формула стоит на следовых оксидах.

**Коды ошибок эндпоинта:** `missing_recipe` (400), `no_fluxes` (422),
`no_known_materials` (422), `empty_composition` (422), `nonfinite_result` (422),
`server_error` (500) — последний, в частности, на нечисловой ячейке в `formula`
материала.

**Пример запроса с cURL:**
```bash
curl -X POST http://localhost:5000/api/sensitivity \
  -H "Content-Type: application/json" \
  -d '{"recipe": {"Нефелин-сиенит VR13": 30, "Кварцевая мука Кварцверке W12": 20, "Волластонит МИВОЛЛ": 20, "Улексит (Химпэк)": 15, "Каолин КЖФ-1": 15}}'
```

### Список материалов

**Параметры запроса:**

```json
  {
    "name": "Нефелин-сиенит VR13",
```

## Коды ошибок

### HTTP Status Codes

- `200 OK` - Запрос выполнен успешно
- `400 Bad Request` - Отсутствуют обязательные параметры или неправильный формат запроса 
- `403 Forbidden` - Рецепт на glazy.org не публичный
- `404 Not Found` - Запрашиваемый ресурс не найден
- `422 Unprocessable Entity` - Запрос корректен, но обработать его нельзя: у рецепта на glazy.org нет оксидного анализа, либо рецепт в `/api/sensitivity` не даёт формулы, которую можно проанализировать
- `500 Internal Server Error` - Ошибка при выполнении запроса на сервере
- `502 Bad Gateway` - glazy.org недоступен или ответил непонятным образом
- `504 Gateway Timeout` - glazy.org не ответил за отведённое время

### Error Response Format

```json
{
  "error": "error_code",
  "message": "Detailed error message"
}
```

Возможные значения `error_code`:
- `missing_umf` (400) - Отсутствует обязательный параметр umf
- `missing_weights` (400) - Отсутствует обязательный параметр weights
- `missing_recipe` (400) - В `POST /api/glazy_import` не передан ни `recipe`, ни `recipe_id`; в `POST /api/sensitivity` не передан `recipe` либо он пустой
- `invalid_recipe_id` (400) - Из `recipe` не удалось вытащить ID рецепта Glazy
- `unknown_solver` (400) - В параметре `solver` передано значение, отличное от `classic` и `iterative`
- `glazy_forbidden` (403) - Рецепт Glazy не публичный; импорт работает только с публичными рецептами
- `file_not_found` (404) - Файл базы данных не найден
- `not_found` (404) - Запрашиваемый API-эндпоинт не существует
- `glazy_not_found` (404) - Рецепта с таким ID на glazy.org нет
- `no_analysis` (422) - У рецепта Glazy нет оксидного анализа, импортировать нечего
- `no_fluxes` (422) - В рецепте `POST /api/sensitivity` нет флюсов (R2O/RO): unity-базис UMF не определён, чувствительность считать не на чем
- `no_known_materials` (422) - Ни один материал рецепта `POST /api/sensitivity` не пригоден для расчёта: имени нет в базе либо доля материала отбракована (не число, не конечное число, ноль или больше 1e6). Причина по каждому материалу — в `warnings`
- `empty_composition` (422) - У всех материалов рецепта `POST /api/sensitivity` пустая `formula`
- `nonfinite_result` (422) - Расчёт `POST /api/sensitivity` дал бесконечность или NaN (бесконечность или NaN в ячейке `formula` материала, переполнение при возведении отклика в квадрат). Числа не имеют смысла и не возвращаются; в лог сервера попадает первое нефинитное поле ответа с именем материала или оксида. Нечисловая ячейка (`"много"`, `null`) сюда не относится: она даёт `TypeError` в `calculate_recipe_composition` и `server_error` (500). Это известная незакрытая дыра, а не контракт — см. раздел эндпоинта
- `calculation_error` (500) - Ошибка при расчете рецепта
- `server_error` (500) - Внутренняя ошибка сервера
- `glazy_unavailable` (502) - glazy.org недоступен или вернул неожиданный ответ
- `glazy_timeout` (504) - glazy.org не ответил за отведённое время

**Пример ошибки:**
```bash
curl -X POST http://localhost:5000/api/solve \
  -H "Content-Type: application/json" \
  -d '{"umf": {"SiO2": 4}, "solver": "magic"}'
```

